# Cost juror, round 2 — the-fleet-writes-the-design

Position: amend

The revision applies every round-1 cost amendment in substance. The spec run now has a switch that defaults off, its own key, its own worktree, a time bound, a failure store, a stop after 3, a cross-machine claim on origin, a start rule that shares one non-slice slot with the verify run, and a cost line. The spike slice is now the smallest design for its Changelog line: six phase guards and no new rule. Two new defects remain in the bounds, and both leave a person with no command that works. First, the restart command cannot lift the fleet-wide halt, so after 3 failures the spec run is dead for good. Second, a run "succeeds" when its branch carries any commit, so a run that pushes and opens no PR holds the plan with no row and no restart. Both are small text changes to the plan. The cost line also counts the host writes and the model wrong. Amend, then proceed.

## Findings

1. **high — the restart command cannot lift the halt, so 3 failures stop spec runs permanently.** The plan halts every spec run at "3 failures across plans since the last success" (plan `:58`), and `specStart` tests `halted` before `stopped` and `waiting` (plan `:47`). The halt reads `failedAt` and `lastSuccessAt` across plans (`packages/domain/src/rules/auto-verify.ts:73-85`), and only a success moves `lastSuccessAt`. The restart command "clears the plan's failure record and deletes the claim ref … The next pass then starts a run" (plan `:61`). It does not clear `failedAt` or move `lastSuccessAt`, so the next pass reads `halted` and starts nothing, and no run can ever succeed to lift it. One plan that fails 3 times reaches `stopped` and `halted` together, so the plan's own restart path dead-ends on its first use. The verify run escapes this because its restart is a person's run, `/plot-deliver --verify <slug>` (`auto-verify.ts:334`), which can succeed by itself; the spec restart only hands the start back to the fleet. Checked: `auto-verify.ts:1-180`, `:321-336`, `auto-deliver.ts:71-112`, plan text. Acceptance (plan `:97`, `:99`) tests `halted` and tests restart, but never restart after a halt.
2. **medium — success is "the branch reads `work`", not "a draft PR exists", and the gap has no control.** A run that commits and pushes but whose `pr-create` fails (a GraphQL limit, a host 5xx), or that hits `Worker bound` after a partial commit, leaves `idea/<slug>-spec` reading `work` with no PR. The plan records that as success (plan `:58`). `designWork` then answers `none` for that plan forever (`specRef` is `work`, plan `:46`), the failure store has no record, so *Waiting on you* shows no row, and the restart command deletes a `work` ref only "when the spec PR is closed unmerged" (plan `:61`): with no PR at all, its answer is unstated. The person has no signal and no command. Checked: plan `:46`, `:58`, `:61`; `claimTip` answers (`packages/domain/src/rules/claim.ts:5-15`).
3. **medium — the cost line undercounts host writes and names a model this repository does not declare.** Plan `:63` states "two host writes (the push and `pr-create`)". The run makes three on success: fleetd's claim push (plan `:54`), the agent's push, and `pr-create`; a failed run adds a claim-ref delete, and the restart adds one PR-state read. "Opus in this repository's commands" is not a fact on main: `CLAUDE.md` declares no `Design command` and no `Auto-design` (grep, 0 hits; `Verify command` and `Auto-verify: false` are at `CLAUDE.md:102-103`). The plan does not say whether it adds the two keys to this repository's config. Checked: `grep` over `CLAUDE.md`.
4. **medium — a crashed or killed run leaves a `claim-only` ref and a worktree that nothing reports.** Settlement happens "when the run ends" (plan `:55`, `:58`). If fleetd stops or the machine restarts mid-run, no settlement runs: the claim ref on origin reads `claim-only`, `designWork` answers `none` (plan `:46`), and no failure record exists, so *Waiting on you* shows nothing. The worktree under `.plot/state/design/<slug>/` stays. The verify run has no precedent here because it runs in `repoRoot` (`packages/fleet/src/shared/auto-verify.ts:531`), so the worktree lifecycle is new code with no reaper. `Claim stale after: 24` exists in the config but the plan does not use it for spec claims. Checked: `auto-verify.ts:520-540`, `ports/trees.ts:242-331`.

## Amendments I require

- A1. Make the restart able to start a run under a halt. Either the restart clears `failedAt` (or moves `lastSuccessAt`) as well as the plan's record, or `specStart` lets a run that a person restarted pass `halted` once. Add an acceptance case: 3 failures of one plan, restart, the next pass starts one run.
- A2. Define success as "the branch reads `work` and a draft PR for `idea/<slug>-spec` exists", read once at run end, and record a failure otherwise. State what the restart does for `work` with no PR. Alternatively, let fleetd open the draft PR through the host port after a `work` run, so the agent needs no host CLI and the fleet observes the outcome itself.
- A3. Correct the cost line: three host writes per successful run, one more per failure, and the model of whatever `Design command` this repository declares; state whether the plan adds `Design command` and `Auto-design` to this repository's `## Plot Config`.
- A4. Name what settles an unsettled run: at fleetd start, a `claim-only` spec ref with no going run on this machine and older than `Claim stale after` is recorded as a failure and deleted, and an orphan spec worktree is removed. Add one test.
- A5. Add a domain `specRow` beside `verificationRow`, unit-tested in `design-work.test.ts`, and keep at most one browser test for the rows.
