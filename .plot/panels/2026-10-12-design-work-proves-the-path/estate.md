# Estate lens — design-work-proves-the-path

Position: amend

The plan's cited line numbers are correct. Its estate claims are not. A spike marker, a pre-approval tracer path and three approved-only dispatch gates already exist, and the plan names none of them. Each gap has a direct fix in the plan text, and none of them re-decides D3–D5. My position is amend, not reject.

## Findings

1. **A spike marker already exists, and the plan says none does. Severity: high (blocks approval).** `packages/board/src/contract/schema.ts:1488-1521` defines `SPIKE_SLICES = ['tracer', 'spike']` and `isSpikeSlice(wave)`. A slice whose heading is `### Tracer`, `### Spike` or `### Tracer bullet` reads as a spike, and `packages/board/src/app/lib/agent-rows/rows.tsx:1210-1231` renders an amber `spike` badge and `data-slice-kind="spike"` for it. `schema.ts:2095-2098` records the operator model of 2026-08-21: *"a tracer or spike produces a REFINED PLAN; that plan is cut into slices"*. That model is D4's model. The Notes line *"`spike` returned no marker"* is false. The plan adds a second spike marker (`<!-- spike -->` on a branch line) beside the first, and says nothing about which one wins. A plan can carry `### Spike` with no annotation (the board says spike, `spikeOf` says none), or an annotated branch under `### Implementation` (the reverse). `spikeOf` also lands in the domain while `isSpikeSlice` stays in the board contract. Two rules answer one question, and no corpus test or declaration holds them together.

2. **The estate already has a pre-approval tracer path, and the plan replaces it without saying so. Severity: high (blocks approval).** `skills/plot/SKILL.md:282-298` and `.plot/templates/plan.md:69-82` describe `### Tracer` + `### Implementation`. `SKILL.md:294`: *"Pre-approval (Draft): Tracer code lives on the `idea/<slug>` branch … Update `Status:` to `Complete` and add a `## Tracer Results` section"*. `skills/plot-approve/SKILL.md:138-157` (step 2b) reads `### Tracer` with `Status: Complete` and warns on an incomplete one. That is the estate's current answer to "prove the path before approval". The new spike path is different: the spike is dispatched from the default branch, a person approves it, and approval refuses `spike-unmerged`. Slice 4 only says `/plot-approve` and `SKILL.md` "describe the spike path". It does not say whether step 2b, the `### Tracer` heading convention and the template comments are retired, kept as a lighter alternative, or mapped onto `<!-- spike -->`. So the estate ends with three meanings of *tracer*: a `### Tracer` slice that `isSpikeSlice` reads as a spike, a `Type: tracer` plan, and the `tracer-bullets` skill. The Notes line says `### Tracer` "orders slices inside a plan and does not mark a plan". That is half the story: the board also reads it as a spike.

3. **Dispatch has two more approved-only gates that `sliceVerdict` does not open. Severity: high (blocks approval).** The plan changes only `sliceVerdict` (`rules/eligible.ts:43`, `:107`) and says *"`/plot-dispatch` and the dispatch endpoint can then dispatch the spike"*. That is not true:
   - `packages/domain/src/workflows/dispatch.ts:527-546` `plangate` admits only `approved`, and refuses `design` with `state-wrong` (*"not Approved"*).
   - `skills/plot/scripts/plot-dispatch.sh:2795-2830` holds the shell copy of the same phase gate, read from `origin/<main>`. The comment at `rules/eligible.ts:36` says that `DISPATCHABLE_PHASE` mirrors this gate.
   - `packages/domain/src/workflows/implement.ts:131-138` refuses `draft` and `design` with `state-too-early`.
   - `packages/domain/src/rules/phase-gate.ts:185-186` `phaseGateRefusal` (the PreToolUse hook `plot-phase-gate.sh`) refuses an implementation commit while the plan is `Design` on the shared ref. The plan maps the branch to the plan by slug (`slugOfBranch`, `:77`), so this refusal hits a spike branch named after its plan.

   A spike that `sliceVerdict` calls `eligible` would still be refused at dispatch, at implement and at the agent's first commit. Each gate must learn "the approved spike of a Design plan", and the shell gate must agree with the domain one. Under *A Shell Script Asks The Domain*, that is a declared duplicate, or the shell gate moves into the domain.

4. **`Spike approved:` opens dispatch, and no gate guards the write. Severity: medium.** `rules/state-transition.ts:18-29` `statusStateOf` and `owningCommand` (`:93-107`) cover the `State:` line only. The plan says *"`State:` does not change, so the state gate is not involved"*. That is the problem: under D4, `Spike approved:` is an approval and only a person may give it, but a hand edit or a master agent's `sed` writes it with no refusal. CLAUDE.md *Gates Over Rules* and *The Master Agent Uses The Controllers* (the `setSprintState` measurement) predict this exact bypass. A sibling write has the same exposure: `the-fleet-writes-the-design` (`designWork`, table row 2) reads this record to auto-dispatch.

5. **Under the Open Point 4 default, the merged plan PR already means "approved" to the existing approve controller. Severity: medium.** `packages/board/src/server/entry/approve.ts:574-575`: *"PR #N is already merged — the approval already happened"*. The plan's default merges the plan PR at spike approval with `State: Design`. The later `/plot-approve` on a `Review: pr` plan then takes the merged-PR branch, and `approve()` (`transitions/plan.ts:310-313`) checks no reviewer for `pr`. So the second approval, the confirmation of rewritten slices, gets no review and no named person. The plan says it *"records through the `in-session` channel"*. But `approve()` switches on the file's `Review:` value, and nothing in the plan changes that value or adds a channel override. The plan must state how the second approval names a person.

6. **The new `proven` status has readers the plan does not list. Severity: medium.** `PlanStatus` exists twice: in the domain (`rules/phase.ts:26`) and on the wire (`contract/schema.ts:395`). Both need `proven`. `board/src/server/fleet.ts:6385-6400` and `:6465-6478` count sprint progress with a `switch` on status that has no `proven` arm, so a proven tracer plan would drop out of the open/WIP/done counts. `board.ts:2096-2117` and `:2226-2240` derive `card.deliverable` from `status === 'deliverable'`, so a proven tracer plan loses the Deliver control, and the plan never says whether a person may deliver it alone. `entry/ask.ts:46` (`plot-ask.mjs deliverable`) and `server/deliver.ts:278-336` answer a `deliverable` verdict that a tracer plan will no longer reach. Automatic delivery reads `phase === 'approved'` plus `allSlicesMerged` directly (`rules/auto-deliver.ts:180`, `:279`, `:355`), not `planStatus`, so making `proven` replace `deliverable` does not make auto-delivery skip a tracer. The slice names that skip separately, which is correct, but the Approach implies the opposite.

7. **`Type: tracer` has more readers than `norm_type`. Severity: low.** `packages/board/src/server/idea.ts:519-521` refuses any type except feature/bug/docs/infra, so the board's idea route cannot create a tracer plan. `packages/domain/src/workflows/release.ts:257` branches on `docs`/`infra`. `ports/plan-store.ts:28` documents four types. Open Point 6 covers the meaning, but the slice does not list these callers.

8. **No domain plan parser exists for annotations. Severity: low.** `waits:` and `deferred:` reach the domain only through `plot-plan-meta.sh` JSON (`domain/src/adapters/plan-store/plan-store-shell.ts:14-74`), and no TypeScript parser reads them. *"`plot-plan-meta.sh` and the domain's plan parser read two new markers … or the parse moves into the domain parser alone"* therefore names a component that does not exist. The marker also has to work in both slice dialects: list items, and `### Name (Branch: …)` headings (`plot-plan-meta.sh:1048-1066`, and `:391-392` for the annotations both dialects read). The plan names only "a branch line".

9. **Slice order collides with a sibling. Severity: low.** `feature/a-tracer-plan-stays-in-design` changes the auto-bump to read `proven`. That bump lives at `board.ts:2082-2117`, which `the-phases-are-declared`'s `feature/the-board-draws-the-declared-phases` rewrites. This plan waits only on `feature/the-phases-are-a-declaration`. `approveSpike` and the `approve` change both edit `transitions/plan.ts`, which `feature/a-draft-can-need-design` (`needsDesign`) also edits. In the other direction, `the-fleet-writes-the-design` waits on this plan's last slice although it needs only `spikeOf` and `Spike approved:` (slices 1–2). That costs time, not correctness.

10. **The cited lines are correct.** I read each one: `rules/eligible.ts:43` (`DISPATCHABLE_PHASE`) and the `sliceVerdict` body at `:92-108`; `rules/phase.ts:147-163` (`planStatus`); `transitions/plan.ts:258` (`approve`); `plot-plan-meta.sh:448` (`norm_type`, four words) and `:94` (the `design` comment); the `### Tracer` heading comment at `:1054`; `entities/workflow.ts:20`.
