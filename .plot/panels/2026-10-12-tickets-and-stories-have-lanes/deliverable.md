## Findings

1. **The GitHub arm already states a category, so the "no category" rows never fire on GitHub, and Changelog bullet 2 describes behaviour no slice builds.** `plot-host.sh:4730-4736` sets `statusCategory: "To Do"` for every open GitHub issue (`if $status == "open" then "To Do" else "Done"`). The lane table's first row, `category To Do → Open`, therefore wins for every open GitHub ticket, and the row `no category, open, namedByPlan true → In progress` is unreachable. On GitHub, the one tracker with no workflow states, no ticket ever reaches In progress. D7 and `DESIGN-phases.md` §5 say "Where the tracker has none (GitHub Issues)", so the intent is clear, but the plan does not name the change that makes it true. Either slice 1 changes the GitHub projection to emit `''` (and states that this changes the Delivery tab's existing rendering of `statusCategory`), or `ticketLane` treats a category that the connector derived from open/closed as no category. Must change before approval: slice 1's `builds:` or the Design must name which one.

2. **Slice 1 adds a port operation that nothing in production calls, and the real change is in `plot-host.sh`.** The board does not read the `Tracker` port for lists: `refreshIssues` calls `scriptsFor(opts).hostSaid(['issue-list', '--limit', …])` directly (`fleet.ts:1494`). The only board import of the `Tracker` type is `server/entry/issue-status.ts:2`. Both connectors are shell-backed: `tracker-shell.ts:145` runs `plot-host.sh issue-list`. So `issueListClosed(since)` on `tracker-github.ts` and `tracker-jira.ts` needs a new `plot-host.sh` operation or flag (a `gh issue list --state closed --search "closed:>=…"` arm and a Jira JQL arm), and slice 2 needs to call either the port or that operation. Neither slice's `builds:` names the `plot-host.sh` change, and slice 2 does not say whether `refreshIssues` moves onto the port. The deliverable of slice 1, as written, is testable only through the fixture connector. Must change before approval: name the shell operation in slice 1, and name in slice 2 which caller the fold uses.

3. **The delta has no operation to ask.** The Design says "each later fold asks for issues updated after the watermark". Slice 1 adds only `issueListClosed(since)`, which filters by close date, and `Issue` carries no `updatedAt` (`issue.ts:33-59`). A ticket that reopens is not in a closed-since list. The plan relies on the open list to move it back, but the open list is capped at 50 (`fleet.ts:190` `ISSUE_LIMIT`) and the Jira default scopes it to `assignee = currentUser() AND resolution = EMPTY` (`plot-host.sh` Jira arm, the `jql=` line). So "a closed ticket that reopens moves at the next fold" is not guaranteed by any slice. Must change before approval: either slice 1 adds an updated-since read (and `Issue.updatedAt`), or the Design drops the watermark delta and states the fold re-reads closed-since-14-days plus the open list.

4. **"Every closed ticket" has no scope and no pagination.** The Jira arm reads one page (`maxResults` default 50, and the comment states no `nextPageToken` loop is needed because the inbox is small). `gh issue list` defaults to 30. The first fold "reads every closed issue once", which needs a page loop that no slice names. The Design also does not say whether the closed Jira query keeps the default scope (`assignee = currentUser()`, `Ticket prefixes`) or the `PLOT_JIRA_JQL` override; with the scope, the toggle shows "every closed ticket assigned to me", which is not what Changelog bullet 3 says. Bound size is story Open Point 8 and can stay open; the scope and the pagination must be stated before approval, because they decide what slice 1 ships.

5. **No slice carries planned tickets to the client.** The board payload today holds only unplanned open issues: `fleet.ts:1576-1577` filters out every issue a plan references. The In progress lane is made of exactly those tickets (`namedByPlan` true). Slice 2 says "the board reads the index", and slice 3 says it builds the lanes, but neither names the payload change: a field in `contract/schema.ts` (`:4167` `issues: z.array(IssueRowSchema)`) that holds planned and closed tickets with `closedAt` and `namedByPlan`, without leaking them into *Waiting on you*. Must change before approval: put the payload field in slice 2's or slice 3's `builds:`.

6. **The `waits:` sits on the wrong slice.** Slice 1 (`feature/the-tracker-lists-closed-issues`) waits on `feature/the-tabs-are-discovery-planning-delivery`. A port operation and its connectors do not need the Discovery tab. The Note (`:81`) gives the reason "the Discovery tab exists only after that slice", which is slice 3's need. Because the three headings are three waves (`.plot/templates/plan.md:80-84`), slice 3 already waits on slice 2 and slice 2 on slice 1, so slice 3 is correct by chain; slices 1 and 2 are held for no reason. Must change before approval (one-line fix): move the `waits:` to slice 3. Slice 3 does depend on slice 2 (it needs closed tickets on the board) and on slice 1 (`closedAt`), so the wave order itself is right.

7. **The single writer is undecided.** See "Did not hold" above. If the board server's `refreshIssues` folds the file, the board is a writer, and "The fleet is the one writer" is false for this index. CLAUDE.md *A Decision Reads The Index* names one writer to avoid a read-fold-write race. Must change before approval: name the process and the module that folds the issue index, beside `pr-refresh.ts`.

8. **The Jira WONTFIX sentence is wrong for Jira.** Design `:52` says "A Jira ticket closed without the `Done` category (`WONTFIX`, for example) has no category". Jira always returns a `statusCategory` for a status; a resolution is a separate field. The `issue.ts:52-56` comment that the plan echoes is about Bitbucket. A Jira ticket resolved in a status of category `To Do` takes the first row (Open) and never reaches Done. Can stay an Open Point: name the precedence of `closedAt` over category for a resolved ticket.

9. **`Issue.open` duplicates information.** Slice 1 adds both `closedAt: string | null` and `open: boolean`. The plan does not say when they disagree (for example a tracker that gives a state but no close date). Can stay an Open Point: state the invariant or drop one field.

10. **Changelog against slices.** Bullets 1 and 3 match slice 3's `builds:`. Bullet 2 matches nothing on GitHub until finding 1 is fixed. Slices 1 and 2 ship no user-visible change and have no bullet; this is acceptable for infrastructure, but the summary line "The tracker port lists closed issues, and the board reads them through the index" is the only text that names them. Also `?released=1` is the same key the Planning tab's *Show released* uses (`the-board-has-three-tabs` Design); the plan does not say whether the toggle carries across tabs. Can stay an Open Point.

11. **Testability of slice 3 holds.** `ticketLane(issue, namedByPlan, now)` takes `now` as a value and `storyLane(story)` takes a story, so each table row is a unit test with no clock or port. `StoryStanding` already includes the derived `archived` (`transitions/story.ts:36`), so `storyLane` moves `COLUMN_OF` (`StoriesTab.tsx:30-38`) into the domain without new readings. No change needed.
