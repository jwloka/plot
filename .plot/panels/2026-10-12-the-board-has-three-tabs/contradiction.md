# Contradiction juror: the-board-has-three-tabs

Position: amend

The plan agrees with D6, D8, D9 and D20 to D23 in its decisions, and most of its estate claims are true on `main` at `316d3de0e`. It disagrees with main in three places that matter. First, it says the failed-verification row in *Waiting on you* is built by `the-fleet-verifies-what-it-delivered`, but #1635 merged on 2026-10-13 without that row, and jwloka moved it to issue #1640. No slice of this plan builds it. Second, the assignee does not reach the board through `issueOf`, because the board's inbox parses `plot-host.sh issue-list` by hand in `refreshIssues`. Third, on this repository a reader that `People` matches sees zero tickets by default, because 0 of 126 open issues have an assignee. That breaks D22's rationale, "Nothing is hidden silently", and the plan's own sentence that repeats it. The plan also has no `## Acceptance` section, and it treats an undeclared GitHub login differently from the shipped `prOwnership` rule. Each defect has a contained fix, so the position is amend.

## Findings

1. **High: the plan relies on a verification row that is not on main and that no slice builds.** Evidence: plan *Waiting on you* says `verificationRow` is built and rendered in this section by `feature/the-fleet-verifies-a-delivered-plan`. `docs/plans/2026-10-12-the-fleet-verifies-what-it-delivered.md:279` records jwloka's decision of 2026-10-13: "the board's *Waiting on you* row needs a new row kind and moves to #1640". Line `:246` was amended to match. PR #1635 merged at 2026-10-13T05:55:47Z, and issue #1640 is OPEN. Its first item says "A failed or stopped verification has no row in *Waiting on you* on the board". The signature on main is `verificationRow(slug, commit, store, log, now)` (`packages/domain/src/rules/auto-verify.ts:321`), not `(plan, runState)`. `DESIGN-phases.md` §5 *Delivery* has the same stale claim. Checked with `git grep verificationRow`, `gh issue view 1640` and `gh pr view 1635`.
2. **High: a matched reader loses every unassigned ticket from the default view, and no notice says so.** Evidence: `gh issue list --state open --limit 200 --json assignees` on this repository returns 126 open issues, and 0 have an assignee. `CLAUDE.md` *Plot Config* declares `People: jwloka = Jan Wloka; ...`, so jwloka is a matched reader. The plan says "A ticket with no assignee is not the reader's" and "By default *Waiting on you* shows these". For jwloka, the default inbox is therefore empty. The D22 notice applies only to an unmatched reader. This contradicts D22's rationale ("Nothing is hidden silently"), the plan's own sentence "Nothing is hidden silently", and the shipped design note at `packages/board/src/app/lib/agent-rows/mine-filter.ts:20-30` ("a board that withholds somebody else's work from a reader who never asked is a board that lies by omission"). The issues that D11's verifier opens (`the-fleet-verifies-what-it-delivered`, one `ai-generated` issue per refuted claim) carry no assignee, so by default they also disappear from the section that is meant to show them.
3. **High: `Issue.assignee` does not reach *Waiting on you* by the path the slice names.** Evidence: `packages/board/src/server/fleet.ts:1474-1560` (`refreshIssues`) calls `hostSaid(['issue-list', '--limit', '50'])` and builds `IssueRow` from named keys by hand. The comment at about `:1545` says "a key it does not name is a key the board never shows: that is precisely how the status reached the wire and stopped here". The slice `feature/an-issue-names-its-assignee` names `issueOf` in `trackerReads` (`tracker-shell.ts:46`, `:120`) and not `refreshIssues` or `IssueRowSchema` (`packages/board/src/contract/schema.ts:3368`). The board moves to `trackerForIssues` or `issues.json` only in `tickets-and-stories-have-lanes`' spike (under a fleet) and in `feature/the-index-holds-closed-issues` (with no fleet). This plan waits on neither.
4. **Medium: the plan's rule for an undeclared GitHub reader contradicts the shipped `prOwnership` rule and the plan's own `assigneeHandle`.** Evidence: `packages/domain/src/rules/ownership.ts:66-72` matches a PR author to the reader through `resolvePerson`, and `resolvePerson` (`entities/person.ts:44-50`) resolves an undeclared login to itself. A GitHub reader with no `People` entry therefore owns their own PRs today. The plan says `assigneeHandle` resolves a GitHub login "through `resolvePerson`", which matches an undeclared login in the same way. But *An unmatched reader* treats "host login resolves to no declared handle" as unmatched, so it shows every ticket and the notice. The two sentences give different answers for the same reader. D21 and D22 do not require `People` on GitHub, where the host login and the assignee are the same kind of account.
5. **Medium: the plan gives two rules for a ticket with no assignee.** Evidence: the plan says "A ticket with no assignee is not the reader's" for `waitingTickets`. *Only my work* extends `rowsForReader`, which uses `isMine`. `isMine` keeps a row whose ownership is `unknown` (`ownership.ts:126-135`, `mine-filter.ts:126-134`). The plan does not state which rule *Only my work* applies to tickets, and it adds no `ticket` kind to `OwnedRow` (`ownership.ts:42-46`).
6. **Medium: one assignee string cannot hold a GitHub issue's assignee list.** Evidence: the GitHub arm adds `assignees` to `--json` (`plot-host.sh:4732`). GitHub returns `assignees` as an array, but the plan types `assignee: string`. The plan does not say which element the `jq` projection keeps. If it keeps one, a ticket assigned to two people leaves the other person's inbox. On this repository the count of such tickets is 0, but the rule is general.
7. **Medium: the issue-index change is conditional in the Approach and missing from the slice, but the order is already known.** Evidence: `origin/feature/the-fleet-indexes-issues` is claimed (`930cb07d7`) and is wave 1 of `tickets-and-stories-have-lanes`. This plan's assignee slice is in wave 2, after the tab rename. The assignee slice will therefore land second. Its bullet must name `assignee` in `IssueIndexSchema`, the fold that writes it, and the raised `ISSUE_INDEX_VERSION`. The bullet names none of the three.
8. **Medium: the plan does not say where the inbox filter and the 50-row cap run.** Evidence: `docs/plans/2026-10-12-tickets-and-stories-have-lanes.md:110` says `/api/fleet` carries "the rows that pass the inbox filter, newest first, capped at `ISSUE_LIMIT` (50)" (`fleet.ts:192`). This plan's `waitingTickets` also needs every unplanned ticket for the "shows every unplanned ticket" control. If the assignee filter runs after the cap, it loses a reader's tickets that are not among the 50 newest. If it runs before the cap, the control has no rows to show. The plan names neither the order nor the payload.
9. **Medium: the plan has no `## Acceptance` section.** Evidence: `grep -c '^## Acceptance'` returns 0 for this plan, and 1 each for `design-work-proves-the-path`, `the-fleet-verifies-what-it-delivered` and `tickets-and-stories-have-lanes`. The verifier panel judges "each Changelog and acceptance claim" (D11). Panel round 3 made the same finding against `the-fleet-verifies-what-it-delivered:196`. No named test proves these Changelog claims: the old `?tab=` values redirect; a Bitbucket inbox never shows empty; no Jira inbox widens at upgrade; *Show released* is off by default.
10. **Medium: the assignee slice probably fails the shell-line ratchet.** Evidence: `scripts/check-shell-lines.sh:1-20` says "MAY SHRINK AND MAY NOT GROW", with "no override, no allowance". The slice adds `jq` projection lines in two arms of `plot-host.sh` (`:4709-4716`, `:4735-4736`). It says only "the PR states the net count of `check-shell-lines.sh pr`". The sibling plan names its compensating lines, "net about −1" (`tickets-and-stories-have-lanes`, slice `the-tracker-lists-closed-issues`). This plan names none.
11. **Low: `planningColumns` builds on the wrong shipped rule.** Evidence: the plan builds `planningColumns` on `planPhases(map)`, which returns names only (`workflow-phases.ts:169`). The board draws from `phaseColumns(map)` (`workflow-phases.ts:221`, used at `packages/board/src/server/board.ts:2332`), which carries leadership, accent and the checklist flag. The columns are built on the server, and `?released=1` is a client parameter, but the plan does not say which side drops the column. A custom map (D12, D26) can put `plan:released` in a phase that also holds `plan:delivered`. "Drops the phase that holds `plan:released`" would then also hide delivered plans.
12. **Low: the URL rule for *Show released* has no stated reason against the board's own convention.** Evidence: `packages/board/src/app/components/Board.tsx:173-181` keeps "I unfolded Released" out of the URL, because the URL holds only what is worth sending to someone. `mine-filter.ts:5-15` refuses `?mine=1` for the same reason. `DESIGN-phases.md` §5 chooses `?released=1`, so the plan follows its spec. Neither document says why this toggle is worth sharing when the column fold is not. The plan also does not say where the *Active sprint* toggle is stored.
13. **Low: the *Active sprint* toggle overlaps the existing multiselect.** Evidence: `sprintMembership` (`packages/board/src/server/fleet.ts:6283-6300`) keeps only `phase === 'Active'` sprints, so the Delivery tab's multiselect (`AgentList.tsx:592-597`) already lists only Active sprints. The toggle has the same effect as checking every option. Manifesto question 5 asks for the smaller design, for example an "all active" option in the multiselect.
14. **Low: one line reference is off, and the other estate claims are true.** Evidence: `parseTab` is at `App.tsx:123`, not `:122`. I checked these claims and found them true: `App.tsx:118`; `App.tsx:633-638` (the `onTab` URL write); `mine-filter.ts:119` and `:162`; `sections.ts:25` (6 groups); `AgentList.tsx:597`, `:1123` and `:2367`; `issue.ts:21-31`; `ports/tracker.ts:31-41`; `plot-host.sh:4684`, `:4696` and `:4732`; `tracker-shell.ts:46` and `:120`; `person.ts:62-75`; `sprint.ts:9`; `planPhases` exists; `feature/the-board-draws-the-declared-phases` is merged (#1623, `5d78df1e8`). The old `?tab=agents` URL appears in 12 board test files. These tests keep working through the redirect, but tests that assert the label *Agents* will need edits.
15. **Low: wave 2 holds three branches, and two of them wait on the tab rename for no reason.** Evidence: `docs/stories/the-master-agent-holds-the-fleet/DESIGN-slice.md:57` says "A slice holds exactly one branch". *Planning and the assignee* holds three branches. Wave order makes `an-issue-names-its-assignee` and `people-names-a-tracker-account` wait on the tab rename, which neither one reads. The sibling plans group branches in the same way, so this is estate practice and not specific to this plan.

## Amendments I require

- A1. Choose one owner for the failed-verification row, to match the 2026-10-13 decision. Either add #1640's new row kind, client rendering and browser test to `feature/the-delivery-tab-filters-by-sprint-and-owner`, or state that this plan does not build the row and that #1640 owns it. Remove "which `the-fleet-verifies-what-it-delivered` builds and renders". Use the shipped signature of `verificationRow`. Raise the same correction for `DESIGN-phases.md` §5 *Delivery*.
- A2. State what a matched reader sees when the source has unassigned tickets. Either `waitingTickets` answers a notice with the count of hidden tickets, for example "126 unassigned tickets hidden", or unassigned tickets stay in the default view. Add a unit test with this repository's shape: a matched reader and zero assigned tickets.
- A3. Add the board's real path to the assignee slice: the `refreshIssues` projection at `fleet.ts:1535-1560` and `IssueRowSchema`. As an alternative, make the slice wait on the slices of `tickets-and-stories-have-lanes` that replace that path.
- A4. Make the GitHub match agree with `prOwnership`. Either an undeclared host login matches an equal assignee login, or the plan states why tickets need `People` when PRs do not. Then make `assigneeHandle` and *An unmatched reader* give the same answer.
- A5. State the rule for a ticket with no assignee under *Only my work*. Add a `ticket` kind to `OwnedRow` in `rules/ownership.ts`, so that the rule is a domain property.
- A6. Define `Issue.assignee` for a list of assignees. Either use `assignees: string[]` and match any element, or name the element the projection keeps and the cost of that choice.
- A7. Move the `IssueIndexSchema`, fold and `ISSUE_INDEX_VERSION` change into the assignee slice's bullet without a condition, because the spike lands first. State where `waitingTickets` runs relative to the 50-row cap, and which payload carries the unfiltered rows for the "every unplanned ticket" control.
- A8. Add `## Acceptance`, with one test per Changelog claim and per D22 or D23 reason. Make the assignee slice name its shell-line compensation, so that `check-shell-lines.sh pr` passes.
