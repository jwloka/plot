# Contradiction juror, round 2 — the-fleet-writes-the-design

Position: amend

The revision applies all ten of my round-1 amendments, and through the contradiction lens most of the revised plan is sound: it agrees with D3, D10's human acts, D12 and the shipped auto-verify shape, and every cited function exists on main. Three problems remain. First, Open Point 1 rests on a false premise: it says the fleet reads plans on the default branch only, but `plot-fleet-scan.sh` also reads plans from prefixed branches. The plan repeats the D13 rationale that round 1 O3 flagged and that the revision declined to correct. Second, for a `Review: pr` plan, which is the default channel, the spec run starts only after a person approves the spike, and a `Review: pr` Design plan without a spike never gets a fleet spec at all, because its approval merges the plan PR and writes `Approved` in one act. Changelog item 2 and D10 state the spec run without that limit. Third, the plan counts a run as a success when its branch reads `work`, but the Changelog says the run opens a draft PR, and a `work` branch with no PR has no row and no restart arm.

## Findings

1. **medium: Open Point 1 rests on a premise that is false on main.** Evidence: the plan says "under D13 the fleet reads plans on the default branch ... so the fleet never sees a Design plan whose plan PR is open" (plan line 71). `skills/plot/scripts/plot-fleet-scan.sh:143-158` enumerates "`origin/<main>` first, then each prefixed branch's own tree for the plans the default branch does not carry". The pulse therefore reports a `Review: pr` Design plan from its `idea/<slug>` branch with `phase: design`. The plan's reader then calls `refs.showFile` at `origin/<main>` (plan line 49), where the file is absent, and the plan does not say what follows: skip, `unread`, or a failure. The same false sentence is D13's rationale in the story (`STORY-plot-works-in-five-phases.md:88`), which round 1 O3 asked to correct. Checked by reading the scan header and the reader the plan copies (`auto-verify.ts:293-330`, which lists an unreadable plan in `unread`).
2. **high: for the default review channel, the spec run does not do what D10 and Changelog item 2 say.** Evidence: D10 (`STORY-...md:85`) says "for a plan in `State: Design` with an empty spec, the fleet commissions an agent to write it", and Changelog item 2 states it with no limit beyond the two keys. Under D13 a `Review: pr` plan reaches the default branch only when a person approves its spike (`DESIGN-phases.md:176`). So the fleet writes no spec before the spike approval, and the person approves a spike with an empty spec. A `Review: pr` Design plan with no spike never reaches the default branch in Design: `packages/domain/src/workflows/approve.ts:337-358` merges the plan PR and writes `State: Approved` in one approval, and the person arm keys on `design`, not on a spike (`approve.ts:251-256`). That plan never gets a fleet spec. The plan mentions the timing only in passing ("for plans that reach main at spike approval anyway") and does not mention the no-spike case. 98 plan files under `docs/plans/` declare `Review: pr` (grep), and this plan is one of them. Checked by reading `approve.ts` and `needs-design.ts:116-131`, which writes `State: Design` onto the plan PR's head.
3. **medium: the success rule contradicts the Changelog, and one end state has no row and no restart.** Evidence: Changelog item 2 says the agent "pushes `idea/<slug>-spec` and opens a draft PR, and a person merges it". The failure-store rule says "a run that leaves the branch reading `work` succeeded" (plan line 58). A run that pushes a commit and does not open the PR, or pushes a commit that leaves `## Spec` empty, reads `work` and counts as a success. It is then in no row, because *Waiting on you* shows failed runs only, and `designWork` answers `none` for `work`, so no run starts again. `plot-design.mjs restart` deletes a `work` ref only "when the spec PR is closed unmerged" and refuses an open one (plan line 61). It names no arm for a `work` ref with no PR. Checked against `ClaimAnswer` (`rules/claim.ts:15`).
4. **low: the cost line contradicts the retry rule.** Evidence: "Runs follow person acts only" (plan line 63). The failure store uses `retryVerdict`, which answers `ready` again after the delay and before 3 failures (`packages/domain/src/rules/auto-deliver.ts:104-112`), so the fleet starts up to two more runs with no person act.
5. **low: two line references point at the wrong line.** Evidence: `rules/claim.ts:15` is the `ClaimAnswer` type, and `claimTip` is at `:40`. `sections.ts:27` is the `working` group, and *Waiting on you* is at `:26`. Checked with `sed -n`.
6. **low: the removal leaves text that names the removed route.** Evidence: `packages/fleet/src/shared/implement-run.ts:24-33` justifies the one-capability-one-key rule with "`/api/commission` reuses `Idea command`", and the plan cites that comment as its rule but does not list it for change. `DESIGN-phases.md:40` and `:143` cite `commission.ts:136-177`, and `:268` says "this is today's *Commission design* agent". The plan edits no story file, so after the removal the binding spec names code that does not exist.
7. **low: the tab name differs from the open sibling.** Evidence: `the-board-has-three-tabs` (Draft, revised at `553c4777b`) renames the Agents tab to Delivery and changes 16 files under `packages/board/src` (its line 80). This plan adds rows and a browser test that name "the Agents tab". Whichever plan merges second must follow the other's name, and neither plan says so.
