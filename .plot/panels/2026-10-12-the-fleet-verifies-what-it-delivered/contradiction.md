Position: amend

The plan follows D11 and DESIGN-phases.md §6 closely, and its Motivation claims are true on this branch. The contradictions are with the panel mechanism it says it reuses unchanged, and with the tracker write path. The first one decides whether the record can be written at all.

## 2. Contradictions

**C1 (the main one). The panel mechanism commits one position per juror per plan, not one per claim.** `readJuror` reads every `Position:` line in a file and refuses a file whose lines name two different words: "claims both supported and refuted" (`packages/domain/src/rules/panel.ts:162-165`). `PanelReading` reports `unanimous`, `divided` by juror, or `refused` (`panel.ts:176-179`). The plan's record needs a per-claim answer ("5 supported, 1 refuted", one `## Verification` line per claim, plan lines 39-44), and `verificationOf` reads per-claim refutations. No gated output of `/plot-panel` carries that. A juror that writes one `Position:` line per claim is refused by the gate whenever claims differ, and a juror that writes one plan-level position leaves the per-claim split in prose. The per-claim record therefore comes from the moderator's prose (`skills/plot-panel/SKILL.md:155-163`), which is judgement the gate does not check. That contradicts the plan's own sentence "the fleet is its third caller and implements none of it" (line 49), and it contradicts `/plot-deliver` step 5, which reads the moderation into a checklist by a person, not into a record a machine trusts (`skills/plot-deliver/SKILL.md:191`). The plan must choose: one panel per claim (subject is still one plan, the claim goes in the rubric), a per-claim commitment label such as `Claim-3: supported|refuted` checked by one `plot-panel.mjs check` call per label (the mechanism already takes N labels, `skills/plot-deliver/SKILL.md:304-306`), or a plan-level record only.

**C2. The vocabulary is not the one step 5 uses.** DESIGN-phases.md §6 item 1 says "the vocabulary `/plot-deliver` step 5 already uses". Step 5 uses two commitment lines, `Position: supported|refuted` and `Evidence: executed|read`, and gates both (`skills/plot-deliver/SKILL.md:266-269`, `:315-320`). The plan names only `supported,refuted` (line 49) and asks jurors to "run what a claim says where it can" in prose, which is the exact rule step 5 measured as unenforced and replaced with the `Evidence:` line (`:274-294`). The plan should carry `Evidence:` into the record line ("the command a juror ran", line 43) or say why it drops it.

**C3. The fleet cannot run `/plot-panel` by naming it, and the plan names no runner, lenses or rubric.** `/plot-panel` needs four caller parameters and refuses unattended when one is missing (`skills/plot-panel/SKILL.md:58-67`, `:104-105`). The board's interrogate controller records this: "Naming `/plot-panel` directly supplies only the subject, and an unattended panel refuses when a parameter is missing" (`packages/board/src/server/interrogate.ts:111-117`), and it requires an `Interrogate command` because "no script can" run a panel (`interrogate.ts:27-28`, `:49`). Step 5's lenses "are this caller's and do not transfer" (`skills/plot-deliver/SKILL.md:247-249`). The plan names no `## Plot Config` command key for the verification agent, no lenses, and no rubric. Its sibling `the-fleet-writes-the-design` names its key (`Idea command`, its line 43) and lists the alternative as story Open Point 10. This plan needs the same: a command key (reuse `Interrogate command` or add one) and a skill-side caller that owns the lenses and rubric, as `/challenge-the-plan` does for the Draft panel.

**C4. "The fleet's capacity counts each juror like any agent" contradicts how a panel runs.** Jurors are `Task` subagents inside one process (`skills/plot-panel/SKILL.md:15`, `:109`). CLAUDE.md *The Domain Package* says the Machine counts workers, a worker is an Agent's process, and the Registry counts agents. A Task subagent is neither a process the machine sees nor an agent the registry declares. The fleet can count one verification worker; it cannot count jurors. The sentence should say what is counted.

**C5. `issueOpen` must reach the host CLI through `plot-host.sh`, and the plan does not name that op.** Every connector write goes through `plot-host.sh` (`tracker-jira.ts:67`, `:89` runs `plot-host.sh issue-status`), and `scripts/check-host-cli-callers.sh` gates any other caller (CLAUDE.md *Gates Over Rules*). The slice `feature/a-refuted-claim-opens-an-issue` names the port and "both connectors" but not a new `plot-host.sh` op, and not the four doc sites listed in section 1 that state "no ticket is created". Updating only "the port's doc" (plan line 53) leaves `tracker.ts:84-88`, `:126-129` and `plot-host.sh:4929-4934` stating the opposite of the code.

**C6. On this repository the issue write never fires.** This repo's `## Plot Config` declares no `Tracker` key (CLAUDE.md lines 1-40 of *Plot Config*; `grep -n Tracker` finds only prose). `trackerFor` maps an absent scheme to `trackerNone` (`packages/domain/src/adapters/tracker/tracker-resolve.ts:35-44`). So Plot's dog-food run of D11 opens zero issues and every refuted record says "no issue was opened". This is not a re-decision of D11, but the plan should state it and either add `Tracker: github-issues` in a slice or say that the dog-food estate will not exercise the write.

**C7. The issue is opened before the record that makes it idempotent exists.** The status write is "idempotent by nature" (`tracker.ts:129`); `issueOpen` is not. The plan makes it idempotent through the issue number in the record (line 53), but the record lands on the default branch by `commitAndPush` after the issue opens (`packages/board/src/server/entry/deliver.ts:406-426` shows the push can be `rejected`). A run that opens issues and then fails to push leaves issues with no record. "One run per plan" (line 49) stops a duplicate, but then the plan stays `unverified` forever with open issues nobody links. The plan should name this case.

**C8. The panel's directory collides with the Draft panel.** `panelDir(subject)` is `.plot/panels/<slug>` with no caller in the path (`panel.ts:32`, `:40`, `:58`), and the directory is tracked (`panel.ts:21-30`). The Draft rounds of the same plan already write there, including `panel.md`. A verification panel overwrites the Draft moderation. The plan also does not say whether the fleet commits the juror files to the default branch with the record.

**C9. The checklist shape differs from `/plot-release rc`.** `rc` writes one item per delivered feature or bug plan from its Changelog (`skills/plot-release/SKILL.md:221`, `:233-234`). The plan writes one item per supported claim of every Delivered plan (line 57), which includes docs and infra plans and changes the granularity, while it claims "the shape `/plot-release rc` writes". The board's Testing-column checklist badge reads the lexically last `*-checklist.md` (`packages/board/src/server/board.ts:419-428`; contract at `packages/board/src/contract/schema.ts:1305-1309`). `next-checklist.md` sorts before every `v*` file, so the fleet's draft never reaches that badge, and the plan's Board impact comment (line 19) does not mention the badge. (The same sort already prefers `v2.9.0` over `v2.19.0`; that is a pre-existing defect, not this plan's.)
