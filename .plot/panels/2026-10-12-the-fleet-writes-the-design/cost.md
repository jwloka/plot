# Cost juror — the-fleet-writes-the-design

Position: amend

The plan makes the fleet start an Opus agent on its own, and it names none of the bounds that its sibling `the-fleet-verifies-what-it-delivered` needed three panel rounds to add and that main now carries in `rules/auto-verify.ts` and `fleet/shared/auto-verify.ts`: no switch, no time bound, no tree, no failure record that a person can clear, and no priority against waiting slices. The spec run also starts in the operator's checkout if it copies *Commission design* as the plan says. The spike half is cheap and correct, but it can be smaller: the scan's verdict already admits only the approved spike, so the `dispatch-spike` arm duplicates a rule that exists. The removal of *Commission design* (424 lines in `commission.ts`) lowers maintenance and is the right trade. Amend, then proceed.

## Findings

1. **high — the spec run has no switch and no rate.** Every plan that reads `State: Design` with an empty spec starts one `Idea command` run, and this repository's `Idea command` is `claude -p --model opus` (`CLAUDE.md:77`), so each run is one Frontier context. The plan names no key that turns it off and no expected count. The sibling for the same fleet adds `Auto-verify`, default off (`CLAUDE.md:103`; `autoVerify` in `packages/domain/src/rules/auto-verify.ts:100`), after its round-1 cost finding (`docs/plans/2026-10-12-the-fleet-verifies-what-it-delivered.md:169`). Measured: 360 plans were added to `docs/plans/` since 2026-09-12 (`git log --diff-filter=A`), about 12 a day; 0 plans read `State: Design` today and 0 carry `## Spec`, so no base rate exists. Checked: `CLAUDE.md` config lines, `auto-verify.ts`, `git log`, `grep` over `docs/plans`.
2. **high — the spec run's tree is unnamed, and today's mechanism writes in the operator's checkout.** The plan says the agent runs *as Commission design does today*. `commission.ts:402-405` starts the run with `tree: opts.repoRoot`, the main checkout. Unattended from `plot-fleetd`, an Opus agent then commits and pushes from the checkout that the operator and the board use. The plan names no worktree, no marker file, and no cleanup; the sibling needed a whole section for this (`the-fleet-verifies-what-it-delivered.md:65`, `:193`). Checked: `commission.ts:395-424`.
3. **high — no time bound and no failure record that a person can clear.** `startBoardRun` takes `boundSeconds`, and absent means no bound (`packages/fleet/src/shared/board-run.ts:41-42`, `:235`); commission passes none. The plan records "one spec run per plan" and never starts it again, and it removes the only manual trigger (Open Point 13). A failed or closed spec run then holds the plan with no command that clears the record, so the person writes the spec by hand or edits fleet state. Main already has the mechanism to reuse: `recordDeliveryFailure`/`retryVerdict`, the in-flight store per kind, `verifyHalted` after 3 failures, and a restart command shown in *Waiting on you* (`rules/auto-verify.ts:1-85`, `the-fleet-verifies-what-it-delivered.md:134`). Checked: `board-run.ts`, `auto-verify.ts`, plan text.
4. **medium — "never displaces a slice agent" is not what the stated rule does.** The plan starts a run "when the cap has a free slot". A free slot in a pass where slices are held `no-free-agent` is the slot `scaleUp` would fill with a slice agent (`packages/domain/src/workflows/assign.ts:219-236`), so the spec run takes it. `verifyStart` refuses on `no-free-agent`, on `starved` without `Machine override`, and while one run is going (`rules/auto-verify.ts:172-186`), and `assign.ts:229` adds `verifying` to `running`. The plan names neither change, and `registryd-main.ts:980` does not state that "`Parallel agents` counts processes"; it states that the cap is the board's control (`:976`, `:983`). Checked: `assign.ts`, `auto-verify.ts`, `registryd-main.ts:970-1030`.
5. **medium — the plan-PR-head arm is unreachable, so it is code to build and keep for no run.** D13 says the fleet reads plans on the default branch only (`STORY-plot-works-in-five-phases.md:88`). For `Review: pr`, *Needs design* commits `State: Design` onto the plan PR's head branch (`packages/domain/src/workflows/needs-design.ts` doc of `NeedsDesignTarget`), and the plan reaches main only when the spike approval merges that PR. So the fleet never sees a Design plan whose plan PR is open, and every spec run goes to `idea/<slug>-spec`. The arm also needs a host call per start to find the PR head. Checked: `needs-design.ts:1-80`, D13.
6. **medium — the `designWork` table rows overlap, and the overlap costs a Frontier run per spike plan.** A plan in Design with an empty spec and a `Spike approved:` record matches row 1 and row 2. DESIGN §4 makes the spec and the spike two forms of design work (`DESIGN-phases.md:136`), so a spike-first plan with no spec text gets a spec run it may not need, and nothing says which row wins. Checked: plan table, `DESIGN-phases.md:132-150`.
7. **medium — `dispatch-spike` duplicates the scan verdict; a smaller slice 3 exists.** `sliceVerdict` already admits a `design` plan's slice only when it is the single spike and is approved (`packages/domain/src/rules/eligible.ts:63`, `:132-135`), and `planAutoDispatch`, `startableBranches` and `skippedClaimedBranches` already read `wave.verdict === 'eligible'` (`rules/auto-dispatch.ts:531-540`, `:582-584`, `:617-619`). Admitting `phase === 'design'` at those three guards gives the same Changelog line with no new rule arm. The plan names two of the three guards and cites the third in its Motivation (`:617`). Checked: `eligible.ts`, `auto-dispatch.ts:520-625`.
8. **low — host calls and review load are not named.** Each spec run pushes a branch and opens a draft PR (2 host writes through `plot-host.sh`), and each one is a PR a person reviews and merges. The plan states neither, nor the rate it expects. Checked: plan text.
9. **low — a spec run is not counted in the machine's process total.** With a verify run and a spec run going, the machine carries `Parallel agents` + 2 processes, not `+ 1` as `DESIGN-phases.md:284` states for verify alone. Checked: `DESIGN-phases.md:262-285`.
10. **low — slices 2 and 3 share one wave heading.** Each can merge alone; one heading per branch matches the estate's slice rule and lets the cheap spike change ship before the spec agent. Checked: plan `## Slices`.

Facts checked and true on main: `commission.ts` exists (424 lines) and its prompt forbids writing the spec (`:136-177`); `implement-run.ts:29` names the `Idea command` reuse; the `commission` log kind is in `KINDS` (`agent-log.ts:319`); the three `phase !== 'approved'` guards are at `auto-dispatch.ts:531`, `:582`, `:617`; `feature/the-spike-can-be-dispatched` merged as #1634, so the first slice's `waits:` is satisfied; `CLAUDE.md:499` lists `commission` among the controller endpoints and carries no count word.

## Amendments I require

- A1. Add a switch for the spec run, default off, in the shape of `Auto-verify`: a `## Plot Config` key that seeds a field in `fleet-controls.json`, with the exact-literal rule. Off starts no run.
- A2. Name the tree: the run works in its own worktree outside `Worktree root` (or under it with a marker the reaper and scan read), never in `repoRoot`, and the fleet removes it after the run. State where the commit is booked.
- A3. Bound the run with `Worker bound`, record failures with `recordDeliveryFailure`/`retryVerdict` in an in-flight store kind `design`, stop after 3, and show a failed run in *Waiting on you* with a restart command a person can run. Name that command, since the button is removed.
- A4. Write a `specStart` rule beside `verifyStart`: refuse on `no-free-agent`, on `starved` without `Machine override`, and while one spec run is going; add going spec runs to `running` in `assign.ts:229`. Correct the `registryd-main.ts:980` claim.
- A5. Drop the plan-PR-head arm under D13, or state the reading that lets the fleet see a Design plan on an open PR and price its host calls.
- A6. Make the `designWork` rows exclusive and name the order; state whether a plan with an approved spike gets a spec run.
- A7. State the cost line: Opus contexts per spec run, host calls per run, and the review load, at a stated or measured rate of plans entering Design.
