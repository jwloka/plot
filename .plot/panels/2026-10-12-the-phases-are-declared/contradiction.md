# Contradiction lens — the-phases-are-declared

Position: amend

## Summary

The plan agrees with D1–D12, with DESIGN-phases.md §2–§3 and with its five sibling plans. Its `waits:` names and rule names match what the siblings consume. It contradicts the repo in four places: MANIFESTO §10 fixes `/plot-idea` at two ceremony questions, `/plot-idea` requires an unattended answer for every question, the existing `PHASE_WORKFLOWS` doc states a different placement principle, and the prose slice risks merging two meanings of "phase" that MANIFESTO and CLAUDE.md keep apart. Each one needs a sentence in the plan, not a redesign.

## Findings

1. **Unresolved. The design question contradicts MANIFESTO §10.** `skills/plot/MANIFESTO.md:79` says "Every plan answers two independent questions" (`Review:` and `Impl:`). The `plot-idea` frontmatter (`skills/plot-idea/SKILL.md:3-5`) says "answer the two ceremony questions", and so does the CLAUDE.md Architecture row ("two-question triage"). The plan puts the design question into step 4 *Answer the Ceremony Questions* (`SKILL.md:196`) as "a third question". D3 is binding, so the question stays. But the plan must either keep the design question out of the ceremony questions (its own step, recorded as `State:`, not as a ceremony answer) or amend MANIFESTO §10 in the prose slice. Today the prose slice names MANIFESTO §"Four phases" and §"Lifecycle" only. The skill description and the CLAUDE.md row also need the change. Under §10 the "lightest allowed" default applies, so the plan must also state that the default answer is *no* (Draft).

2. **Unresolved. No unattended behaviour for the new question, and D3 needs one.** `skills/plot-idea/SKILL.md:58` says: with `PLOT_UNATTENDED=1`, "each question below declares what to do instead". The plan gives the question a Mid-tier recommendation and a Small-tier ask, but it says nothing for an unattended run. The board's idea route and this very batch run (Notes: "drafted by an unattended `/plot-idea` batch run") are unattended. If the model answers *yes* by itself, an agent decides design. That contradicts D3 ("The fleet never decides it") and DESIGN-phases.md §7 ("Deciding that a plan needs design | a person"). Add: "Unattended, the answer comes from the prompt; with no answer in the prompt the plan is created as Draft, and the output names the skipped question."

3. **Unresolved. `phaseWorkflows` uses a placement principle that contradicts the one `entities/workflow.ts` documents, and the new principle does not cover two workflows.** `packages/domain/src/entities/workflow.ts:126-137` says "Placement follows each workflow's own writes" (Design ends at `approve`, which writes `State: Approved`). The plan says "a lifecycle workflow belongs to the phase that holds the state it moves a plan out of". `dispatch` and `implement` move a plan out of no state (`workflow.ts:133-134`: "write no phase"), so the plan's rule gives no answer for them, and the equality test against `PHASE_WORKFLOWS` (`workflow.ts:143-149`) then passes only through an unstated special case. Also, a custom map can put `plan:draft` and `plan:design` into two phases; then `approve` moves a plan out of two phases. Change the rule to "the phase that holds the state the workflow acts on: `approve` on draft and design, `dispatch`, `implement` and `deliver` on approved, `release` on delivered", say which phase wins when the states of one workflow sit in two phases, and say that this text replaces the doc at `workflow.ts:126-137`.

4. **Unresolved. The prose slice risks merging plan states and board phases, which MANIFESTO and CLAUDE.md keep apart.** `MANIFESTO.md:101` says "Plot's phases (below) are **states of a plan**", and its table (`:104-109`) already sets four *activities* across them: Discovery "before Draft", Design "Draft → Approved", Development "Approved → Delivered", **Endgame** "Delivered → Released". CLAUDE.md *Phase Guardrails* (`CLAUDE.md:205-209`) and MANIFESTO *Lifecycle* (`:148`) are about plan states and the guardrails on them. D2 keeps the states. So the correct edit to `:148`, CLAUDE.md *Phase Guardrails* and the `skills/plot/SKILL.md` *Plan Phases* table (`:170-182`) is to add `Design` as a plan state (written by `/plot-idea` or *Needs design*), not to replace those states with the declared phases. The activity table is where the declared phases go, and there "Endgame" becomes "Testing" (D1) and Released is added. `skills/plot/SKILL.md:182` ("Individual plans don't track a 'Testing' phase") contradicts D1 and must change. State in the slice which text changes in which way, and name the term split once: *state* is the `State:` word, *phase* is a declared column. The domain already uses `phase` for the state (`rules/phase.ts:118` `PlanReadings.phase`, "The phase the plan file states"), so `phaseOfPlan(map, readings)` reads `readings.phase` as a state. Per CLAUDE.md *The design spec's terminology is binding*, the plan should say how the new code names the two.

5. **Unresolved. CLAUDE.md sections that the new controller changes are not in the prose slice.** *Needs design* adds a tenth controller action with a bundle and an endpoint. CLAUDE.md *The Master Agent Uses The Controllers* lists "Nine actions exist as controller endpoints today" and names each bundle. CLAUDE.md also says the state gate admits a write only when "`plot-approve.sh`, `plot-deliver.sh` or `plot-sprint-state.sh` made the write". `owningCommand`'s fallback text names "the plan lifecycle is Draft > Approved > Delivered > Released" (`rules/state-transition.ts:102`). Add these to the prose slice or to the *Needs design* slice. Then `./scripts/check-agents-md.sh --write` regenerates `AGENTS.md`.

6. **Wrong claim, minor.** "`owningCommand` names the action for `design`, so the state gate admits the write when the receipt matches." `owningCommand` (`rules/state-transition.ts:93-104`) only builds the refusal text. The gate admits a transition when `receipts.spend(path, transition.after)` succeeds (`packages/board/src/server/entry/gate.ts:248-253`). The receipt admits the write; `owningCommand` only names the command in the refusal. Reword the sentence.

7. **Wrong claim, carried from the story.** The story's *Why Now* says `storyPhase` "spreads stories over all five columns, so the Plans tab mixes two subjects". `storyPhase` (`rules/phase.ts:72`) has no production caller: a grep finds it only in `packages/domain/test/phase.test.ts` and `test/workflow.test.ts`. Say that `phaseOfStory` has no caller until `the-board-has-three-tabs` or `tickets-and-stories-have-lanes` uses it, or drop it from this plan.

8. **Gap, transitional.** After the second slice the board draws one column per declared phase. With the default map the Discovery column of today's Plans tab is then empty, because Draft plans move to Design and stories are not cards. `planningColumns` in `the-board-has-three-tabs` removes it later. The plan should say that the empty column is expected between the two plans, or draw only phases that hold plan states from the start.

9. **Gap.** The auto-bump reads "the phase that holds `plan:delivered`". A custom map may hold no `plan:delivered`; today's code asserts non-null (`board.ts:2115`, `toBoardPhase('delivered')!`) and would drop the card (`if (!phase) continue`). State that a deliverable plan stays in its state's phase when no phase holds `plan:delivered`.

10. **Gap, minor.** The plan says "the wire field typed `z.enum(BOARD_PHASES)`". There are three: `packages/board/src/contract/schema.ts:425`, `:736` and `:2486` (the row phase, nullable). `Board.tsx:217-219` and `Swimlanes.tsx:161-163` index `PHASE_LEADERSHIP[phase]` with no guard, so a declared name outside the five throws there; the plan's "no leadership badge" needs that guard named.

11. **Vacuous check.** "A grep for `BOARD_PHASES`, `toBoardPhase` and `storyPhase` under `packages/fleet/src` returns zero matches after the first slice" is already true today (my grep returned zero). It proves nothing about D12. The phase reader that carries the fleet's name is `packages/board/src/server/fleet.ts:5463` (`rowPhase`). Either drop the check or point it at the true risk.
