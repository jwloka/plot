## Findings

1. **high: the fold's row projection is missing from the assignee slice, so under a fleet `assignees` never reaches the index.** On the spike, the fold turns each `Issue` into an index row through `rowOf` (`packages/fleet/src/shared/issue-refresh.ts:46-52`, `rows: result.value.map(rowOf)` at `:112`), which copies `number`, `title`, `url`, `createdAt`, `status` and `statusCategory` and nothing else. The slice `feature/an-issue-names-its-assignee` lists `issueOf`, `IssueIndexSchema`, "the board's index-row projection", `refreshIssues`' projection and `IssueRowSchema`, but not `rowOf`. If `rowOf` is not extended, `issueOf` reads `assignees` and the fold drops it. The board's read then decodes the absent key as `[]`, and `waitingTickets` hides every ticket of a matched GitHub reader and counts it as not theirs. The Acceptance cannot catch this: `tracker-shell.test.ts` tests `issueOf`, and `unplanned-issues.test.ts` tests the board's reads; nothing tests the fleet's write. Under a fleet is the common case on this estate (`readIssuesFromStore` replaces `refreshIssues` whenever `fleetOwnsPrs` answers true, spike `fleet.ts` diff at the old `:1687`). I checked this with `git show origin/feature/the-fleet-indexes-issues:packages/fleet/src/shared/issue-refresh.ts`.
2. **medium: the spike's index schema forbids the plan's decode rule, and its `.strict()` rows break the "no upgrade shows *no issue index*" claim.** The spike's `IssueIndexRowSchema` is `.strict()` and its doc says "**NO `.default()` ANYWHERE**" (spike `packages/domain/src/entities/issue-index.ts:17-36`). The plan says `IssueIndexSchema` "decodes an absent `assignees` as `[]`". That needs either a `.default([])`, which the spike's contract refuses, or an `.optional()` field that each reader maps to `[]`, which the plan does not say. In the other direction, `.strict()` makes a reader built before the slice refuse a row that carries `assignees`; `decodeIssueIndex` then answers `null` and `readIssuesFromStore` shows *the fleet has left no issue index to read*. A fleetd restarted on the new bundle while the board process still runs the old one hits this. So the plan's sentence "no upgrade shows *the fleet has left no issue index to read*" is true only when the board and fleetd restart together. The spike is still open, so its contract may change, but the plan judges against it.
3. **medium: `ticketSourceOf` inherits the board's `?? 'github'` default and can read a Bitbucket repository as GitHub.** `refreshIssues` passes `gitHost: entry.backend ?? 'github'` (`packages/board/src/server/fleet.ts:1482`), and `entry.backend` starts `null` (`:2037`) until `resolveBackend` answers. For `issueSource` the default is harmless, because a repository with no `Tracker` key answers `git-host` whatever the backend. For `ticketSourceOf` it is not: a Bitbucket repository read before the backend resolves gets source `github`, and every ticket (all `assignees: []`) is hidden and counted, which is the D22 failure the source field exists to prevent. The plan should say that `ticketSourceOf` takes the resolved backend (`resolveBackend`, `:1633`), and that an unknown backend, or one outside `github`/`bitbucket`, reads as unmatched: every ticket and a notice.
4. **low: after the spike the board has two issue reads, and the plan names one.** The spike adds `readIssuesFromStore` beside `refreshIssues`; each applies the planned filter and then `ISSUE_LIMIT` (spike `fleet.ts`, the `.slice(0, ISSUE_LIMIT)` in `readIssuesFromStore`). *Waiting on you is decided on the server* and the slice say "the board's issue read". `waitingTickets` and `FleetShape.waiting` must be set on both, or the fleet path sends `waiting: null` and the client falls back to `issues`. The Acceptance line in `unplanned-issues.test.ts` should name both reads.
5. **low: `identity` and `people` are module-private.** The plan says the read builds the `Reader` from `server-info.ts:178` and `:205-216`. Both are `const`, not exported (`server-info.ts:178`, `:206`), and live beside a 60 s identity TTL. The slice must export them or move them, which is cheap, but the plan should say so, so that a worker does not write a second identity read in `fleet.ts`.
