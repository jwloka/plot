# Cost lens, round 3: tickets-and-stories-have-lanes

Position: amend

The round-2 cost defects are answered in design. The issue fold has its own gate, the pacing formula is right, and the Bitbucket price matches the table's own comment. Four points still do not hold against the code: the "today" spend figure ignores the cadence stretch that the code applies today, the subtraction has no named input and no named site, the toggle read under a fleet has no gate to read, and the shell-line arithmetic does not balance under the gate's own count.

## Findings

1. **Must change: the "120 → 90" figure is the unstretched count, and the real spend rises.** The plan says GitHub spends 60 (PR) + 60 (board `issue-list`) = 120 requests an hour today and 90 after (plan `:70`). Today the cadence does not leave the fleetd PR pass at 60 s. Under a fleet the board calls `issue-list` every 60 s (`readPrsFromStore` stamps `PR_REFRESH_MS` unstretched, `packages/board/src/server/fleet.ts:1648`; call at `:1688`, `:1490`). The `gh` wrapper records that call (`skills/plot/scripts/plot-host.sh:3382-3388`). `spend-rate` sums every bucket of the git-host connector (`plot-host.sh:5236-5240`). fleetd reads it (`packages/fleet/src/shared/pr-refresh.ts:1341`), and `othersPerHour` counts the 60 a hour as another spender (`packages/domain/src/rules/cadence.ts:97-101`). Others (60) reach the share (60), so `targetStretch` answers `MAX_CADENCE_STRETCH` (`cadence.ts:140`, `:32`). A replay of `cadenceStretch` over 400 steps settles the fleetd PR pass at 480 s: 7.5 PR + 60 issue = **67.5 requests an hour today**, not 120. After the plan, the subtraction returns the PR pass to 60 s: 60 + 30 = **90**. So on a quiet GitHub account with a fleet, spend rises by about 22 an hour, PR freshness improves from 480 s to 60 s, and ticket freshness falls from 60 s to 480 s. Without a fleet, today's board settles at a stretch of 2 (PR and `issue-list` on one gate, `fleet.ts:1688-1703`): 30 + 30 = 60 an hour, and after the plan 60 + 30 = 90. Bitbucket today is 105 unstretched (3 real `pr-list` requests every 240 s = 45, plus 60), not 120. fleetd also starts a standing 30 an hour on every repository whether a board is open or not; today no issue is read without a board. Change: state the stretched figures for both modes and both hosts, and name the trade as "PR freshness for ticket freshness, at about +22 to +30 requests an hour", not as a saving.

2. **Must change: the subtraction has no named input, sits at the wrong line, and must skip a Jira source.** The plan puts the subtraction "from the observed rate it reads at `pr-refresh.ts:1341`" (plan `:70`). That same `rate` feeds the banner `entry.prSpendPerHour` (`pr-refresh.ts:1345`) and the limit reading (`:1352-1356`), so a subtraction there makes the banner understate the account's spend. The cadence reads the rate only in `scheduleNextPr` (`pr-refresh.ts:1022-1032`, called at `:1619`, `:1691`, `:1738`), which passes it to `prRefreshMsFor` and `prNextDueAt`; the subtraction belongs there, on a copy. The plan also says `PrWorld` does not change (plan `:66`), yet `refreshPrs(world, entry)` needs the fold's pages and interval: the plan must name the `PrState` field that the issue pass writes and the PR pass reads (both share `prState` at `packages/fleet/src/server/entry/registryd-main.ts:2013-2020`). The derived spend `pages × 3 600 000 / issueIntervalMs(pages)` is the constant 30 for every `pages ≥ 1` (computed below), so the field can be the constant or the source. For a Jira source the fold spends Jira, and `spend-rate` filters by the git-host connector (`plot-host.sh:5236`; `budget_record_jira` writes connector `jira`, `:2688-2691`), so subtracting 30 there under-counts others and under-stretches the PR pass. The no-fleet board runs the same `refreshPrs` (`fleet.ts:75`, `:1663-1671`) and needs the same subtraction from its own `issueNextAt` state. Change: subtract in `scheduleNextPr`, name the field, subtract only where the issue source is `git-host`, and say the board's no-fleet path subtracts too.

3. **Must change: under a fleet the toggle endpoint has no issue gate to read, and its read is not priced.** The plan says `GET /api/issues/closed` keeps its answer "for the issue gate's current interval" and asks nothing "while the issue gate's backoff holds" (plan `:77`; Acceptance `:178`). Under a fleet the issue gate and the shared backoff live in fleetd's memory (`registryd-main.ts:2013`), and the plan's `issues.json` holds `answer`, `failedAt` and rows (plan `:67`) but no interval, no next time and no backoff end. The board can read the PR error from the bridge (`fleet.ts:1641-1642`), but no field carries the issue gate. The board is also the caller here, so a rate limit the toggle read meets has no backoff to set under a fleet. The read itself is up to 10 pages at the 1000 cap (`ceil(1000/100)`), once per interval: on a repository whose fold is 2 pages (240 s), that is up to 150 requests an hour outside the 30 cap, and fleetd's PR pass counts it as another spender and stretches. Change: write the gate's next time and backoff end into `issues.json` (or the bridge) for the board to read, and pace the toggle read by `issueIntervalMs` of its own page count.

4. **Must change: the named shell lines do not pay for the new arms.** `scripts/check-shell-lines.sh:41-46` counts non-comment, non-blank lines only. Gate-counted lines in the blocks the plan names: the `nobody` preamble `plot-host.sh:4642-4649` = 5 and `:4831-4835` = 5; the `gh` failure blocks `:4737-4745` = 5 and `:4863-4874` = 5 (of which `else`/`fi` stay); the Jira single page `:4686-4698` = 7. A helper `issue_source_or_exit` (about 4–7 lines) and 2 call lines save about 1–4 lines; a `gh` failure helper saves about 0–3; the comments the plan's dedupe also removes count for nothing. So the dedupes free about 1–7 lines. The first slice adds, at a sketch estimate, `--state`/`--since` parsing (about 3), the GitHub `--search` and per-100-row `budget_record_call` (about 3), the Bitbucket exit 4 (about 3), the Jira `Ticket prefixes` guard (about 3), the closed JQL and `resolutiondate`/`closedAt` projections (about 3), and a `nextPageToken` loop net of the 7 lines it replaces (about 3–8): about 18–23 lines. The gap is about 11–22 lines. The D20 slice names no lines at all (plan `:120`). Change: name lines that cover the estimate, or move the page loop and the JQL assembly into a bundle, and state the expected net count per slice.

5. **Open point: the shared backoff must not move the PR gate earlier, and the Jira inbox loses its 60 s freshness.** The issue pass sets `prNextAt` and `prNextIsBackoff` on a git-host rate limit (plan `:71`). When the PR pass is stretched, its ordinary `prNextAt` can lie later than `now + wait`; an assignment would advance the PR pass. Change: set `prNextAt = max(prNextAt, now + wait)`. On Jira after D20, *Waiting on you* refreshes on the whole pass's interval: 1000 open rows at 100 a page plus the inbox page is 11 pages, 22 minutes, and at 50 a page 21 pages, 42 minutes, against 60 s today. The Changelog's "one refresh per 2 minutes per 100 tickets" assumes 100 rows a page, and the plan names no Jira page size (`maxResults` default is 50, `plot-host.sh:4690`). Change: name the Jira page size and state the inbox freshness for a large project.

6. **Note: the pacing arithmetic is right.** `issueIntervalMs(p) = max(120 000, p × 120 000)` gives `p × 3 600 000 / interval = 30` for every `p ≥ 1`, and the interval after a pass is sized by that pass's own pages, so no hour can exceed 30 by this gate. On this repository `ceil(108/100) + ceil(154/100) = 4` pages, 480 s, 30 an hour; Acceptance `:174` (`issueIntervalMs(4) = 480 000`, `issueIntervalMs(1) = 120 000`) agrees. The cap is per fleetd and repository, not per account: the fold takes no part in the account division (`cadence.ts:153-161`), so two machines spend 60.

7. **Note: `PR_REQUESTS_PER_REFRESH` at `bitbucket: 3` matches the comment's `pr-list` price.** The header and the table say 3 for `pr-list --state all` and 1 for `issue-list` (`pr-refresh.ts:136-137`, `:155`, `:186-188`). fleetd's `refreshPrs` never calls `issue-list` (its only host calls are `spend-rate`, `:729`, and `pr-list`, `:1427`, `:1536`), so fleetd over-declares today, and 3 raises fleetd's unstretched Bitbucket PR spend from 45 to 60 an hour. The "4 → 3 because `bb issue list` leaves the PR refresh" reason holds for the board's no-fleet path (`fleet.ts:1696-1703`). The `github: 1` comment also names `runs` (`:183-185`); that call is the board's (`fleet.ts:1645`) and stays.

8. **Note: the index rules hold.** fleetd stays the one writer and a test asserts it (plan `:66`); a missing or mismatched file shows a sentence and asks nothing (plan `:73`, as `fleet.ts:1636`); open rows reach only a view (plan `:154`); a failed pass keeps rows and `at` moves only on an answer. The `source` field is a derived reading, not a bought answer, but it serves only as a guard against reading another source's rows, so *Answers, never verdicts* is not broken.

9. **Note: the port doc has a fourth budget sentence.** `packages/domain/src/ports/tracker.ts:77-82` says each implementation "owns its OWN budget"; `trackerGitHost` spends the git host's budget by design (plan `:46`; `tracker-shell.ts:156-161` filters `limit()` by connector tag, so the mechanism works). The plan amends `:66-72`, `:103`, `:114` and not `:77-82`. Change: add `:77-82` to the slice-1 doc edit.

10. **Note: the D23 inbox read stays within the cap.** `pages` counts every request of the pass (plan `:70`), so the inbox page adds to the interval and not to the hourly spend: a Jira pass of p pages still spends 30 an hour. It costs freshness (finding 5), not budget.

## Ready to approve?

No. The mechanisms are sound in shape, and the 30-an-hour gate is correct. Findings 1–4 each need one or two sentences: the true before/after figures, the subtraction's field, site and source condition, the gate reading for the toggle under a fleet, and shell lines that balance.
