# Estate lens: the-fleet-verifies-what-it-delivered

Position: amend

The estate already holds most of what this plan needs: a delivery panel with a supported/refuted vocabulary, a committed record directory for it, an agent-launch route that runs a panel, a release checklist and a typed delivery commit path. The plan reuses the vocabulary and the commit path. It does not reuse the second commitment line, the record directory convention, or the agent-launch shape, and its per-claim record cannot come out of the panel gate as the gate is built. Nothing here contradicts D11; the gaps are in how the slices reach the existing code.

## 2. Buildability

- **Slice 2 (`the-fleet-verifies-a-delivered-plan`) does not name how a process runs a panel.** "`plot-fleetd` runs `/plot-panel`" is not buildable as written: `/plot-panel` is a skill, and the estate already says "no script can run a panel" (`packages/board/src/server/interrogate.ts:27`). The existing shape is `POST /api/interrogate`: a configured `Interrogate command` started through the `agentRun` port with a prompt, a slug-keyed state file, Draft-only (`interrogate.ts:11-24`, `:69-80` `not-a-draft`). The sibling `the-fleet-writes-the-design` names its command key (`Idea command`) and its launch site (`packages/fleet/src/shared/implement-run.ts:29`) at its `:43` and `:54`. This plan names neither a command key nor a launch site, nor whether it reuses `interrogate.ts`'s state file or the fleet's state.
- **Slice 2 supplies no lenses.** `/plot-panel` takes four parameters and refuses unattended when one is missing (`skills/plot-panel/SKILL.md:58-67`, `:104`). The plan says "one juror per lens" and names none. Step 5's lenses are Deliverable, Behaviour and Changelog (`skills/plot-deliver/SKILL.md:251-255`); the plan should adopt them by reference or name its own.
- **Slice 2 drops the Evidence gate.** Step 5 gates two lines, `Position: supported|refuted` and `Evidence: executed|read`, with two `check` calls (`skills/plot-deliver/SKILL.md:266-320`). It argues why: `readJuror` discards everything after the first word (`panel.ts:149-153`), so "ran X" on the Position line is ungated prose. The plan names only `supported,refuted` and then asks in prose that "a juror must run what a claim says where it can, as step 5 asks". That is the rule step 5 replaced with a gate. An unattended fleet run is where the gate matters most.
- **Slice 1's per-claim record cannot come from the gate as built.** `readJuror` reads one position per juror file and refuses a file that names two different positions ("claims both", `panel.ts:162-165`). A juror that finds claim 2 supported and claim 5 refuted cannot commit both under one `Position` label. So the record's `supported — <claim>` / `refuted — <claim>` lines would be moderator prose, not gated output, and `Verified: … 5 supported, 1 refuted` would count ungated text. The mechanism already allows a fix with no domain change: one `Commitment` label per claim (for example `Claim-1: supported`), each checked by its own `plot-panel.mjs check` call, exactly as step 5 adds `Evidence` (`skills/plot-deliver/SKILL.md:304-306`). The plan must choose this or say how per-claim positions are derived.
- **The panel's files need a name prefix.** `moderationPath` is fixed at `.plot/panels/<slug>/panel.md` (`panel.ts:58`), which the Draft rounds already use. The delivery panel avoids the clash by convention with a `deliver-` prefix (see the directory above). The fleet run needs its own prefix (for example `verify-`), or it overwrites the Draft moderation in a tracked directory.
- **The commit path exists but has no section write.** The deliver workflow emits typed writes: `plan-phase`, `plan-record`, `index-move`, `sprint-annotation`, `commit`, `push` onto `plot/deliver-<slug>` then `plot-push-main.sh` (bundle `skills/plot/scripts/board/plot-deliver.mjs`, the `Mm` deliver decision and the `plot-push-main.sh` call). A `Verified:` line fits `plan-record`. A `## Verification` section is a new write kind; slice 2 should name it.
- **Slice 4's file is read by code the plan does not name.** The board's Testing badge reads the newest file matching `/-checklist\.md$/` by lexical sort (`packages/board/src/server/board.ts:417-429`). `next-checklist.md` matches the pattern and sorts before every `v…` file, so the badge never shows it. (The sort is already wrong today: `v2.9.0` sorts after `v2.19.0`.) The plan's board-impact note says "The release checklist gains a fleet-written draft" and does not say whether the badge should count the draft.
- **Slice 4 changes the checklist's grain.** `/plot-release rc` writes one item per plan, from its Changelog (`skills/plot-release/SKILL.md:219`, `:234-235`). The plan says "in the shape `/plot-release rc` writes" and then writes one item per supported claim. That is a different shape; the plan should say so and change `:219-235` in the same slice.

## 3. Agreement with siblings, spec and repo decisions

- Spec §6 (`DESIGN-phases.md`, *In Testing*) and D11 agree with the plan's intent. The spec says jurors use "the vocabulary `/plot-deliver` step 5 already uses"; that vocabulary is two lines, not one.
- D11 ("each Delivered plan") does not decide whether a plan already panelled at `/plot-deliver` is panelled again. The plan decides it silently by ignoring the `deliver-*` record. Either answer is within D11; the plan must state one. A cheap answer the estate supports: `verificationOf` reads a committed `deliver-panel.md` as a verification, and the fleet runs only for plans without one, which is exactly the auto-delivered set the gap at `auto-deliver.ts:311-315` names.
- `the-board-has-three-tabs` lists *Waiting on you*'s content (`:27`, `:43`) and does not mention a failed verification row. This plan says a failed run shows there. The sibling `the-fleet-writes-the-design` makes the same claim for spec runs (`:43`, `:47`). One of the two plans must own the row and its domain property, per CLAUDE.md's *Every rendered state is a domain property*.
- Opening an issue: D11 decides the write, and the plan states it as the port's second write. That is consistent with CLAUDE.md's connector rule (tracker is a connector; `trackerNone` answers `unaskable`, `packages/domain/src/adapters/tracker/tracker-none.ts`).

## 4. The single most important change

Make the panel the plan runs the one that already exists: state the launch (command key and site, after `interrogate.ts`), the lenses (step 5's three, by reference), the commitment (step 5's `Position` and `Evidence` lines, plus one gated label per claim so the per-claim record is gate output), the file prefix under `.plot/panels/<slug>/`, and what a committed `deliver-panel.md` means for `verificationOf`.
