# Cost juror, round 2: the-board-has-three-tabs

Position: amend

The revision applies all five of my round-1 amendments and all four optional points, and the new `### Cost` section is true where I measured it: zero new host or tracker calls, 47 test files that keep `?tab=agents`, 63 browser test files, a docs grep of 24 files of which 17 change, and no net shell lines. Two costs remain unbounded, and both sit in *Waiting on you*. First, the hidden count runs in the client over at most 50 rows (`ISSUE_LIMIT`), so on this repository it says 50 or fewer where the plan says 127, and the cap hides the rest with no word, which is what D22 forbids. After `feature/the-lanes-read-the-whole-jira-project`, which waits on this plan, the same cap drops a matched Jira reader's own tickets beyond the 50 newest of the project; the plan leaves that as an Open Point while its own wave order ships it. Second, a Jira reader whose email Jira hides is matched by `accountId`, so a person who writes `jira:<email>` in `People` sees their own tickets hidden and counted as "not assigned to you". A smaller design fixes the first: apply `ticketOwnership` on the server before the cap, where the reader is already known, and send the count with the rows. Measured on `main` at `553c4777b`, 2026-10-13.

## Findings

1. **High — the hidden count counts within the 50-row cap, so the Design's figure for this repository is false and the cap hides tickets silently.** `packages/board/src/server/fleet.ts:192` sets `ISSUE_LIMIT = 50`, and `:1492` asks `issue-list --limit 50`; `:1577-1579` then drops planned tickets. So `/api/fleet` carries at most 50 ticket rows today. `gh issue list -R plot-pm/plot --state open --limit 300 --json assignees` answers 127 open issues and 0 assigned. The plan's *Waiting on you* says "On this repository that reader sees 0 tickets and the count 127, so nothing is hidden silently (D22)", and *The inbox cap* says `hidden` "counts within the 50". Both cannot hold: the reader sees a count of at most 50, and at least 77 tickets are hidden with no word. The Acceptance case "127 tickets, 0 assigned, `hidden` 127" passes as a unit test over an input the client never receives, so it proves the rule and not the Changelog line "says how many tickets it hides". Checked by reading `fleet.ts:186-194`, `:1490-1495`, `:1570-1590` and the live issue count.
2. **High — after the lanes plan's project-wide Jira read, the cap drops a matched Jira reader's own tickets, and the plan's own wave order ships that regression.** `tickets-and-stories-have-lanes.md:110` keeps `/api/fleet` at "the rows that pass the inbox filter, newest first, capped at `ISSUE_LIMIT` (50)", and `:119` says a matched reader's inbox is "the project-wide rows filtered by `Issue.assignee`". That plan's `feature/the-lanes-read-the-whole-jira-project` waits on this plan's `feature/the-delivery-tab-filters-by-sprint-and-owner` (`:119`, and this plan's *The assignee filter comes before a project-wide Jira read*). So once both land, a reader who adds `jira:<account>` to `People` on a 1000-ticket project sees only their tickets among the 50 newest of the project, where today's `assignee = currentUser()` read (`plot-host.sh:4684`) gives them 50 of their own. The plan names this as an unchecked Open Point with a recommended answer, but nothing holds the lanes slice until the answer ships. The recommended answer is small: `readerFrom` (`mine-filter.ts:119`) reads `ServerInfo.hostUser`, `gitEmail` and `people`, which the server holds, so the server can order or filter by `ticketOwnership` before it applies the cap and send the total it left out. That also fixes finding 1, and it shrinks the payload for a matched reader with no assigned ticket.
3. **Medium — a Jira reader whose email Jira hides sees their own tickets hidden, and the plan names no way for a person to find the right spelling.** The assignee slice projects `emailAddress`, or `accountId` where Jira hides the email (*The assignee*), and Acceptance tests that `accountId` output. The `ticket` arm answers `unknown` when no `jira:` spelling names the value, and the inbox default hides and counts `unknown` (*An unassigned ticket*, last sentence). The sibling's Changelog shows the spelling as an email (`tickets-and-stories-have-lanes.md:23`, `jira:jan.wloka@quatico.com`). So a reader whose instance hides emails writes the email, becomes "matched", and sees their own tickets counted as "not assigned to you" — a regression from today, where every row of the Jira read is theirs. The maintenance cost to the person (find the `accountId` and write it into `People`) is unnamed, and the sentence they see does not name the value it could not match.
4. **Low — the index-version window is named once but the field could avoid it.** The plan states up to 22 minutes of *the fleet has left no issue index to read* after the raise (`tickets-and-stories-have-lanes.md:118`). `origin/feature/the-fleet-indexes-issues` holds only its claim commit `930cb07d7` and no work (`git log origin/main..origin/feature/the-fleet-indexes-issues`). If the spike's first `IssueIndexSchema` carries `assignees`, defaulted to `[]` by `issueOf`, the version never needs a raise for this field. The plan declines the coordination because the spike is claimed; a claim with no commits is cheap to brief.
5. **Low — the seven browser tests are counted but not placed.** Acceptance names one browser test each for the tab redirect, *Show released*, the active-sprint button and the verification row, two for *Waiting on you*, and one case in `mine-filter.browser.test.ts`. It does not say which go into existing files and which start new ones. Most board browser tests start a full board server, and the `validate` job took 18 m 39 s on the last green `main` run (`gh run view`, 2026-10-13 08:57-09:16). Adding cases to `agents-tab.browser.test.ts` and `mine-filter.browser.test.ts` costs less than six new files.
6. **Low — six slices for six fleet agents; the active-sprint slice is small.** `feature/the-active-sprint-button-selects-every-active-sprint` is one helper beside `sanitizeSelection`, one button, one unit test and one browser test. It was split out on the deliverable juror's request (round 1, A3), so I accept it; it can still fold into the rename slice, which already changes the Delivery tab, and save one agent and one review.
