The *Working* section (`sections.ts:27`, `AgentList.tsx:1082`) has no plan-level row today. So the slice-4 agent must design a new *Working* path and map the `specRow` shape onto `VerificationRowView`, and the line names neither. The phrase "the stubbed-test counts" in the slice line also has no referent in the plan. Checked: read both plans and grepped `AgentList.tsx`.
2. **medium — The removal waits on a Draft sibling for no reason.** `sliceVerdicts` makes each heading wait on every heading before it (`packages/domain/src/rules/eligible.ts`, the fold after `:136`). *The button goes* (`:135`) comes after *The spec rows* (`:131`), which waits on `feature/waiting-on-you-shows-a-failed-verification`. The removal does not use the spec rows, and slice 3 already moves the log helpers it needs. So Changelog item 8 is blocked on the approval and two merges of another plan. Checked: the slice order, the sibling's state and its slice order.
3. **medium — The declined check can decline a restarted plan again.** The check reads `host.prState('idea/<slug>-spec')` (plan `:64`). By branch, that answers one PR: the newest (`plot-host.sh:3557`, `pulls?head=…&state=all&per_page=1`; `gh pr view <branch>` on the GraphQL path). After a person restarts a declined plan, the restart mark passes `declined` once (`:52`, `:100`), and the start consumes it. If that run then fails before `prCreate` (`no-commit`, `spec-empty`, `no-branch`), the ref is deleted, and the retry pass reads the old closed PR as the newest. The fleet then writes `declined` again, so the two retries of Changelog item 5 do not happen and the plan reads declined, not failed. The plan also does not say whether fleetd writes the `declined` mark before or after it reads the restart mark. No Acceptance item (`:146`, `:147`) covers a restart of a declined plan followed by a failed run.

On Bitbucket, `--draft` "depends on the bb CLI version" (`plot-host.sh:435`), and the plan does not say what a refused draft does.
