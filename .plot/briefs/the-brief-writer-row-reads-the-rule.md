### The decisions the plan settles — do not re-derive them

- **The domain rule and its row-level consumer already exist; this wave's job is closing four specific gaps, not building `briefWriterNote` from scratch.** The plan's own `<!-- builds: -->` annotation names `briefWriterNote` as new, but no such function is missing — `briefNote` already exists and already switches on the right precedence (`writing` > `failed` > `asked`, per its own TSDoc at `row-identity.ts:296-301`). Extend `briefNote`'s `writing` case to carry an age; do not introduce a second note-building function alongside it.
- **Rename the field, not the helper.** `briefWriting` the FIELD becomes `briefWriter`; `briefWriting` the FUNCTION (the boolean reader) stays `briefWriting`. The plan's finding is about the field/function collision, and the fix that removes the collision is renaming the one that is a noun pretending to be a state (the field) rather than the one that is already a verb phrase reading naturally (the function).
- **The start-time fix (#1437 L4) needs a format decision the plan leaves open** (see the plan's own Open Questions: "is the process start time readable on both macOS and Linux without a shell call per row, or does the fix belong to a later slice?"). `ps -o lstart= -p <pid>` works on both macOS and Linux but is a shell call per row — exactly what the open question flags as a possible blocker. The cheaper fix: record the start time in the state file alongside the pid when `startRun` writes `running ${process.pid}` (e.g. `running ${process.pid} ${Date.now()}`), compared against on the next read with no process spawn. This requires no new I/O per read and no platform-specific parsing — prefer it over `ps`/`lstart` unless there's a reason the state file format can't carry a third token. If you find one, say so in the PR body and either defer L4 to a later slice (the plan permits this) or justify the per-row shell call's cost given `CLAUDE.md`'s general caution about spawns outside adapters.
- **Do not re-test `briefWriterState` itself.** `packages/domain/test/brief-writer.test.ts` (64 lines) already covers the rule's four-state decision table. This wave's tests are for: the schema-parse gap (M1), the rename's ripple (L1), the tie between the two unions (L2), and the age-carrying note plus the start-time comparison (M3, L4) — new behavior, not re-coverage of what `#1417` already tested.
- **Style:** `packages/domain/src/rules/brief-writer.ts` is under `packages/domain/src/`, so `CLAUDE.md`'s arrow-function rule binds it fully — `briefWriterState` is already an arrow; keep any addition (e.g. an age-computing helper) an arrow too. `row-identity.ts` and `fleet.ts` are board-package files outside that scope, but any NEW helper you write in them is still an arrow per the repo-wide rule for new code; only pass-through edits to existing declarations are exempt.
- **No browser test is added.** The plan is explicit: `agents-tab.browser.test.ts` changes its assertions for the renamed field and the aged note, but adds no `it(`, so `EXPECTED_TESTS` in `stubbed-tests-start-no-board.test.ts` stays unchanged. If you find yourself adding a new `it(` there, stop and check whether the plan's assumption still holds — it may mean the field rename touches more assertions than one test block and you've split it, which is fine, but don't let a split count as new coverage requiring a bump.

### Done when

The plan's own list is the specification — a domain rule decides the brief note and its age (the rule already exists; the age-carrying extension is the remaining work), the field becomes `briefWriter` and derives from the domain's union (rename plus a tie test, since "derives from" has no existing mechanism and a test is the cheapest proof of agreement), a schema test pins its default (the M1 gap), the TSDoc states the interface (already true — verify it stays true after the rename), and a run file records its start time (L4).

The assertions that exist because a naive implementation would pass without them:

- **The schema-parse test (M1) must omit the field from the input object, not merely assert the default inside a built row.** `AgentRowSchema.parse({ ...fullRow, briefWriter: undefined })` — following `brief-gap.test.ts:161`'s exact shape — proves the schema's own default fires on a payload missing the key. A test that reads `rowFor(...)`'s output and checks `briefWriter === 'none'` only proves the fleet-building pipeline happens to produce `'none'` today, which is what the existing (insufficient) test already does.
- **The age-carrying `writing` note must be tested with a NON-ZERO age that a fixed string would fail to show.** A test asserting the note contains the word "writing" or matches the OLD fixed string passes whether or not the age was wired in. Assert the note's text contains a rendered duration (reusing `askedLabel`'s format, e.g. `"42s"` or `"3m"`) computed from a specific elapsed time your fixture controls, the same way `briefAskedNote`'s own test (wherever it lives) must already prove its age renders correctly.
- **The rename's test sweep must catch every `row.briefWriting` reference, not just the ones in `brief-failed.test.ts`.** `grep -rn 'briefWriting' packages/board` after the rename should find only the function name and its doc comments — any surviving `.briefWriting` field access (as opposed to a `briefWriting(row)` call) is a missed rename, and TypeScript will not catch a stale string literal inside a test fixture object the same way it catches a typed field access.
- **The tie test (L2) must fail if either union drops or adds a value independently.** Asserting `BriefWriterStateSchema.options.length === 4` passes even if both sides drifted to the same WRONG four values by coincidence. Derive the expected list from the domain's `BriefWriterState` type at the type level (a `satisfies` check or an exhaustive switch that fails to compile if a value is missing) rather than hand-copying the four strings a second time into the test.
- **The start-time test (L4) must prove a REUSED pid is caught, not just that a timestamp is stored.** Write a state file with a pid and an old start time, then simulate that pid being alive (the existing `livePid`/`deadPid` fixtures in `brief-failed.test.ts` show the pattern) with a start time that does not match what's recorded — assert the mismatch reads as `failed`, not `writing`. A test that only checks the timestamp round-trips through a write/read cycle proves nothing about the defect it's meant to close.
