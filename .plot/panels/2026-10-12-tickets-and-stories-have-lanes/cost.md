## Findings

1. **The new port operation has no path on most repositories, including this one.** Must change before approval. `issueSource` (`rules/issue-source.ts`) answers `git-host` for a repository that declares no `Tracker`, and `trackerFor('')` (`tracker-resolve.ts:35-44`) answers `trackerNone`. Plot's own `## Plot Config` declares no `Tracker`, so `issueListClosed` on `trackerNone` answers `unaskable` here and on every Bitbucket repository that tracks in Bitbucket issues (`TRACKER_LISTERS` lists only `jira` and `github-issues`, `tracker-listers.ts:14-17`). The plan (Design, *Closed issues on the port*) names two connectors and `trackerNone` and no git-host path. The plan must say who lists closed issues for the `git-host` source, and what Bitbucket's `bb issue list` (one fixed page, no `--limit`, no `createdAt`, `plot-host.sh:4740-4750`) costs or answers for closed states.

2. **The first full read on GitHub hits the search cap and records one call for many pages.** Must change before approval. The plan asks GitHub with a `closed:>=` search (Design, *Closed issues on the port*). GitHub's issue search returns at most 1000 results per query, so the first fold (`since` = the beginning) on a repository with more than 1000 closed issues is silently truncated, and the fold then writes a watermark over a hole. `gh issue list --state closed --limit N` paginates without that cap, at 100 rows per GraphQL page, but the `gh` wrapper records one call per process (`plot-host.sh:3382-3388`, `budget_record_call` once), so a 20 000-issue first read spends about 200 GraphQL requests and the ledger shows 1. The Layering Rule says a connector "records what a call spent"; this read under-declares by the page count. The plan must name the full-read call (search windows by date, or the paginated list), record a completeness flag as the PR index does (`entities/pr-index.ts:90-120`, `complete` "recorded, never inferred"), and record spend per page.

3. **The Jira read has no pagination and no scope.** Must change before approval. The Jira arm asks one page, `maxResults` default 50, with the comment "no nextPageToken loop is needed" because the inbox "is small by construction" (`plot-host.sh` issue-list Jira arm, the `max="${limit:-50}"` line). A `resolved >= <since>` read of "every closed ticket" is not small: it needs a `nextPageToken` loop at about 100 rows per call, each call recorded by `budget_record_jira` with basis `unknown` (`plot-host.sh:2688-2690`), so the connector cannot report its headroom while it spends it. The inbox JQL also scopes by `assignee = currentUser()` and `Ticket prefixes`, because an unscoped query "returned another customer's ticket to a reporter's board" (same arm, the `scope` comment). The plan writes `resolved >= <since>` with no scope. On a shared enterprise instance that is an instance-wide read of every resolved ticket: the largest cost in the plan and a leak of the class the scope clause was added to stop. The plan must state the closed JQL's scope (project and, to match the open lane, assignee or not) and its page loop.

4. **The plan drops the periodic full read that DESIGN-index requires, and with no bound that read is the expensive one.** Must change before approval. DESIGN-index.md:167 says "A periodic full read is required, not optional", because a delta cannot see a deletion, a transfer, or a back-dated field. The plan says "the shape `DESIGN-index.md` gives the PR index" and then gives only the first full read and deltas. Either the plan adds the daily full read and prices it over an unbounded closed set (finding 2 and 3 apply each day), or it states why issues are exempt. The delta also has no field to stand on: DESIGN-index.md:87 takes the watermark from "the newest `updatedAt` the host RETURNED, never the local clock", and the plan adds `closedAt` and `open` to `Issue` but no `updatedAt`, while the port operation filters by close date (`issueListClosed(since)`), not by update. The plan must say which field the watermark is.

5. **The board's own issue call stays, so the plan adds spend instead of moving it.** Must change before approval. Today the board asks `issue-list` every 60 s even when the fleet owns PRs (`fleet.ts:1686-1689`), and `PR_REQUESTS_PER_REFRESH` counts that call in the fleet's pacing (`pr-refresh.ts:185-197`, Bitbucket 4 = three listings plus the issue call). The fleet asks for no issues today, so the fold is a new caller with a new cadence. The plan does not say whether the board's 60 s call stops, what cadence the fold runs on, or how `PR_REQUESTS_PER_REFRESH` changes; DESIGN-index.md:197 says that number "must follow", and the file's own comment says under-declaring it is the failure it names. The plan must state the fold's cadence, the board's call it replaces, and the new per-refresh figure per backend.

6. **The miss path can repeat the full read on every refresh.** Must change before approval. "A missing, unparseable or other-version file makes the board ask the tracker directly" (Design, *The issue index*). With no fleet, or after a version bump, the board then re-reads every closed issue on each 60 s tick, because the board never writes the index. This is not hypothetical: CLAUDE.md, *A Decision Reads The Index*, records that the live PR store read `v: 1` against version 2, "so every read fell through to the host". The plan must bound the fallback: on a miss the board asks for the open list and the 14-day window only, and the released toggle reads "not available" until the fleet has written the index.

7. **Every closed issue rides the 4 s fleet payload.** Must change before approval. Issues travel in `buildFleet` (`fleet.ts:6705-6708`), which the client polls every 4 s per open tab (`App.tsx:32,283`, `FLEET_POLL_MS = 4_000`). The toggle is client state (`?released=1`), so as written the server ships every closed issue on every poll whether the toggle is on or not. At about 250 bytes per row, 20 000 closed issues are about 5 MB per poll, about 75 MB per minute per tab. The plan must say that the payload carries the 14-day window and that the full closed set is served only on request when the toggle is on, or put the closed set on the 30 s board payload with a measured size.

8. **The Open lane is computed from a truncated list.** Can be an Open Point, but the plan must name it. `ISSUE_LIMIT = 50` (`fleet.ts:190`) caps the open list, and its comment justifies the cap by "an inbox is only ever the top of the list". This repository has 108 open issues today, so 58 open tickets reach no lane, and `ticketLane`'s `namedByPlan` rule never sees a planned ticket past position 50. A lane view is not an inbox. Raising the cap costs pages on every refresh (finding 2 applies to the open list too); the plan must choose the cap or move the open list into the index as well.

9. **The unbounded index has no stated size, and the cheap bound already satisfies the default view.** Open Point 8 can stay open, but the plan must state the cost of its default. The default view needs only tickets closed in the last 14 days, which one bounded `closed:>=<now-14d>` read answers in one page on most repositories. Only the toggle needs "every closed ticket" (D7). `issueView` already sets the precedent that a read whose subject is a person's choice runs at "a call whose cadence is a human's" (`ports/tracker.ts:113-114`, `plot-host.sh:322-328`). A 14-day index plus an on-demand paginated read when the toggle turns on meets D7 with no unbounded file, no unbounded daily full read, and no unbounded payload. I recommend it as the plan default; the operator decides.

10. **The index file name can collide with the PR index.** Can be an Open Point. The PR index is `.plot/state/index/<connector>.json` under the git common dir (`pr-index-file.ts:17-31`), and the GitHub tracker connector tags itself `github` (`tracker-github.ts:18`). "An issue index under `.plot/state/`, with a per-connector watermark" does not name its path; a per-connector file in the same directory overwrites `github.json`. The plan should name the file, for example `.plot/state/index/issues-<connector>.json`.

11. **The shell ratchet charges the new arms.** Can be an Open Point. Each connector reads through `plot-host.sh` (`tracker-shell.ts:120-151`), so a closed-issue arm for GitHub, Jira and, per finding 1, Bitbucket adds shipped shell lines. `scripts/check-shell-lines.sh` (`ci.yml:765-767`) refuses a change that adds shell lines without removing an equal count. The first slice must name the lines it removes, or put the closed read in a TypeScript connector.

12. **Outside the cost lens, noted once.** Can be an Open Point for the domain lens. The GitHub arm derives `statusCategory` from the state it asks for: open is `To Do`, closed is `Done` (`plot-host.sh` issue-list GitHub arm, the `jq` projection). So a GitHub issue always has a category, the "no category" rows of `ticketLane` never fire on GitHub, and a planned open GitHub ticket reads Open, not In progress. DESIGN-phases.md:214 says GitHub has no category; the code says it does.
