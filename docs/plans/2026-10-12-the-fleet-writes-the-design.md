# The fleet writes the design

> For a plan that a person put in `State: Design` and whose spec is empty, the fleet commissions an agent to write the spec, and after a person approves a plan's spike, automatic dispatch starts it. Approval stays a person's act.

## Status

- **State:** Draft
- **Type:** feature
- **Story:** plot-works-in-five-phases
- **Review:** pr
- **Rounds:** 3
- **Impl:** own branches

## Changelog

- With auto-dispatch on, the fleet dispatches a Design plan's spike as soon as a person approves it, and only after its brief exists.
- With `Auto-design: true` and a `Design command` declared, the fleet writes the design spec of a plan in `State: Design` whose `## Spec` section is empty. An agent writes the spec in its own worktree and pushes `idea/<slug>-spec`; the fleet then opens a draft PR for that branch, and a person merges it or closes it.
- The fleet reaches only the Design plans it reads on `origin/<main>`: a `Review: in-session` or `ballot` plan, or a `Review: pr` plan after a person approves its spike (D34). A `Review: pr` Design plan whose plan PR is open, and one with no spike, get no fleet spec.
- The fleet starts one spec run per plan, across every machine: the run's branch on origin is its claim. After a person closes a spec PR, the fleet starts no new run for that plan until a person restarts it.
- A spec run that opens no PR fails. A failed spec run shows in *Waiting on you* with its reason, its log and a restart command, and a going one shows in *Working*. The fleet retries a failed run twice; after 3 failures of one plan it stops, and after 3 failures across plans it starts no spec run until one succeeds.
- `plot-design.mjs restart <slug>` starts a new run of that plan on the next pass, also while spec runs are halted, and the success of that run lifts the halt.
- This repository's `## Plot Config` declares `Design command` and `Auto-design: false`.
- The board's *Commission design* button, its row-menu entry and `/api/commission` are removed.

## Motivation

D10 in [the story](../stories/plot-works-in-five-phases/STORY-plot-works-in-five-phases.md) gives the fleet the mechanical part of design work. Measured on `main` at `8b0180d52`, 2026-10-13:

- *Commission design* is a board route (`packages/board/src/server/commission.ts`, 424 lines). A person clicks it on a Draft plan, and an agent started with the `Idea command` in the operator's checkout (`tree: opts.repoRoot`, `commission.ts:406`) is told to move the plan to Design and add an empty `## Spec` section, and not to write the spec (`commission.ts:135-205`). Its agent edits `State:` by hand, which the state gate refuses where the gate is installed, so the route does none of its job today.
- `the-phases-are-declared` (Delivered) gives the move to Design to a person: `/plot-idea` writes `State: Design` on yes (#1628), and *Needs design* moves a Draft plan (#1633). Both write a `Design:` record and the `## Spec` placeholder `SPEC_PLACEHOLDER` (`packages/domain/src/workflows/needs-design.ts:5`).
- Since #1634, `sliceVerdict` admits the approved spike of a Design plan and refuses its other slices (`packages/domain/src/rules/eligible.ts:127-134`). Automatic dispatch still skips every non-`approved` plan, at six places in `packages/domain/src/rules/auto-dispatch.ts`: `planAutoDispatch` (`:531`), `startableBranches` (`:582`), `skippedClaimedBranches` (`:617`), `firstBrieflessBranch` (`:656`), `skippedPlans` (`:733`) and `dispatchCandidates` (`:798`). The fleet builds `missingBriefs` from `dispatchCandidates` only (`packages/fleet/src/shared/auto-dispatch.ts:333-335`).
- The fleet already starts one non-slice agent per plan: the verify run of #1635. `packages/domain/src/rules/auto-verify.ts` holds the failure store, `verifyStart` with named refusals and `verificationRow` (`:321`); `packages/fleet/src/shared/auto-verify.ts` (593 lines) reads the `Verify command` and `Auto-verify` keys, bounds the run with `Worker bound` and starts it through `startBoardRun`. No board component renders `verificationRow` today; `the-board-has-three-tabs` builds that row (#1640).

## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §6, *In Design*.

**The person's decision.** The fleet writes a spec only for a plan that a person already put in Design. `State: Design` comes from `/plot-idea` (#1628) or *Needs design* (#1633), each with a `Design:` record that names who decided, and the state gate refuses a `State:` change by any other writer. The fleet moves no plan into Design (D3). The spec it writes is a proposal on a draft PR: a person merges it or closes it, and a person later approves the plan through the person arm. An operator opts in with `Auto-design: true`; the default is off.

**The reach (D34).** The fleet reads a Design plan's text at `origin/<main>` through `refs.showFile`, as `readVerifyCandidatesWith` does (`packages/fleet/src/shared/auto-verify.ts:293-330`). The pulse also carries plans that only a prefixed branch holds: the scan reads `origin/<main>` first, then each prefixed branch's tree for the plans the default branch does not carry (`skills/plot/scripts/plot-fleet-scan.sh:143-158`). So a `Review: pr` plan that *Needs design* moved on its open plan PR's head (`packages/domain/src/workflows/needs-design.ts:116-131`) is in the pulse with `phase: 'design'`, and `showFile` at `origin/<main>` fails for it. Such a plan goes into the reader's `unread` list, `designWork` answers `none`, the fleet records no failure and shows no row. Under D13 that plan reaches the default branch when a person approves its spike, and the fleet writes its spec from then on. A `Review: pr` Design plan with no spike never reaches the default branch in Design, because its approval merges the plan PR and writes `State: Approved` in one act (`packages/domain/src/workflows/approve.ts:337-358`); the fleet writes no spec for it. D34 accepts both limits and adds no reading of open plan PRs.

**The spike.** No new rule. The six `plan.phase !== 'approved'` filters in `rules/auto-dispatch.ts` admit a `design` plan too, and the scan's `wave.verdict` decides, as it does for an approved plan. `sliceVerdict` answers `eligible` for the approved spike only, so every other slice of a Design plan stays out. Because `dispatchCandidates` (`:798`) and `firstBrieflessBranch` (`:656`) admit it, a briefless spike enters `missingBriefs`, is reported `no-brief`, is offered to the `Brief command` and is not dispatched. `skippedPlans` (`:726-787`) admits a `design` plan only when it has an eligible slice, so a Design plan with no approved spike does not join the `no-eligible-wave` line that `packages/fleet/src/shared/auto-dispatch.ts:368-373` prints on every pulse. The two `hasEligible` reads in the fleet (`auto-dispatch.ts:243`, `:282`) admit a `design` plan the same way, so a spike that waits at the cap is named.

**What the fleet reads.** `specOf` moves from `packages/board/src/server/entry/needs-design.ts:146-163` into the domain beside `SPEC_PLACEHOLDER`, and the board entry imports it. Four rules in `packages/domain/src/rules/design-work.ts` use it:

- `specIsEmpty(text)`: true when `specOf(text)` is `''` or `SPEC_PLACEHOLDER`. A section that holds only a link to a `DESIGN-*.md` file counts as written.
- `designWork(readings: { state: string; text: string; specRef: ClaimAnswer })`: `write-spec` when `state` is `design`, `specIsEmpty(text)` and `specRef` is `absent`; otherwise `none`. `specRef` is `claimTip`'s answer (`rules/claim.ts:40`, type `ClaimAnswer` at `:15`) for `idea/<slug>-spec` on origin, so `unknown` answers `none`. The spike does not change the answer: a spec and a spike are two forms of design work (DESIGN-phases.md §4), and the spike dispatches through the verdict whatever the spec says.
- `specStart(input)`, beside `verifyStart`: refuses, in this order, `off`, `running` (a spec run or a verify run is going), `declined`, `host-unknown`, `halted`, `stopped`, `waiting`, `queue-unread`, `no-free-agent`, `starved` (without `Machine override`). A plan with a restart mark passes `declined`, `halted`, `stopped` and `waiting` once. Its input names its readings as `VerifyStartInput` does (`rules/auto-verify.ts:124-149`).
- `specRow(slug, designCommit, store, log, going, now)`, beside `verificationRow` (`rules/auto-verify.ts:321`): the *Working* row of a going run, the *Waiting on you* row of a plan whose failure record carries the current `Design:` commit, or `null`. The row names the reason, the log, the restart command, `stopped` and `fleetHalted`. The board renders it and decides nothing.

**What is shared with auto-verify.** The spec run imports every part of the verify run that is not about verification, and copies nothing that is a rule:

- `packages/domain/src/rules/fleet-run.ts` takes from `rules/auto-verify.ts` the store type (`VerifyStore`, `:27`, as `RunStore`), `VERIFY_HALT_AFTER` (`:21`), `recordVerifyFailure` (`:46`), `verifyRetryVerdict` (`:61`), `failuresSinceSuccess` (`:73`) and `verifyHalted` (`:84`), plus `slotRefusal`, the three last refusals of `verifyStart` (`:164-179`: `queue-unread`, `no-free-agent`, `starved`). `auto-verify.ts` re-exports them under their current names and `verifyStart` calls `slotRefusal`, so no verify caller changes.
- `packages/fleet/src/shared/fleet-run.ts` takes from `packages/fleet/src/shared/auto-verify.ts` the state file reader and writer (`readVerifyState` `:161`, `updateVerifyState` `:192`, over a path argument), `pidAlive` (`:207`), `verifyRunGoing` (`:225`, as `runGoing`), `boundSecondsOf` (`:393`) and the status line format of `verifyStatusLines` (`:584`).
- Each run keeps its own prompt, its own candidate reader (Delivered plans at the delivery commit against Design plans at `origin/<main>`) and its own settlement arms. These answer different questions, so they are not a duplicate of one rule, and no corpus pair is needed.

**The spec run.** `packages/fleet/src/shared/auto-design.ts`:

- Two `## Plot Config` keys. `Design command` names the runner; an absent key starts nothing. It is its own key under the one-capability-one-key rule (`packages/fleet/src/shared/implement-run.ts:22-33`): writing a spec is not the idea binding. `Auto-design` turns the run on for the literal `true` only, and defaults off. The slice adds both to this repository's `## Plot Config`, beside `Verify command` and `Auto-verify: false` (`CLAUDE.md:102-103`): `Design command` with the `Idea command`'s `claude -p --model opus` line, and `Auto-design: false`.
- The declined check. Before it claims, fleetd reads `host.prState('idea/<slug>-spec')` once (`packages/domain/src/ports/host.ts:161`). A closed or merged PR for that branch while the spec on `origin/<main>` is still empty means a person declined the spec: fleetd writes `declined[slug] = <Design: commit>` into the store, starts nothing, and reads the mark on every later pass with no host call. A host that cannot answer refuses as `host-unknown`.
- The claim. fleetd pushes `idea/<slug>-spec` to origin with one empty `plot: claim idea/<slug>-spec` commit (`CLAIM_SUBJECT_PREFIX`, `rules/empty-claim.ts:12`) through `Trees.addBranch`, `Trees.commit` and `Trees.push` (`packages/domain/src/ports/trees.ts:280`, `:403`, `:420`). A rejected push means another machine holds the run, and nothing starts. The branch on origin is the one-run record: every machine reads it, and it is in git (Manifesto Principle 1). The commit-time phase gate exempts `idea/` (`packages/domain/src/rules/phase-gate.ts:62-67`), so the spec commits pass it.
- The tree. The agent works in its own worktree at `.plot/state/design/<slug>/`, checked out on `idea/<slug>-spec`, never in the operator's checkout. The directory sits beside the verify run's `verifyRunDir` (`auto-verify.ts:47`), so `Worktree root` keeps only slice desks. fleetd removes the worktree and its local branch with `Trees.removeWithBranch` (`trees.ts:296`) when it settles the run.
- The bound. `startBoardRun` takes `boundSeconds` from `Worker bound` (28800 in this repository, `DEFAULT_VERIFY_BOUND_SECONDS` where absent), as the verify run does (`auto-verify.ts:393`, `:526-536`).
- The prompt. *Commission design*'s prompt turned around: read the plan and its story, write the spec into `## Spec`, commit and push `idea/<slug>-spec`, change no `State:` line, approve nothing, write nothing to a tracker, and open no PR.
- The PR. fleetd opens the PR itself, through `Host.prCreate` (`host.ts:222`), with the title `plot: the spec of <slug>` and `draft: true`. Why fleetd and not the agent: the fleet then reads the outcome itself, a failed `pr-create` becomes a recorded failure instead of a silent `work` branch, and the agent needs no host CLI. The slice adds an optional `draft` field to `PrCreateRequest` (`host.ts:90-99`) and `host-shell.ts:352-366` passes `--draft`, which `plot-host.sh pr-create` already takes (`plot-host.sh:3871`). Existing callers omit the field and keep a ready PR.
- The cap. A going spec run counts in `scaleUp`'s `running` (`packages/domain/src/workflows/assign.ts:229`) beside `verifying`, so it starts one slice agent fewer. `specStart` refuses while a verify run goes, and `verifyStart` gains the same refusal for a going spec run, so the machine keeps the `Parallel agents` + 1 bound that DESIGN-phases.md §6 states. The verify pass runs before the spec pass, so when both may start, the verify run starts.

**Settling a run.** After the run's process ends, fleetd fetches and reads `claimTip` of `origin/idea/<slug>-spec`, then settles by one arm and removes the worktree:

| Ref reads | Also read | Outcome | Ref |
|---|---|---|---|
| `work` | the plan's spec on the branch is written; `prCreate` answers | success: `lastSuccessAt` moves, which clears the halt | kept, the PR's head |
| `work` | spec written; `prCreate` fails | failure `pr-not-opened` | kept; restart opens the PR |
| `work` | spec empty on the branch; `prMerged` reads `not-merged` | failure `spec-empty` | deleted |
| `claim-only` | none | failure `no-commit` | deleted |
| `absent` | none | failure `no-branch` | none |
| `unknown` | none | unsettled; the next pass reads again | untouched |

A failure goes through `recordRunFailure`, keyed by the commit that added the plan's `Design:` record (`refs.recordCommit(file, 'Design')`, `packages/domain/src/ports/refs.ts:358`), and `runRetryVerdict` answers `waiting` (60 s, then 120 s, `packages/domain/src/rules/auto-deliver.ts:74-112`) or `stopped` after 3. Three failures across plans since the last success halt every spec run. The store `.plot/state/auto-design-in-flight.json` is machine-local (`.gitignore:30`), so the counts hold per machine.

**Deleting a remote ref.** No port operation deletes a branch on origin today: `Trees.deleteBranch` (`trees.ts:331`) is local. The spec-run slice adds `Trees.deleteRemoteBranch(branch, expectedTip)`, which runs `git push --force-with-lease=refs/heads/<branch>:<tip> origin --delete <branch>` in `trees-git.ts`, so it deletes only the tip that was read. A `work` ref holds commits, so every deletion of a `work` spec ref reads `host.prMerged` (`host.ts:174`, the `mergedAt` reading) first and deletes only on `not-merged`, never on a PR's `state` (CLAUDE.md, *One Answer To "Did This Land"*).

**A crashed run.** A run's record in the store survives a stopped fleetd and a machine restart. On each pass, a record with no end code whose pid is dead past the start grace (`runGoing`) settles through the table above. A `claim-only` spec ref that no run record on this machine names, and whose claim commit is older than `Claim stale after` (24 h, above the 8 h `Worker bound`), is another machine's lost run: fleetd records failure `stale-claim` and deletes the ref. A directory under `.plot/state/design/` with no run record is removed with `Trees.removeWithBranch`.

**The person's controls.** `node skills/plot/scripts/board/plot-design.mjs restart <slug>` reads the spec ref and the host, then acts by one arm:

- `absent`: clears the plan's failure record and its `declined` mark, and writes a restart mark for the plan's `Design:` commit.
- `claim-only` with no going run on this machine: deletes the ref, then as `absent`.
- `claim-only` or any ref with a going run on this machine: refuses `running`.
- `work` with an open spec PR: refuses `open-pr`, naming the URL.
- `work` with no PR and the spec written on the branch: opens the draft PR through `Host.prCreate` and records a success.
- `work` with no PR and the spec empty, or with a closed PR: deletes the ref when `prMerged` reads `not-merged`, then as `absent`.
- `work` whose PR merged: refuses `merged`; the plan's text on `origin/<main>` decides from then on.
- `unknown`, or a host that cannot answer: refuses `unknown`.

`specStart` lets a plan with a restart mark pass `declined`, `halted`, `stopped` and `waiting` once, and the start consumes the mark. So a person's restart starts a run while spec runs are halted, and that run's success moves `lastSuccessAt` and lifts the halt for every plan. `/plot-fleet --status` prints the same line as the row, and `/api/fleet` carries the rows in a `design` field.

**The cost.** One spec run is one `Design command` context (Opus, by the line this slice adds), one host read (`prState`) and three host writes: the claim push, the agent's push and `prCreate`. A failed run adds at most one `prMerged` read and one ref deletion. Runs follow a person's act, plus at most two automatic retries per plan under `runRetryVerdict` before `stopped`. 0 plans read `State: Design` on `main` today.

**Removing *Commission design*.** The board route and every reader of it go: `packages/board/src/server/commission.ts`; `CommissionDesignButton.tsx`; `POST /api/commission` and `GET /api/commission/<slug>` (`packages/board/src/server/index.ts:34`, `:298-317`, `:484`, `:768-798`); the board's `commission` capability (`packages/board/src/contract/schema.ts:1234-1292`, `packages/board/src/server/board.ts:2389-2392`); `CardControls.commission` (`packages/domain/src/rules/card-controls.ts:12`, `:43`, `:81`); `askedWithoutTransport`'s `commission` (`packages/board/src/server/entry/ask.ts:153`); the reads in `App.tsx:484-491`, `:1147-1164`, `AgentList.tsx:306`, `:1662`, `:1996` and `packages/board/src/app/lib/agent-rows/rows.tsx:233-260`, `:463`, `:524-526`, `:880`, `:1717`; the row-menu entry in `menus.tsx` (`:11`, `:1345-1508`, `:1588-1590`).
