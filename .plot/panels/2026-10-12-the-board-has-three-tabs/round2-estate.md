## Findings

1. **high: the client receives no issue source and no `inbox` rows, but `waitingTickets` needs both.** `waitingTickets(issues, inbox, reader, source, showAll)` returns every ticket with a notice for a Bitbucket source, hides and counts for a GitHub source, and returns `inbox` for an unmatched Jira reader. `refreshIssues` computes `issueSource` (`packages/board/src/server/fleet.ts:1480-1484`) and stores only `issues`, `issueAnswer`, `issueError` and `issueAbsence` on the entry. `FleetShape` (`packages/board/src/contract/schema.ts:3994-4428`) has no source field and no `inbox` field, and `ServerInfoSchema` (`:1089`) carries `hostUser`, `gitEmail` and `people` but no backend or tracker. On this repository 127 of 127 open issues have `assignees: []` (`gh issue list --state open --json assignees`), the same shape every Bitbucket ticket has. So the client cannot choose between the D22 notice and the hidden count without a field the plan does not name. The plan's source union `'github-issues' | 'bitbucket' | 'jira'` also mixes a tracker scheme with a backend word: `issueSource` answers `{ ask: 'git-host' }` for a repository with no `Tracker` key (`packages/domain/src/rules/issue-source.ts:46-51`), and the backend word is then `github` or `bitbucket`, so the mapping to the union is not stated. The lanes plan says `/api/fleet` "carries only the inbox" (`tickets-and-stories-have-lanes.md:110`) and adds no `inbox` field either. The Board impact comment (`:23`) names only `assignees`, `releasedOnly` and the verification row kind. I checked this by listing the `FleetShape` keys with `awk` and reading `refreshIssues`.
2. **medium: `releasedOnly` changes the payload, and the plan says it does not.** *The Planning tab* says "the server and the payload do not change". `board.ts:2332` spreads `phaseColumns(...)` into each `Column`, so the new flag rides `/api/board`. The client's type is `Column = z.infer<typeof ColumnSchema>` (`schema.ts:772-783`), which has `phase`, `leadership`, `accent`, `checklist` and `cards`. `ColumnSchema` must therefore gain `releasedOnly` before the client can read it. The client casts and does not parse, so a payload from an older server has no flag. If `planningColumns` reads an absent flag as false, it shows Released with the checkbox off. Also, `PhaseColumn` names its field `name` (`workflow-phases.ts:208-217`) and the payload's `Column` names it `phase`, so `planningColumns(columns, …)` cannot take `board.columns` with a `PhaseColumn[]` signature. I checked this by reading `ColumnSchema` and with `grep -rn "BoardSchema.parse"`, which finds no server-side or client-side parse of the board payload.
3. **medium: the "127 hidden" example is false on the board, and the cap Open Point applies today, not only after the index.** `refreshIssues` asks `issue-list --limit 50` (`fleet.ts:1492`, `ISSUE_LIMIT` `:192`) and then drops the referenced tickets (`:1578`). So `/api/fleet` holds at most 50 tickets, and `hidden` can never read 127 on this repository. *Waiting on you* says "On this repository that reader sees 0 tickets and the count 127", and the Acceptance's first `waiting-tickets` case uses 127. As a domain test over 127 inputs the case passes, but it describes nothing a reader sees. The Open Point *Assigned tickets beyond the 50-row inbox cap* places the problem "with the lanes index". This repository has 127 open issues today, so an assigned ticket older than the 50 newest is hidden silently already, against D22.
4. **medium: the verification row would duplicate a plan-level row that already exists.** *The verification row* says "*Waiting on you* rows are per-branch `AgentRow`s, so a plan-level row is a new row kind". The section already renders two kinds of non-`AgentRow` row. Draft plans render through `DraftPlanRowView` (`packages/board/src/app/lib/agent-rows/draft-plan-row.tsx:18`, which uses `tupleFromPlan` and `TupleRowView`) from `draftRows` at `AgentList.tsx:1123`. Tickets render at `:2367`. A failed verification is a plan-level row of the same shape: plan, a sentence, and no branch. The plan does not name this precedent, so a worker can add an `AgentRow` kind and the server-side sort plumbing that the drafts path does not need. #1640 (H7) asks only for "a new row kind, client rendering, a browser test and a raise of the stubbed-test counts".
