# Contradiction lens — design-work-proves-the-path

Position: amend

The plan's design choices agree with D3, D4 and D5 and with its siblings. The plan contradicts four things this repo already decided or already enforces: the approval workflow picks the channel from the plan's `Review:` field, so the stated "later approval through in-session" does not happen. Two dispatch gates beyond `sliceVerdict` refuse a Design plan. Manifesto P2 says implementation references an approved plan. The controller gate does not know about the new approval bundle. Each one has a concrete fix. None of them requires a re-decision of D1 to D12, so the position is `amend` and not `reject`.

## Findings

1. **HIGH (blocks approval). The second approval does not go through in-session. It goes through `pr`, and nobody has to be present.** The plan (Design › *Where the plan lives while its spike runs*) merges the plan PR when the spike is approved. It then says "the later approval then records through the `in-session` channel on the default branch". The approval workflow does not take its channel from the caller. It reads the plan's declared `Review:` field: `const inSession = readings.review === 'in-session'` (`packages/domain/src/workflows/approve.ts:227`), and the record text follows from that (`approve.ts:270-274`). For a `Review: pr` plan whose PR is `MERGED`, the workflow accepts (`approve.ts:231-233`), skips the merge (`approve.ts:252`), flips the state and writes `Approved: <date>, <who>, plan-PR #N merged`. The bundle passes `channel: 'in-session'` (`packages/board/src/server/entry/approve.ts:520-525`), but the workflow ignores it unless `Review:` is `in-session`. The unattended refusal (`entry/approve.ts:527`) applies only when `inSession` is true. `/plot-approve` tells an unattended run to proceed under `Review: pr` (`skills/plot-approve/SKILL.md:122-124`). Three results follow. (a) An unattended agent can approve the plan into Development as soon as the spike merges, and that contradicts D10 ("Approval stays a person's act") and DESIGN-phases.md §7. (b) The `Approved:` record names the PR merge, but that merge approved only the spike. (c) The only way to get the in-session channel is to rewrite `Review: pr` to `Review: in-session` by hand. No controller does that, and "The Master Agent Uses The Controllers" (CLAUDE.md) forbids it. The *Phase Guardrails* rule "cannot approve an unreviewed draft" is also weakened: the person rewrites the remaining slices on the default branch, and no review channel sees that rewrite.

2. **HIGH (blocks the slice's outcome). Changing `sliceVerdict` does not make the spike dispatchable.** The plan says that after `sliceVerdict` changes, "`/plot-dispatch` and the dispatch endpoint can then dispatch the spike". Three other gates refuse a Design plan, and the plan names none of them. (a) The dispatch workflow's `plangate` accepts only `approved`. It refuses `design` with `state-wrong` ("not Approved") (`packages/domain/src/workflows/dispatch.ts:527-546`). Its doc comment calls it the gate for "a plan nobody approved" (`dispatch.ts:475-480`). (b) The brief gate refuses a branch that has no brief on `origin/<main>` (`dispatch.ts:470`). The only writer of a brief is `/plot-implement`, and its workflow refuses `design` with `state-too-early` (`packages/domain/src/workflows/implement.ts:131-138`). (c) The commit-time phase gate refuses an implementation commit while the plan is Design on the shared ref (`packages/domain/src/rules/phase-gate.ts:185-192`). It fires whenever the branch slug equals the plan slug (`packages/board/src/server/entry/gate.ts:336-382`), which is the usual shape for a one-branch spike. The sibling `the-fleet-writes-the-design` repeats the same claim ("makes an approved spike of a Design plan eligible for `/plot-dispatch`", its Motivation, line 27) and changes only `planAutoDispatch` and `startableBranches`. So the error is inherited by both plans.

3. **MEDIUM. Manifesto Principle 2 is contradicted, and the plan does not say so.** `skills/plot/MANIFESTO.md:21-23` says "implementation only ever references a stable, **approved** plan … the invariant is the recorded approval". The phase gate's refusal quotes it (`phase-gate.ts:191`). D4 is binding, so the spike runs before approval. But CLAUDE.md names the manifesto the design authority ("when in doubt, the manifesto wins"). The plan must amend P2 so that a `Spike approved:` record counts as the recorded approval of one branch. Otherwise every gate in finding 2 still has a manifesto sentence that tells a later reader the spike is a violation.

4. **MEDIUM. The plan does not say who merges the plan PR at spike approval, and the plan gives no pin.** Approach says "approving the spike merges the plan PR". But `approveSpike` is described as a transition that "writes `Spike approved:`" and nothing else. A transition cannot reach a host. The merge is a `pr-merge` write in the workflow, as `approve.ts:252-257` shows. The controller gate refuses an unpinned merge (CLAUDE.md, *The Master Agent Uses The Controllers*; `packages/board/src/server/entry/gate.ts:497-505`). The plan must name an `approveSpike` workflow that holds the `pr-ready`/`pr-merge` writes pinned to the head SHA. It must also say on which branch the record commit lands (on the PR head before the merge, or as a booking commit after the merge).

5. **MEDIUM. The new bundle bypasses the controller gate.** The gate classifies only the five names in `GATED` (`packages/domain/src/rules/ci-suite.ts:233-240`; `scriptNamed` at `:284-292` matches only exact basenames). The prefilter matches `plot-approve-spike.mjs` (`rules/controller-gate.ts:47-53`), but `controllerInvocation` answers `null`, so the gate allows the command. CLAUDE.md says the gate refuses the `approve` and `deliver` bundles when no controller receipt exists. A new lifecycle bundle that merges a PR and writes an approval record needs the same entry: a `ControllerAction` (`controller-gate.ts:11`), a `GATED` key and a receipt from `POST /api/approve-spike`. Without them a master agent can run the bundle directly, which is the 2026-09-08 failure that the CLAUDE.md section records.

6. **MEDIUM. The source of "spike merged" is not named, and approval is a destructive decision.** The `spike-unmerged` refusal decides whether a phase flips. *One Answer To "Did This Land"* (CLAUDE.md) puts a phase flip in the destructive class. That class reads the host's `mergedAt` and nothing else, never a merge subject and never ancestry. The plan must name that reading. In the transition it is a `Precondition` (`transitions/plan.ts:258` takes `input.preconditions`, and line 335 checks it). In the bundle it is the host port's PR state for the spike branch.

7. **MEDIUM. The tracer plan's state is written in "the same step" without a receipt for it.** "`deliver` delivers a proven tracer plan in the same step as its first dependent." The state gate clears one receipt per `(path, value)` and spends it (`packages/board/src/server/entry/gate.ts:231-250`). The deliver workflow writes one plan today. The plan must say that the deliver workflow writes the tracer plan's `State: Delivered` and its index symlink, and records a second receipt. If it does not, the commit is refused, or someone writes the second file by hand.

8. **MEDIUM. "The person edits the remaining slices in the same change" does not match how approval commits.** Under the default-branch flow the approval bundle writes in a booking worktree cut from `origin/<main>` (`entry/approve.ts:285-286`, `:693-698`). It stages only the plan file, `.plot/hold` and the sprint file (`workflows/approve.ts:326-331`). The person's slice edits in their own checkout do not go into that commit. The plan must name the edit route: a reslice through `/plot-reslice`, or a plan-file commit before approval. It must also state that the approval refuses when the checkout holds unpushed slice edits.

9. **LOW. A spike in a later slice heading, or in a heading with other branches, has no defined result.** `sliceVerdict` judges a slice heading, and the fold blocks every slice after a slice that is not `complete` (`rules/eligible.ts:92-112`, `:132-139`). The spike is a branch annotation. The plan must say that `approveSpike` refuses unless the spike branch is alone under the first slice heading. The other option is that eligibility goes to that branch and not to its heading.

10. **LOW. The board's draft placement rule does not cover `design`.** `draftPlacement` answers only `planPhase === 'draft'` (`packages/domain/src/rules/draft-placement.ts:44-45`). So the invariant that the released plan `a-draft-slice-waits-on-its-approval` holds ("no row pairs `verdict: unapproved` with `group: not-started`") does not apply to a Design plan's non-spike slices. The plan's *Every view state is a domain property* names `spikeOf` and `planStatus` and does not name this rule.

11. **LOW. The `waits:` sits on the wrong slice.** The note says the first slice waits on `feature/the-phases-are-a-declaration` "because `phaseOfPlan` is where a tracer plan's phase is read". But `phaseOfPlan` is used by `feature/a-tracer-plan-stays-in-design`, not by the markers slice. The wave order still holds, because the tracer slice follows the markers slice, so this costs only a delay. The markers slice could start now.

The claims I verified as true: `rules/eligible.ts:43` (`DISPATCHABLE_PHASE = 'approved'`); `rules/eligible.ts:92` (`sliceVerdict`); `transitions/plan.ts:258` (`approve`, which already accepts `design`); `rules/phase.ts:147` (`planStatus`); `plot-plan-meta.sh:448-458` (`norm_type` reads only feature, bug, docs and infra); `plot-plan-meta.sh:94` and `:1054`; `rules/state-transition.ts:93` (`owningCommand`). "`State:` does not change, so the state gate is not involved" is true for `approveSpike`: `stateTransitionOf` passes an unchanged value (`state-transition.ts:141`). The later Design to Approved flip gets its receipt from the approval bundle, as it does today (`entry/approve.ts:320-321` flips `design`). The siblings agree with the plan on markers, records and order. `the-phases-are-declared` gives the tracer refinement to this plan (its line 42), and `the-fleet-writes-the-design` waits on this plan's last slice (its line 61).
