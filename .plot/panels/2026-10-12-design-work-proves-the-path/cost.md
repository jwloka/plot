# Cost lens — design-work-proves-the-path

Position: amend

The plan prices its new markers and its new controller, and it names the shell line ratchet for `plot-plan-meta.sh`. It does not price the dispatch path. Three gates refuse a `design` plan today, and the plan names one of them. The slice that claims to make a spike dispatchable therefore costs about twice what it states. Most of the extra cost is shell in two scripts that the ratchet counts, and two readers of the pulse that the plan does not name. These are amendments to the slice text and do not change any decision. D4 and D5 stand as written.

## Findings

1. **HIGH: three dispatch gates refuse `design`, and the plan names one.** The plan says that after the `sliceVerdict` change "`/plot-dispatch` and the dispatch endpoint can then dispatch the spike". That claim is false for the code that the slice touches. (a) `packages/domain/src/workflows/dispatch.ts:527-545` refuses every phase except `approved`, and `design` gets `state-wrong` at `:545`. (b) `skills/plot/scripts/plot-dispatch.sh:2957-2977` keeps its own `case "$gate_phase"` and gives `design` the `*` arm at `:2973`: *"is in phase 'design', not Approved"*. (c) `sliceVerdict` (`rules/eligible.ts:94-108`) gets its readings from `plot-fleet-scan.sh:4561`, which writes the three-column line `outstanding<TAB>phase<TAB>states`, and `packages/board/src/server/entry/verdicts.ts:63-92` parses exactly those three columns. A spike flag and a `Spike approved:` reading have no column. So `feature/the-spike-is-approved-alone` must also change the domain dispatch gate, the shell dispatch gate, the scan's reading line and the verdicts entry's parser. The shell ratchet (`scripts/check-shell-lines.sh`) applies to both scripts. The plan accounts for it only on `plot-plan-meta.sh`.

2. **MEDIUM: "the domain's plan parser" does not exist.** The plan says that `plot-plan-meta.sh` "and the domain's plan parser" read `<!-- spike -->`, and it offers to move "the parse into the domain parser alone" to pay the ratchet. No TypeScript parser reads plan markdown branch annotations. `deferred` and `waits` reach TypeScript only as `plot-plan-meta.sh` JSON, through `PlanMetaSchema` (`packages/board/src/contract/schema.ts:76-98`). The real second reader is that schema, plus the fleet scan's JSON. The ratchet escape that the plan names is a new parser in a new place, and the plan does not size it.

3. **MEDIUM: the pulse carries no plan type, so automatic delivery cannot skip a tracer plan as written.** `planAutoDeliver` (`rules/auto-deliver.ts:274-300`) reads `pulse.plans`, and the pulse's `PlanSchema` (`entities/fleet.ts:695-713`) holds `file`, `phase` and `slices` only. To skip `Type: tracer`, `plot-fleet-scan.sh` must emit the type, and `entities/fleet.ts` must accept it. That is a second shell change, under the ratchet, in a script that `skills/plot/scripts/README.md:7` calls "a plan of its own". The slice `feature/a-tracer-plan-stays-in-design` does not name it.

4. **MEDIUM: `proven` has readers that the plan does not name.** `PlanStatusSchema` has two definitions, `packages/domain/src/rules/phase.ts:25-27` and `packages/board/src/contract/schema.ts:394-396`, and both need the new word. The sprint counters in `packages/board/src/server/fleet.ts:6387-6410` and `:6465-6486` switch on the status, and `proven` falls to the default arm, so the plan is not counted. A tracer plan in a sprint then drops out of the sprint's open, WIP and done totals. The auto-bump at `board.ts:2113-2115` keys on `deliverable` and is safe, as the plan says.

5. **MEDIUM: two branches under one slice heading.** `### The spike and the tracer` holds `feature/the-spike-is-approved-alone` and `feature/a-tracer-plan-stays-in-design`. The estate's own term is that a Slice holds exactly one branch (CLAUDE.md, *The Domain Package*), and `/plot-reslice` exists to repair this shape. With auto-dispatch on, the two branches run in parallel. Both edit the plan card (spike button versus `proven` badge), `plot-plan-meta.sh` readers and the board contract schema, so a rebase conflict between them is likely. The cost is one extra conflict round, paid by a worker. Two headings in order remove it, at no loss, because neither branch needs the other.

6. **MEDIUM: the spike slice must be the first slice, or `sliceVerdict` blocks it.** `sliceVerdicts` is a fold (`rules/eligible.ts:110-130`). A slice after an `unapproved` or `empty` slice reads `blocked`, so a spike written under the second heading never becomes eligible, even after `Spike approved:`. The plan neither requires the spike to be first nor says how the fold treats it. Without a rule, the operator gets a spike that is approved and never dispatchable, and nothing explains why.

7. **LOW: the plan says that the later approval "records through the in-session channel". The code does not do this.** `approve` picks the channel from the plan file's `Review:` (`transitions/plan.ts:299-332`). The approve workflow already skips the merge when the plan PR is `MERGED` (`workflows/approve.ts:229-257`). So a `Review: pr` plan whose PR merged at spike approval approves through the `pr` arm, with no channel change. That is cheaper than the plan's wording. The Open Point should state the real path, so that nobody builds a channel override.

8. **LOW: delivering two plans "in the same step" is not sized.** `deliver` takes one plan (`transitions/plan.ts:381`). The state gate needs one receipt per `State:` write (`skills/plot/scripts/plot-state-receipt.sh:1-7`). Delivering a tracer plan with its dependent therefore needs either two deliver decisions in one controller call or a new multi-plan transition. The plan names neither.

9. **LOW: the phase gate can refuse a spike commit.** `phaseGateRefusal` (`rules/phase-gate.ts:185-193`) refuses an implementation commit while the plan is `design`. It fires only when the branch slug resolves to the plan's own file (`packages/board/src/server/entry/gate.ts:336-382`). A spike branch named `feature/<plan-slug>` is refused at commit, and other spike branch names pass. The plan should state which applies, or forbid the plan-slug name for a spike.

10. **INFO: claims that hold.** `rules/eligible.ts:43` holds `DISPATCHABLE_PHASE = 'approved'`. `plot-plan-meta.sh:448-457` `norm_type` accepts four words. `transitions/plan.ts:258` is `approve`. `rules/phase.ts:147` is `planStatus`. The template's `### Tracer` heading is at `skills/plot/templates/plan.md:42-55`. The first slice's `waits: feature/the-phases-are-a-declaration` names a real branch of `the-phases-are-declared`. `the-fleet-writes-the-design` waits on this plan's last branch, which matches its Notes.
