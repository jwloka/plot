# Estate juror: the-phases-are-declared

Lens: does this already exist, and does the plan see everything the estate already holds?

Position: amend

## Verdict

The plan builds the right thing. No phase-map parser, no `needsDesign` transition and no owning command for `design` exist on this branch, so the plan does not duplicate an artifact. But the estate holds more hard-coded phase names than the plan lists. Four board sites decide behaviour from the literal `'Discovery'` or from the closed `Phase` union, and the plan names none of them. With the default map, two of them break visibly: the Approve button disappears from every Draft card, and an `idea/` branch row stays in Discovery against D1. The plan also replaces a rule, `storyPhase`, that nothing in production calls. Amend the Design and the first two slices before approval.

## Findings

1. **Unresolved. `isDraft` reads the literal `'Discovery'`.** `packages/board/src/app/components/PlanCard.tsx:83-85` returns `card.phase === 'Discovery'`, and the comment above it says this is the test for "only Draft cards, and every Draft card" that carry the Approve action (`PlanCard.tsx:75-82`). With the default map a Draft plan reads in Design, so `isDraft` answers false for every Draft plan. The Approve button vanishes, and the plan's new *Needs design* button "on a Draft plan's card" has no predicate to hang on. The predicate must read the plan state, not the phase name. The plan does not mention it.
2. **Unresolved. An `idea/` branch row is hard-coded to Discovery.** `packages/board/src/server/fleet.ts:5842` sets `phase: /^idea\//.test(branch) ? 'Discovery' : null`, with the comment "a plan under review is Discovery by definition" (`fleet.ts:5834-5836`). D1 says Discovery holds only stories. After this plan, a Draft plan reads in Design while its own idea branch row reads in Discovery. The row must read the phase that holds `plan:draft` from the map. The plan does not mention it.
3. **Unresolved. `phaseDateOf` switches over the five literal names.** `packages/board/src/server/board.ts:1165-1178` maps `Released`, `Testing`, `Design`, `Development` and `Discovery` to a record. A declared phase outside the five gets no case, and the function stops being total once `phase` is a string. With the default map a Draft plan in Design sorts by `design_raw`, which a Draft plan does not carry. The function must key on the plan state, or on the map's members. The plan does not mention it.
4. **Unresolved. Leadership lookups crash on an undeclared name.** `Board.tsx:217-219` and `Swimlanes.tsx:161-163` read `PHASE_LEADERSHIP[phase].who` and `.icon` with no guard. The plan says a phase outside the five "carries no leadership", but both sites throw a `TypeError` for it. The board slice must name these two sites and the guard.
5. **Unresolved. Three wire fields, not one.** `packages/board/src/contract/schema.ts:425`, `:736` and `:2486` each type a `phase` field as `z.enum(BOARD_PHASES)`. The plan says "The wire field typed `z.enum(BOARD_PHASES)` becomes a string". Name all three. Also name the other `BOARD_PHASES` readers the board slice must move: `board.ts:2252` (the column list), `Swimlanes.tsx:66` (`LANE_PHASES`), `StoryModal.tsx:84` (plan order in a story), and `mock-fleet.ts:306`, `:325`.
6. **Unresolved. `storyPhase` has no production caller.** A grep for `storyPhase` over `packages`, `skills` and `scripts` outside tests returns only its declaration at `packages/domain/src/rules/phase.ts:72` and a CHANGELOG entry (`packages/board/CHANGELOG.md:1578`). The plan's Motivation says it "spreads the six story statuses over all five phases" as if that reached the board. It does not: no story is placed by it today. `phaseOfStory` therefore has no consumer in this plan. Either say that `the-board-has-three-tabs` or `tickets-and-stories-have-lanes` is its first caller, or drop it from the first slice. The plan's own Notes line ("`storyPhase` returned `rules/phase.ts`") already shows the zero, and the Motivation does not draw the conclusion.
7. **Unresolved. `rowPhase` needs the map at its caller.** `rowPhase(planPhase, state)` (`rules/phase.ts:99`) is called by the board's `packages/board/src/server/fleet.ts:5463`. Once it composes `phaseOfPlan(map, …)`, the agent-row build in the board's `fleet.ts` must receive the parsed map. The plan says the board server reads the key "once per build" but names only the board payload, not the fleet-row path. Name the second reader.
8. **Unresolved. The plans board gets a column that can never hold a plan.** With the default map, Discovery holds `story:*` only, yet the Board slice draws "one column per listed phase" on the plans board (`board.ts:2252`, `Swimlanes.tsx:66`). The estate already measured this exact defect: `docs/plans/2026-08-16-board-shows-discovery.md` ("The column that promises a place and can never hold one"), released v2.5.0. Between this plan and `the-board-has-three-tabs`, the plans tab shows an always-empty Discovery column. The board slice should draw only the phases that hold at least one `plan:` member, and say so.
9. **Wrong cause. `owningCommand` does not decide the gate.** `owningCommand` (`rules/state-transition.ts:93-106`) only words the refusal at `:250`. The gate admits a write when a receipt matches (`skills/plot/scripts/plot-state-receipt.sh:6-7`), and an escape already exists: `plot-state-receipt.sh --unowned <path> <value> <reason>` (`:9-11`, `:305`). The Motivation's "so the state gate refuses" and the Design's "`owningCommand` names the action for `design`, so the state gate admits the write" both attribute the gate to the message. Rewrite: the controller writes a receipt through the existing `ports/state-receipts.ts` (the TypeScript writer is `packages/board/src/server/entry/ladder.ts:56`), and `owningCommand` gains a `design` arm so the refusal names `/plot-needs-design`.
10. **Imprecise. The `Design:` record format.** The plan writes `<date>, <who>, <channel>`. `plot-plan-meta.sh:240-245` documents `design_raw` as "who/when, and what the design work is". The parser takes the raw line, so the format does not break it, but the two descriptions differ. Pick one and update the script comment in the same slice.
11. **Imprecise. `local-checks.ts` does not refuse.** The plan says `parsePhaseMap` follows `rules/local-checks.ts`, "which parses the `Local checks` value the same way". `parseLocalChecks` (`rules/local-checks.ts:73-82`) skips a malformed pair silently and has no refusal. The split grammar is shared; the refusal is new. Say so, so the implementer does not copy the silent skip.
12. **Unresolved. The third ceremony question touches more prose than listed.** `skills/plot-idea/SKILL.md:198` says "Every plan records two independent answers (Manifesto Principle 10)", `skills/plot/MANIFESTO.md:77-79` (Principle 10) says "Every plan answers two independent questions", and `CLAUDE.md:166` describes `plot-idea` as "two-question triage". The prose slice lists none of these. Also the board's `idea` controller prompt says "Stop at **Draft**" (`packages/board/src/server/idea.ts:279`), so a board-started idea agent cannot answer yes. State whether the design question is asked there, or name the prompt as out of scope.
13. **Holds. No phase map exists today.** A grep for `Workflow phases`, `phase map` and `parsePhaseMap` finds no artifact. `transitions/plan.ts` holds `design` as a source state for approve (`:261`) and others, but no transition into `design`. `commission.ts:136-177` asks an agent to write `State: Design` by hand, which the plan's Notes already name.
14. **Holds. The cited lines are accurate.** `entities/workflow.ts:35`, `:62`, `:143`, `:166`; `rules/phase.ts:41`, `:72`, `:99`; `board.ts:2082` and `:2115`; `rules/state-transition.ts:93`; `SKILL.md:170`, `:266`; `MANIFESTO.md:99`, `:148`; `DESIGN-plan.md:688`; `DESIGN-story.md:562` all hold what the plan says. `DESIGN-plan.md` §4 runs to `:900`, not `:830`, and `DESIGN-story.md` §4 to `:622`, not `:620`; both still sit inside §4.
15. **Holds, but empty. The fleet grep.** A grep under `packages/fleet/src` for `BOARD_PHASES`, `toBoardPhase`, `storyPhase` and `rowPhase` returns zero today. The plan's acceptance line "returns zero matches after the first slice" is true before any slice. The fleet-side reader of phase is the board's `fleet.ts` (finding 7), which the grep does not cover.
