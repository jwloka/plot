### The decisions the plan settles — do not re-derive them

- **Test the wiring, not the logic.** `defaultBranchRed`, `runIndexMonitor` and `runDeskRelay` already have their own unit tests in the domain and shared-module layers. This wave's job is proving that `registryd-main.ts` calls them with the right world, in the right order, and survives their absence or failure — not re-testing their internals. A test that duplicates `default-branch.test.ts`'s coverage of `defaultBranchRed` itself is out of scope here.
- **Extract the composite `prs` beat into its own exported function, as the plan's "one gap" describes**, even though `indexMonitorOver` and `deskRelayOver` are already separately exported. The remaining gap is specifically the inline closure at `:1936-1943` that sequences `readPrs`, `readDefaultBranch` and `indexMonitor` — pull it out so a test can call it directly with a controlled world, rather than driving it through `startFleetClock`'s pulse machinery.
- **Mutation-check each new test** by removing the line it guards and confirming the test fails. The plan is explicit about this for a reason: `registryd-main.test.ts`'s existing `run` tests already pass `stop: () => true`, which is precisely how the `prs` beat and the relay call went untested for this long — a loop that never iterates never fires either. A new test that merely calls the extracted function without asserting its effect on a distinguishable world is the same mistake one layer up.
- **The null-channel path is a real branch, not a defensive dead end.** `--once` sets `channel` to `null` (`:1908`), which makes `indexMonitor` and `deskRelay` both `null` (`:1909-1914`), and the `prs` beat's `await indexMonitor?.()` and the relay call's `deskRelay?.()` both degrade to no-ops. Test that a `--once` run (or an equivalent world with `channel === null`) completes without throwing and without attempting either call — this is the "a `channel === null` tick still runs" case the plan names.
- **A relay throw only warns, and that is existing behavior to pin, not a new fix.** The `try`/`catch` around `deskRelay?.()` at `:2042-2046` already exists and already only calls `warn`. Write the test that proves it (reject `deskRelay`, assert `warn` was called and the loop did not stop), rather than adding a second layer of defense.
- **SIGTERM/SIGINT is new behavior, not a wiring test.** Unlike the other three items, nothing currently calls `process.on` for either signal in this daemon's own entry. The fix adds handlers that call the existing `stop` mechanism (the loop already checks `stop()` at the top of each pass and already calls `channel?.stop()` on exit, per `:1861-1864` — reuse that path rather than inventing a second shutdown route) so `.plot/fleet.sock` is cleaned up on a real `kill`. Test the handler registration and its effect on `stop`'s return value; do not try to test an actual OS signal delivery in the suite — set the handler to flip the same boolean `stop()` reads, and assert the loop exits on the next `stop()` check.
- **The bind retry (#1465 L3, first half) adds a later-beat retry to `startFleetChannel`'s caller, not a retry loop inside `startFleetChannel` itself.** `startFleetChannel` is a single attempt by design (it is called once, before the loop, at `:1908`); giving it an internal retry loop would block startup. Instead, a later beat — the `prs` beat is the natural one, since it already runs on a cadence independent of the scan — re-attempts the bind if `channel` is still `null` and updates the closed-over `indexMonitor`/`deskRelay`/`channel` bindings on success. This is a design choice the plan leaves open; if you take a different approach, say so in the PR body rather than choosing silently and leaving no trace.
- **The swallowed monitor throw (#1465 L3, second half) is a one-line change in `fleet-clock.ts`'s `guarded()`.** Change the bare `catch {}` to `catch (e) { warn(...) }` — but `guarded` does not currently take a `warn` parameter, so threading one through touches `FleetClockWork` or `startFleetClock`'s signature. Check every call site of `startFleetClock` before changing its signature; `registryd-main.ts` is very likely the only one, but confirm rather than assume.
- **Style:** a function you write is an arrow (`CLAUDE.md`'s domain-package rule does not bind `packages/fleet/src/`, but `registryd-main.ts` and `fleet-clock.ts` are themselves a mix — match the file's existing declarations where you are editing in place, and write new helpers as arrows per the repo-wide rule for new code).

### Done when

The plan's own list is the specification — one exported function with tests for: the hold (`defaultBranchRed` reads a settled-red file and holds, a missing file holds nothing), the beat order (`readPrs` then `readDefaultBranch` then `indexMonitor`, asserted by call-order on mocks, not just by all three having been called), a null channel (the beat runs to completion with `indexMonitor` and `deskRelay` both absent), and a relay throw (warns, does not stop the loop). Plus: fleetd stops on SIGTERM and SIGINT; a failed channel bind retries on a later beat; a swallowed monitor throw in `fleet-clock.ts` now warns; and the relay keeps running while ticks fail (verify this last one is already true with a test, since the code reading suggests it is).

The assertions that exist because a naive implementation would pass without them:

- **Call-order, not call-count.** A test asserting only that `readPrs`, `readDefaultBranch` and `indexMonitor` were each called once passes even if a refactor reorders them — and the plan's own motivation section is explicit that order matters here (`indexMonitor` reads the default-branch file that `readDefaultBranch` just refreshed). Assert the order with an array the mocks each push onto.
- **The settled-red fixture must be old enough, or young enough, to disagree with the alternative.** A fixture with no `at` field, or one so recent that "no reading" and "a fresh reading" both hold, proves nothing about the age check slice 1 added. Use a reading timestamped older than `Checks wait` for the "holds nothing" case and one within it for the "holds" case, per [[mutation-test-fixtures-must-make-arms-disagree]].
- **The SIGTERM/SIGINT test must prove the loop actually exits, not just that a handler was registered.** A test that spies on `process.on` and asserts it was called with `'SIGTERM'` passes even if the handler body does nothing. Drive the test through `run`'s own `stop` callback: register the handler, invoke it, and assert the next `stop()` call (or the loop's next pass) returns true / exits — the same shape the existing `run` tests already use for `stop: () => true`.
- **The bind-retry test must prove the retry replaces the live `null` binding, not merely that `startFleetChannel` was called again.** If the retry re-runs `startFleetChannel` but the `prs` beat's closure still closes over the original `null` `channel`/`indexMonitor`/`deskRelay`, the retry is cosmetic. Assert that a finding published after a successful retry actually reaches the channel.
- **The swallowed-throw test must fail if `warn` is removed from the fix, not merely if the throw itself is removed.** Reject a subscriber's promise and assert `warn` was called with text naming the subscriber or the failure — not just that the clock kept running (it already does; that part is not the bug).
