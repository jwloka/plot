## Findings

- HIGH — The juror command runs the pinned commit's bundle, and that bundle ignores `--files` without a word. The plan tells a juror to run `node skills/plot/scripts/board/plot-local-checks.mjs --files <list>` in `verify-<slug>` (plan:85). That relative path resolves to the bundle committed at the delivery commit. For every plan delivered before `feature/the-fleet-verifies-a-delivered-plan` lands, which is the whole first-run population (Open Point 14), that bundle has no `--files`. Today's entry reads only `argv[2] === '--ci-suite-refusal'` and otherwise calls `run()` (`packages/board/src/server/entry/local-checks.ts:191-196`), and `run()` takes `refs.changedFiles('HEAD')` (`:100`), which is empty at the pinned commit. So the juror gets only the `**` gate checks and no plan-specific test, and nothing reports it. The same question applies to `plot-verify.mjs`. Fix: name the bundle the run calls by absolute path (the operator's checkout or the installed plugin), and let `plot-verify.mjs files` refuse when the `plot-local-checks.mjs` it hands to the juror does not accept `--files`.
- MEDIUM — The headroom condition of `verifyStart` cannot refuse. The plan starts a run when "`fleetSize` with `requested` one above `running` answers `start` 1 against the machine's headroom" (plan:103). `fleetSize` never answers 0 when `wanted >= 1`: `ceilingFor` gives 1 for `starved`, 2 for `tight` and Infinity otherwise (`packages/domain/src/rules/fleet-size.ts:88`, `:168-174`), and `start = min(wanted, ceiling)` (`:144-147`). So a 4-Frontier-context run starts on a starved machine. The estate already has the rule that defers a start on a starved machine: `machineDefers` (`packages/domain/src/rules/auto-dispatch.ts:404`), with its operator override `Machine override` (`packages/fleet/src/shared/fleet-settings-store.ts:58-66`). `verifyStart` should read `machineDefers`, not `fleetSize`.
- MEDIUM — The failed-run record and the 3-failure guard duplicate an existing mechanism and do not name it. Auto-delivery already keeps per-plan failure records with a bound of 3: `AUTO_DELIVER_MAX_FAILURES = 3`, `retryVerdict`, `recordDeliveryFailure` and `pruneFailures` (`packages/domain/src/rules/auto-deliver.ts:61-133`, `:170-190`). It stores them in the in-flight store, which also holds the running pids and is keyed by `InFlightKind = 'dispatch' | 'deliver'` (`packages/fleet/src/shared/in-flight-store.ts:100-127`). The fleet starts its unattended skill runs through `startBoardRun` (`packages/fleet/src/shared/board-run.ts:184`), and run logs use a closed set of kinds that a sweep globs for (`packages/fleet/src/shared/agent-log.ts:317-329`), which has no `verify`. The plan's "one run per plan delivery in the fleet's state" and its fleet-wide guard (plan:109, :121) state none of these. The semantics also differ: auto-delivery retries one plan with backoff and stops that plan after 3, while this plan stops all runs after 3 consecutive failures across plans. The slice text should either extend `InFlightKind` and the auto-deliver failure rule, or say why a second store and a second rule are needed.
- MEDIUM — "A detached worktree is no desk" is true for the fleet scan only. The plan cites `worktree_rows` (`skills/plot/scripts/plot-fleet-scan.sh:1810-1816`), which does skip a worktree with no branch. The reaper and the reconcile scan read every worktree under `Worktree root` that has no `.plot-worker.pid` as an unclassified desk that "needs a person" (`packages/board/src/server/entry/reap.ts:590-610`, `skills/plot/scripts/plot-reconcile-scan.sh:2586-2598`). A free agent's desk is itself detached at `origin/<main>` (`plot-reconcile-scan.sh:2654-2659`). The plan puts `verify-<slug>` under `Worktree root` with `.plot-verify.pid`, which neither reader knows, so every live or leftover verify worktree shows as an unknown desk in `/plot-reconcile` and in reap output. Fix: put the worktree outside `Worktree root`, or teach `reap.ts` and the reconcile scan the new marker in the same slice.
