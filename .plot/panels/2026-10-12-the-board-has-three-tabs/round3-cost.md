# Cost juror, round 3: the-board-has-three-tabs

Position: amend

The revision applies both of my round-2 amendments and two of my three optional points, and it declines the third with a reason. It also carries out D31, D32 and D33. The `### Cost` section is true where I measured it on `main` at `1ad9a9f4f`, 2026-10-13. The assignee adds no host or tracker call: a GraphQL dry run of a 100-issue page costs 1 point with and without `assignees(first:100)`. 47 test files open the `agents` tab, the docs grep names 24 files of which 17 change, the browser cases go into two existing files that the catalogue mock serves without a board server, and the shell gains no net line. The cost of the plan is small and bounded, with one exception. The plan now owns the Jira inbox choice, and after the lanes plan's project-wide read a matched Jira reader on a project with more than 1000 open tickets loses their own tickets that are older than the 1000 newest. The `inbox` page that the same pass already reads holds those tickets, so a zero-call fix exists. The hidden-count sentence under `complete: false` also states a number that the plan does not compute. Two amendments fix both, and neither adds a call, a slice or a browser case.

## Findings

1. **Medium: a matched Jira reader loses their own tickets past the 1000-row index cap, although the pass already holds them.** `waitingTickets` answers a matched Jira reader with the open rows whose `ticketOwnership` is `mine` (plan `:64`, `:69`). After `feature/the-lanes-read-the-whole-jira-project`, the open rows are the project-wide read, capped at `ISSUE_INDEX_OPEN_LIMIT = 1000` with `complete: false` (`tickets-and-stories-have-lanes.md:73`, `:117`). The same pass reads one more page, `assignee = currentUser()`, and the index holds it as `inbox` (`tickets-and-stories-have-lanes.md:116`). On a project with more than 1000 open tickets, a matched reader's ticket older than the 1000 newest is in `inbox` but not in the open rows, so the default view drops it. Today's read (`plot-host.sh:4684`) shows it. The Acceptance case (plan `:96`) puts the reader's 3 tickets inside the 1000 rows, so it does not test this. D23 does not settle this case: it says the matched reader reads the filtered project rows, not that the `inbox` rows are discarded. Checked by reading plan `:61-69`, `:96` and the lanes plan `:73`, `:116-119`.
2. **Low: the sentence under `complete: false` names a number that `hidden` does not hold.** The plan says the sentence "reads *at least 1000*" (`:64`), and the Acceptance case answers `hidden` 997 for the same input (`:96`). "At least 1000 open tickets are not assigned to you" is false when the reader holds 3 of the 1000. The sentence must come from `hidden` (*at least 997*), and no unit test asserts the sentence text. Checked by reading plan `:64` and `:96`.
3. **Low: two line references are swapped.** The plan names `trackerReads`/`issueOf` at `tracker-shell.ts:46`, `:120` (`:53`). On `main`, `issueOf` is at `:46` and `trackerReads` at `:120`. Checked with `sed -n '46p;120p' packages/domain/src/adapters/tracker/tracker-shell.ts`.
4. **Low: the Cost section does not name the fleet agents or the `/api/board` growth.** The plan has six slices in six serial waves, so it spends six fleet agents and six reviews; `### Cost` does not say so. It names the index growth (about 25 KB at 1000 rows) but not that the lanes rows on `/api/board` (polled every 30 s, `App.tsx:31`) carry `assignees` too, if *the board's index-row projection* (`:53`) feeds them. Both are bounded; neither is stated. Checked by reading plan `:73-82` and `App.tsx:30-33`.
5. **Low: the two "older server" fallbacks have no reachable case.** The client and the server build together (`packages/board/package.json:49`, `build:client` then `build:server`) and the server serves the client, so a new client never reads an old server's payload. The plan keeps a branch that renders `issues` when `waiting` is absent (`:63`) and reads an absent `releasedOnly` as false in the client (`:45`). The second costs nothing because `ColumnSchema` defaults it. The first is code that no test can reach except by a hand-made payload, which a person must keep. `waiting` is also `null` when the source is `nobody`, and in that case `issues` is `[]`, so the branch has one real use at most. Checked by reading `package.json:15-49` and plan `:45`, `:63`.
6. **Low: the hidden-count payload repeats rows.** `waiting.tickets` (at most 50) rides `/api/fleet` every 4 s (`App.tsx:33`) beside `issues` (50), and the two lists overlap for a reader whose tickets are among the newest. The plan names the bound (`:76`). The cost is about 12 KB per poll on loopback, so it is acceptable; I note it only as the smaller design.
