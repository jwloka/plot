# Round 2 — cost

Position: amend

The revision answers most of what round 1 asked of this lens. The plan now names the runner, the model, the switch, the push count and the duplicate cost of D18, and the numbers it gives match what I measured. Two cost claims do not hold against the code: the capacity count, and the commands a juror can run at the pinned commit. One new cost lands on a person during the release testing round.

## Round-1 points

- **[Cost] Command, model, capacity, switch — partly held.** The runner key `Verify command` follows the *one capability, one key* rule at `packages/fleet/src/shared/implement-run.ts:22-42`, and its absent-key refusal follows `interrogateAvailability` at `packages/board/src/server/interrogate.ts:40-53`. Held. The switch `Auto-verify` beside `Auto-dispatch` with default OFF matches `packages/fleet/src/shared/fleet-settings-store.ts:56-68` (`AUTO_DISPATCH_DEFAULT = false`). Held. The capacity sentence is not held. Plan:85 says "`Parallel agents` counts processes (`registryd-main.ts:980`), so a run counts as 1". Line 980 says only that the cap is the board's control. The count is in `packages/domain/src/workflows/assign.ts:221-224`: `const running = readings.agents.length`, which counts registered agents, free ones included ("a free agent is carrying one — it holds a slot"). A verify process is not a registered agent, so today it counts as 0, not 1. And because idle agents hold slots and I found no scale-down in `assign.ts` or `registryd-main.ts`, a fleet that auto-dispatch has grown to its cap has no free slot, so the rule "starts one only when the cap has a free slot" starts no verification while the fleet is full. Slice 3 (plan:136) says "starts one run at a time within `Parallel agents`" and names no change to `running`. The plan must say which of the two it builds: verify runs counted into `running` (a domain change in `assign.ts`, and then a verification can hold the slot a queued slice waits for), or verify runs outside the cap (and then the machine runs cap + 4 Frontier contexts).
- **[Cost] Volume and pushes — held.** Plan:34 and plan:85 say 167 `plot: deliver` commits since 2026-09-12, about 5.4 a day. I measured 167 over 30 commit days (`git log origin/main --since=2026-09-12 --oneline | grep -c "plot: deliver"`; `origin/main` head 2026-10-12 12:00). The checklist joins the record's commit (plan:89, plan:101), so one push per plan. All three workflows trigger on `push: branches: [main]` with no path filter (`.github/workflows/ci.yml:6-7`, `build-bundles.yml:11-13`, `release.yml:26-28`). `ci.yml:62-64` keys its concurrency group on `github.run_id`, so a record push does not cancel a delivery's run and each push pays a full `validate` (`timeout-minutes: 25`, `ci.yml:194`). The plan states "Each push runs the three `main` workflows"; it is honest, though it gives no CI-minute figure.
- **[Panel] Issue idempotence across a failed push — held.** Plan:91 orders fold, `issueOpen`, the number to `.plot/state/verify/<slug>.json`, then commit and push, and a failed push retries from the state file. This repository declares no `Tracker`, so the cost here is zero (plan:93).
- **[Panel] Duplicate cost of a hand-delivered plan (D18) — held.** Plan:114 states "one more run of 4 Frontier contexts per hand-delivered plan". The story's D18 (`STORY-plot-works-in-five-phases.md:93`) decides it. On this branch 1 of 130 `.plot/panels/` directories holds a delivery panel (`ls .plot/panels/*/deliver-*`), so the duplicate is small in practice.
- **[Panel] Head versus delivery commit — held for correctness, with a new cost below.** Plan:44 pins the run to the delivery commit in a detached worktree.
- **[Cost] A juror at a desk meets the CI-suite refusal and the board — held in prose, not in effect.** Plan:71 names the allowed commands and forbids board and fleet commands; `ciSuiteRefusal` is at `packages/domain/src/rules/ci-suite.ts:139`. But see the first new defect: the command list the plan names is empty at the pinned commit.
- **[Cost] A run paid and discarded when the plan is Released first — held.** Plan:89 keeps the record on a Released plan. Median delivery-to-release gap from round 1 is 1 day, so this case is common, and the run's value to that release is nil; the plan now says the cost is kept, not wasted.

## New defects

- **The pinned worktree gives the Behaviour juror nothing to run.** Plan:71 says a juror runs "the commands `node skills/plot/scripts/board/plot-local-checks.mjs` prints for the files the plan changed". That script reads its changed files from `refs.changedFiles('HEAD')` (`packages/board/src/server/entry/local-checks.ts:100`), which is `git diff --name-only origin/<main>...HEAD` (`packages/domain/src/adapters/refs/refs-git.ts:309-317`). At a detached delivery commit, HEAD is an ancestor of `origin/main`, so the three-dot diff is empty and the script names no plan file and no related test. I read this; I did not run it. The run therefore pays 4 Frontier contexts and a fresh worktree, and its Behaviour lens falls back to `Evidence: read` unless the juror composes its own commands, which plan:71 does not allow. The plan must pass the plan's merge commits (or the delivery commit's parent range) as the diff base, or drop the claim.
- **The pinned worktree has no dependencies, and the plan does not price them.** A new detached worktree under `Worktree root` holds no `node_modules`. Any executed claim first needs `pnpm install` in that worktree, once per run, about 5.4 times a day. The plan's *Cost and capacity* paragraph names contexts and pushes and does not name this install, its time or its disk.
- **`vnext-checklist.md` hides the RC checklist during the testing round.** `board.ts:420-423` takes the lexical last `*-checklist.md` with a plain `.sort()`; `vnext` sorts after every `v<digit>` name, which plan:21 relies on. After `/plot-release rc` renames `vnext` to `v<version>-checklist.md` (plan:101), the next verify run, within about a day at 5.4 a day, writes a new `vnext-checklist.md`, and the Testing badge switches from the RC under test to the next, mostly unticked, list. The person doing the manual round loses the badge for the checklist they are working through. The plan does not name this.
- **Run throughput is not stated.** One run at a time against about 5.4 Delivered plans a day holds only while a run takes under about 4.4 hours. The plan gives no run duration, and `Worker bound` is 28800 s (8 h). With no measured duration the backlog bound cannot be checked.
- **A failed run costs a person a manual run.** A refused label ends the run with no record (plan:79), the fleet never restarts it (plan:97), and the only restart is `/plot-deliver --verify` by hand at another 4 Frontier contexts. Per-claim labels raise the number of gated lines per juror from 2 to 2 + N (N averaged 2.7 and peaked at 8 over the 65 plans delivered in October). The plan does not estimate how often a run fails.

## Ready to approve?

No. The cost statement exists now and is mostly honest, but its capacity sentence rests on a count the code does not make, and the executed-evidence path it prices returns nothing at the pinned commit. Both are plan-text fixes, not redesigns: name the `running` change (or the out-of-cap choice) in slice 3, name the diff base for the juror's commands, price the worktree install, and say how the RC checklist keeps the badge while `vnext` exists.

## Unresolved finding

The plan says a verify run counts as 1 against `Parallel agents`, but `assign.ts:224` counts registered agents (idle ones included), so a verify process counts as 0 today and, with a full fleet, the "free slot" rule never starts one; the plan must name which behaviour slice 3 builds.
