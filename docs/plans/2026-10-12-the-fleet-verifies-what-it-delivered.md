# The fleet verifies what it delivered

> For each Delivered plan the fleet runs a verification panel against the merged work on the default branch, writes a verification record into the plan, opens one `ai-generated` issue per refuted claim, flags a refuted plan, and keeps a manual release checklist for the endgame round. Release stays a person's act.

## Changelog

- The fleet verifies every Delivered plan that is not a tracer plan against the commit that delivered it, including a plan that `/plot-deliver` already panelled at delivery: each Changelog entry and acceptance claim is judged supported or refuted by a gated juror line, and the plan gains a `Verified:` record and a `## Verification` section. A plan delivered again after `/plot-reject` is verified again. The `Auto-verify` setting turns the run on and off, and the `Verify command` key names its runner.
- The fleet opens one issue, labelled `ai-generated`, for each refuted claim where the repository's issue source (`issueSource`) resolves to a declared `Tracker` with a connector, and the board flags a plan with a refuted claim. `/plot-release` lists refuted and unverified plans before it cuts a release.
- `/plot-deliver --verify <slug>` runs the verification panel on a Delivered plan by hand, at the delivery commit or at a commit the person names, and replaces the record.
- The fleet keeps a manual release checklist for the human testing round in `docs/releases/vnext-checklist.md`. `/plot-release rc` adds the RC line to it in place, and the final release renames it to `docs/releases/v<version>-checklist.md`.

## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §6, *In Testing*.

**The claims.** `claimsOf(plan)` numbers the plan's `## Changelog` entries in file order, then the items of an `## Acceptance` section where the plan has one (none today). Claim numbers are read from the plan at the pinned commit, so a later edit of the Changelog does not renumber a run's claims. `board/plot-verify.mjs claims <slug> <sha>` prints the numbered list, one claim per line, and the run hands that list to the jurors. `/plot-deliver` step 5.1 does not run in verify mode, so the jurors and the fold number one list.

**The pinned commit.** A run judges the plan at its delivery commit: the newest first-parent commit on the default branch whose diff adds a filled `Delivered:` line to the plan file. A new refs operation `recordCommit(file, field)` answers it with one `git log`. Every slice of the plan has merged at that commit. A plan delivered later can still have merged a slice before it, so the pin narrows the window in which a later change can refute a claim and does not close it. The run checks out that commit in a detached worktree under `Worktree root`, named `verify-<slug>`, and removes it when the run ends. `plot-fleet-scan.sh` lists a worktree only with its branch (`worktree_rows`, `:1810-1816`), so a detached worktree is no desk. A person who wants to judge a claim at a later commit runs `/plot-deliver --verify <slug> --at <sha>` (below), and the record names that commit.

**The verification record.** A Delivered plan gains two things:

```markdown
- **Verified:** 2026-10-20, delivery 2026-10-19 at 1a2b3c4, judged at 1a2b3c4, 5 supported, 1 refuted

## Verification

- Claim-1 supported — <claim> — 3 of 3 (executed: behaviour, deliverable)
- Claim-4 refuted — <claim> — behaviour refuted; deliverable, changelog supported — #1712
- Claim-5 refuted — <claim> — changelog refuted — no issue: <the tracker port's reason>
```

`verificationOf(plan)` reads them and answers `unverified`, `supported`, `refuted` or `stale`, with the refuted claims, their issue numbers, the delivery date and both commits. It answers `stale` when the record's delivery date differs from the plan's current `Delivered:` value, or when the plan has no `Delivered:` value. The rule reads text only, so the board can ask it on every render. The record is not a `State:` change, so `plot-state-gate.sh` is not involved.

**A rejected plan.** `/plot-reject` replaces the `Delivered:` line with `Rejected:` and keeps every other record (`skills/plot-reject/SKILL.md:111-112`). The plan then has no `Delivered:` value, so `verificationOf` answers `stale` and the card shows no badge from the old record. When the plan is delivered again, its new `Delivered:` date differs from the record's, the plan reads `stale`, and the fleet verifies it as it verifies an `unverified` plan. A rejection and a second delivery on the same day keep the date; the fleet therefore also compares the record's delivery commit with `recordCommit(file, 'Delivered')` before it treats a record as current. `/plot-reject` does not change.

**Tracer plans.** A plan with `Tracer: yes` (D15) never reads in Testing (D5, D14, `DESIGN-phases.md:114`), and D18 verifies a plan in Testing. The fleet starts no run for a tracer plan, `--verify` refuses one and names D5, and `verificationOf` answers `unverified` for it with no badge. The claims of a tracer plan carried with its first dependent are judged where the dependent's Changelog states them. The `tracer` field comes from `plot-plan-meta.sh`, which `feature/a-slice-is-marked-spike` of `design-work-proves-the-path` adds.

**The panel is `/plot-deliver` step 5's panel.** The fleet's run is `/plot-deliver --verify <slug>`, a new mode of the existing skill with its own step section. It replaces three steps and reuses the rest:

- Step 2's phase check is inverted: verify mode refuses a plan that is not Delivered (or Released, for a person's run) and refuses a tracer plan. Step 2's "Already delivered." answer does not apply in verify mode.
- Step 5.1 is replaced by `plot-verify.mjs claims`.
- Step 5.2 runs as written, with step 5's three lenses and rubric, the `verify-` file prefix and the Commitment list below. Step 5.2b, the per-PR fallback without `/plot-panel`, does not run: verify mode with no `skills/plot-panel/` is a failed run that names the missing skill.
- Step 5.3 does not run. The record comes from `plot-verify.mjs fold` over the juror files, never from the moderation. `/plot-panel` still writes the moderation to `verify-panel.md` for a person to read.
- Steps 4 and 4b run read-only and hand the jurors the plan's merged PRs, as at delivery. Steps 6 to 9 do not run, so verify mode flips no phase.

It hands `/plot-panel` step 5's commitment lines plus one label per claim, shown to the jurors in the form `commitmentLine` renders (`panel.ts:90-91`):

```
Position: <supported|refuted>
Evidence: <executed|read>
Claim-1: <supported|refuted>
Claim-2: <supported|refuted>
```

A line pasted from this form fails the gate, because `<supported|refuted>` is not a word in the vocabulary. The form `Claim-1: supported | refuted` would pass as `supported`, because `readJuror` keeps the first word (`panel.ts:148-151`), so no brief or prompt of the run shows it. The `Position:` line is the juror's answer for the whole plan; it is kept because the moderation reads it.

**The per-claim send-back.** `/plot-panel`'s Commitment parameter becomes a list of one or more labels, each with its own words. Step 2's brief shows every label. Step 3 runs one `plot-panel.mjs check` call per label per juror. Step 4 sends a juror back once, with every refusal text of that juror appended, so a juror that omits `Claim-3:` is asked again for it. A juror refused on any label after its one send-back makes the panel refused, as step 4 already rules for one label. A caller that passes one label sees no change, so `/challenge-the-plan` and `/plot-deliver` step 5 keep their behaviour. The fleet implements no part of the panel. What it adds is the fold below.

**Juror commands.** A juror runs what a claim says where the pinned worktree allows: the commands `node skills/plot/scripts/board/plot-local-checks.mjs --files <list>` prints, and the plan's own bundles. At the pinned commit the script's own source of changed files is empty, because `changedFiles` diffs `origin/<main>...HEAD` (`packages/domain/src/adapters/refs/refs-git.ts:309-317`) and the delivery commit is an ancestor of main. So `plot-verify.mjs files <slug>` writes the plan's own files to `<list>`: for each merged slice branch, the host's merge commit (`host.prMergeCommit`) and the files that commit gave the default branch (`refs.commitFiles`, `git show -m --first-parent`), as `packages/board/src/server/controllers/deliverability.ts:140-150` reads them. A new `--files <path>` option of `plot-local-checks.mjs` takes the changed files from that list instead of `changedFiles('HEAD')`. A branch whose merge commit the host does not name is listed in the brief as unread, and a claim that depends on it is committed `Evidence: read`. The worktree needs the repository's dependencies, so the run runs `pnpm install --frozen-lockfile` in it once before the panel, as a dispatched desk does.

**The CI-suite guard.** The controller gate refuses a `CI suites` command only for `PLOT_UNATTENDED=1` in a linked worktree that holds `.plot-worker.pid` (`packages/board/src/server/entry/gate.ts:415-420`, `:473`). The run writes `.plot-verify.pid` at the root of `verify-<slug>` and sets `PLOT_UNATTENDED=1`, and the gate's desk test (`underDesk`, and the CI-suite arm at `:473`) reads either marker. The verify worktree gets its own marker because the fleet scan, the reaper and the desk adapters read `.plot-worker.pid` as a slice agent's desk. A juror starts no board or fleet command. A claim that only a CI suite proves is judged from the CI run on the plan's merge commits and committed `Evidence: read`, as the one committed delivery panel did for `fleet.test.mjs`.

**File names.** `/plot-panel` gains an optional fifth parameter, `Prefix`, default empty, applied to every juror file and to the moderation. `jurorPath` and `moderationPath` (`panel.ts:49`, `:58`) take it. The verification run passes `verify-`, so it writes `.plot/panels/<slug>/verify-<lens>.md` and `verify-panel.md` and never overwrites the Draft rounds' `panel.md`. A second run moves the earlier `verify-*` files to `verify-<n>-*` before it starts.

**The fold.** `foldVerification(claims, jurors)` is a domain rule. It reads every juror file once per claim label through `readJuror` and gives one line per claim:

- `supported` when every juror commits `supported` for that claim.
- `refuted` when one or more jurors commit `refuted` for that claim. The line names the lenses on each side. One refutation decides, because step 5 asks every juror to refute (Principle 12) and a person reads the issue.
- No record when `readPanel` answers `refused` for any label. The run counts as failed.

The line carries which jurors committed `Evidence: executed`.

**The run.** `plot-fleetd` asks `verificationOf` for every plan that reads `State: Delivered` and is not a tracer plan, including a plan that `/plot-deliver` step 5 panelled at delivery: the delivery panel writes no record, so the plan reads `unverified` and the fleet verifies it again (D18). The selection is by state, not by date: every plan that reads Delivered when the switch is on is eligible, and no Released plan is. For an `unverified` or `stale` plan with no run in the fleet's state, it starts one run through the layering rule: the fleet's controller asks the domain, and an adapter starts the process. The runner is the `Verify command` key, with a prompt naming `/plot-deliver --verify <slug>` and `PLOT_UNATTENDED=1`. The key is its own, as `packages/fleet/src/shared/implement-run.ts:22-42` states the rule *one capability, one key*. This repository declares it with `--model opus`, as step 5 asks a Frontier tier for the panel (`skills/plot-deliver/SKILL.md:191`). An absent key starts nothing, and the fleet's status names the key, as `interrogateAvailability` does (`interrogate.ts:40-53`).

**Capacity.** Today a verify process would count 0 against `Parallel agents`: `scaleUp` counts registered agents, idle ones included (`packages/domain/src/workflows/assign.ts:224`), and a verify process is not a registered agent. Every registered agent holds a slot, so a fleet that auto-dispatch grew to its cap never has a free slot, and a rule that waited for one would never start a run. The plan builds this instead:

- A domain rule `verifyStart(readings)` answers whether this pass starts a run. It starts one when `Auto-verify` is on, `Verify command` is declared, no verify run is going, an eligible plan exists, no slice is held `no-free-agent` in this pass, and `fleetSize` with `requested` one above `running` answers `start` 1 against the machine's headroom. Otherwise it answers the first reason that held, and the fleet's status shows it.
- While a run is going, `scaleUp` counts it in `running` (`assign.ts:224` becomes registered agents plus going verify runs), so the fleet starts one slice agent fewer for its duration.
- The real count: the machine runs at most `Parallel agents` registered agents plus one verify process. The verify process holds a moderator and three `Task` jurors, so 4 Frontier contexts. A full fleet of idle agents does not stop a run; a slice that waits for a free agent does.

**Cost.** At about 5.4 Delivered plans a day, a repository with the switch on pays about 5.4 runs a day, 4 Frontier contexts each, one `pnpm install` each, and gets about 5.4 record pushes to `main` a day, the same count as delivery. Each push runs the three `main` workflows. A path filter on those workflows is outside this plan. One run at a time keeps up with 5.4 plans a day only while a run takes under about 4.4 hours. No run duration exists to measure, because no verify run exists; the one committed delivery panel recorded no time. So the fleet's state records each run's start, install seconds, end and outcome, and the fleet's status reports the waiting count, so the backlog is visible from the first day. A run that reaches `Worker bound` (28800 s here) is stopped and counts as failed.

**Refused runs.** Every refusal that survives the send-back is a failed run a person restarts, so the rate decides whether the run removes work from a person. Measured on this branch: 10 moderations under `.plot/panels/` record their gate, and in all 10 every juror committed on the first run, with one label per juror. No run has gated 2 + N labels; N is the number of claims, mean 2.68 and maximum 8 over the 65 plans delivered in October. The send-back lets each juror miss labels once. The plan states no expected rate, because none is measured. The guard: after 3 consecutive failed runs the fleet starts no further run, and its status and *Waiting on you* name the three plans and the reason, until a person restarts one with `--verify`. A failure rate that would move the cost back to a person therefore stops the fleet instead of queuing restarts.

**The switch.** The `Auto-verify` key seeds an `autoVerify` field in `.plot/state/fleet-controls.json`, beside `autoDispatch` (`packages/fleet/src/shared/fleet-settings-store.ts:56-68` for the keys and defaults; the field and the exact-literal rule at `:90`, `:118`, `:139` and `:161`). It defaults OFF, by the same rule: the exact literal `true` turns it on, anything else reads as off. Off starts no run and stops none.

**Writing the record.** `PlanRecordWrite.field` (`workflows/decision.ts:76`) gains `Verified`, and `PlanRecordWrite` gains an optional `mode: 'replace'`. `withRecord` (`workflows/rendering.ts:66-96`) fills a placeholder or appends, and never replaces a filled line; with `mode: 'replace'` it replaces the filled line of that field in `## Status`, and where none exists it fills or appends as today. Only the `Verified` write passes `replace`, so every other record keeps its behaviour. A new write kind `plan-section` replaces or adds one `##` section of a plan file, with its renderer in `workflows/rendering.ts` and its performer in `adapters/performer/perform-fs.ts`. The verify workflow emits the `plan-record` write, `plan-section`, the juror files, the checklist file where the checklist rule allows it, one `commit` (`plot: verify <slug>`) and one `push` on `plot/verify-<slug>` onto the default branch, as `workflows/deliver.ts:224-225` does for delivery. A plan Released while its run was going keeps the record, so no paid run is discarded; the checklist leaves it out.

**Issues for refuted claims.** The tracker port gains `issueOpen({ title, body, labels })`, and `plot-host.sh` gains an `issue-open` op for `jira` and `github-issues`. The verify workflow resolves the port through `trackerForIssues` (from `tickets-and-stories-have-lanes`, `feature/the-tracker-lists-closed-issues`), which follows `issueSource`: `tracker` resolves to the declared connector, which opens the issue; `git-host` resolves to the read-only `trackerGitHost`, which answers `unaskable` on `issueOpen` as it does on `statusWrite`; `nobody` resolves to `trackerNone` with the source's reason. The issue reads and the issue write therefore follow one decision. The port's doc names it as the second write Plot makes to a tracker, decided by D11, and keeps its refusal of every other widening; the five sites in Motivation say so. The order makes the open idempotent: the fold, then one `issueOpen` per refuted claim with no issue number yet, each number written to `.plot/state/verify/<slug>.json` as it returns, then the record's commit and push carrying the numbers. A push that fails is retried on the next pass from the state file, and opens nothing again. A re-verification opens nothing for a claim whose earlier line already carries a number. It finds that line by the claim's text, not its number, because `--at` can read a Changelog with a different order; a claim whose text changed is a new claim.

**No issue.** An `unaskable` answer writes the claim's line as `no issue: <reason>`, with the port's own reason. `trackerGitHost` gives *no Tracker declared; the git host's issues are read-only to Plot*. `trackerNone` gives the reason `issueSource` stated (`packages/domain/src/rules/issue-source.ts:51-63`), for example *no connector lists issues from the declared tracker `linear`*. This repository declares no `Tracker`, so its own runs open zero issues; the refuted badge, *Waiting on you* and `/plot-release`'s list carry the signal instead. Declaring `Tracker: github-issues` here is a config change for the operator, not a slice of this plan.

**The flag.** `planStatus` is not changed. A new card property `verification` carries `verificationOf`'s answer, and a refuted plan shows a *refuted* badge with the count. Before step 1, `/plot-release` lists every refuted plan and every unverified Delivered plan in the release, in both the RC and the final path, and the person decides. An unverified plan is listed because a plan Released before its run is never verified: measured over ten plans dated 2026-09-29, Delivered to Released took one to two days. A refuted plan that needs more slices goes back to Approved through the existing `/plot-reject`, and its next delivery is verified again (*A rejected plan*).

**A failed run.** The fleet records one run per plan delivery in its state. A run that exits non-zero, reaches `Worker bound`, or whose panel is refused after the send-back is not started again for that delivery. `verificationRow(plan, runState)` is a domain property that puts a failed run in *Waiting on you* (`packages/board/src/app/lib/agent-rows/sections.ts:26`) with its log, its reason and the restart command `/plot-deliver --verify <slug>`. The same row names a fleet stopped by the 3-failure guard. `the-board-has-three-tabs` renames that tab to Delivery and keeps the section's content (D9).

**Re-verification.** `/plot-deliver --verify <slug> [--at <sha>]` is the one path a person uses to write a record over an existing one. A person runs it after a fix lands, or to restart a failed run; it replaces the failed entry in the fleet's state. With no `--at`, it judges the delivery commit again; with `--at`, the named commit. It replaces the `## Verification` section and the `Verified:` line, keeps each issue number on its claim's line, and adds a Notes line naming the earlier record. The fleet never re-runs a plan whose record is current; it runs a `stale` one. Closing an issue stays a person's act (D11).

**The release checklist.** The badge must read the RC checklist from `rc` until the final release, so the file keeps one name through the RC round:

- The verify workflow rewrites `docs/releases/vnext-checklist.md` in the record's own commit, so it costs no extra push, and only while the file carries no `RC:` line.
- Its shape is `/plot-release rc`'s: one `- [ ]` item per feature or bug plan delivered since the last release tag, from its Changelog, with `verified N/N` beside it; refuted plans under a `## Refuted` heading with their issue numbers; the two sign-off lines empty.
- `/plot-release rc` with a `vnext-checklist.md` adds the RC line and the version heading to it in place and keeps its name; with none, it writes `v<version>-checklist.md` as today.
- From the RC line on, the fleet leaves the file alone, so the RC's items and ticks stay as the person left them, and the record of a plan verified during the RC round still lands in its plan.
- The final `/plot-release` renames a `vnext-checklist.md` that carries an `RC:` line to `docs/releases/v<version>-checklist.md`. The next run writes a new `vnext-checklist.md`.
- `vnext` sorts after every `v<digit>` name, so `board.ts:421-422` reads it whenever it exists.

The fleet fills no sign-off line, as `/plot-release` already forbids an agent (`skills/plot-release/SKILL.md:244-246`).

**What stays human.** The fleet delivers nothing new, releases nothing, fills no sign-off, closes no issue and re-runs no plan whose record is current (D11).
