## New defects

1. **HIGH. The person arm keys on a record that a hand edit can remove, so the second approval can fall back to the `pr` arm with no person.** *The second approval is a person's act* routes "a `design` plan with a `Spike approved:` record" through the person arm. *Gating the spike approval* refuses a commit that ADDS the record without a receipt, and says nothing about a commit that removes it. The state gate's model passes a deleted line by design (`rules/state-transition.ts:121-122`, `:140-141`). The `spike-unmerged` refusal itself tells the reader to "remove the `spike` annotation", and a plan-only commit passes the phase gate (`rules/phase-gate.ts:187`). So two plan-only hand edits (the annotation and the record) leave a `Review: pr` plan in `design` with a merged plan PR, and the workflow then approves it through `workflows/approve.ts:252` and `:270-274` with no `--who`, under `PLOT_UNATTENDED=1`, recording `plan-PR #N merged` for a merge that approved only the spike. A second path reaches the same state with no hand edit: `the-fleet-writes-the-design` line 43 commits the spec "onto the plan PR's head branch when one is open", and a person who merges that spec merges the plan PR while the plan is in Design, with no spike record. Both contradict D10 ("Approval stays a person's act"), STORY line 105 (a fleet that approves a plan is out of scope) and DESIGN-phases.md:177. Fix: key the person arm on `phase === 'design'`, which needs no record and covers a Design plan with no spike; or gate the removal of the record as well as its addition.
2. **MEDIUM. `POST /api/approve` decides its agent arm from `Review:` alone.** `packages/board/src/server/approve.ts:306` answers 409 only when `readReview(opts, slug) === 'in-session'`. For a `Review: pr` Design plan with a spike record, a project with an `Approve command` gets an unattended `claude -p /plot-approve` run, which the route starts with `env: {}` (it sets no `PLOT_UNATTENDED`, unlike `deliver.ts:639`). Whether that run refuses then depends on the configured command string, not on the plan. The plan widens the bundle at `entry/approve.ts:480` and not this check. Fix: the 409 reads the same domain answer as the bundle (the person arm), not the raw `Review:` word.
3. **MEDIUM. `approve-spike` has no board-free route and no skill entry, and CLAUDE.md is not amended.** The plan adds `plot-approve-spike.mjs` to `GATED`, so the controller gate refuses it with no receipt. The board-free exit is `plot-state-receipt.sh --unowned-action`, which accepts four actions only (`skills/plot/scripts/plot-state-receipt.sh:240`, `:253-259`), and the script-to-action map at `:175-178` has no entry for the new bundle. No skill names the spike approval: step 2b of `/plot-approve` only reads the annotation. CLAUDE.md *The Master Agent Uses The Controllers* (`CLAUDE.md:499`) lists the actions, bundles and board-free routes, and the plan does not change it, while the sibling `feature/a-draft-can-need-design` amends `:499` for its own controller. Fix: name the skill route, add `approve-spike` to `--unowned-action` and to the map, and amend `CLAUDE.md:499` and the state-gate paragraph that names the three receipt writers.
4. **LOW. The field counts disagree between sections.** The Approach (plan line 41) and the markers slice (line 103) say `PlanMetaSchema` gains five fields: `spike`, `spike_approved_raw`, `slices_confirmed_raw`, `extra_spikes`, `tracer`. The Open Point at line 91 says "four fields" and "the pulse `PlanSchema` gains `type`", which D15 replaced with `tracer` (line 75, line 119).
5. **LOW. Adding a second `plot-approve*` bundle makes a glob ungated.** `scriptNamed` gates a glob only when it matches exactly one `GATED` name (`rules/ci-suite.ts:284-292`). Today `plot-approve*.mjs` matches only `plot-approve.mjs`. After this plan it matches two names, and the gate allows it. Fix: refuse a glob that matches more than one gated name, or name the case in the slice.
6. **LOW. The Changelog over-claims.** Line 17 says approval "always needs a named person, whatever the plan's review channel". The Approach applies this only to a Design plan with a spike record. A reader of the release notes will read it as every plan.
7. **LOW. The person arm overrides `Review: ballot`.** "Whatever its `Review:` field says" includes `ballot`, where today the tally is the approval (`workflows/approve.ts` `ballot` arm, `review-human`). One `--who` then replaces a declared multi-reviewer channel. The plan should say whether a ballot plan keeps its tally.
