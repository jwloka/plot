## Findings

1. **Closed issues go through a port that this repository's open issues do not use.** Must change before approval. The plan puts `issueListClosed` on `Tracker` and lets `trackerNone` answer `unaskable` (plan :36). No production code calls `Tracker.issueList`; the board's open list comes from `plot-host.sh issue-list` (`fleet.ts:1490`), routed by `issueSource` (`rules/issue-source.ts:46-50`), which answers `git-host` when no `Tracker` key is declared. `trackerFor` resolves an undeclared key to `trackerNone` (`tracker-resolve.ts:35-44`). This repository's `## Plot Config` declares no `Tracker`. So here, and in every GitHub or Bitbucket repository that lists issues from its git host, the Open lane fills and the Done lane stays empty forever, and the source of one view splits across two routes that `issueSource` exists to keep as one decision. Bitbucket git-host issues (`pr-refresh.ts:139-145`) have no closed route at all. The plan must route closed issues through the same `issueSource` decision as open ones (a `git-host` arm, or a tracker adapter the undeclared case resolves to). The sibling `the-fleet-verifies-what-it-delivered` (:53, `issueOpen` on the same port) has the same gap and both should resolve it the same way.

2. **The index's writer and miss path contradict the PR-index precedent the plan cites.** Must change before approval. The plan says the fleet writes "as `fleet.ts` is for the PR index today" and that a bad file "makes the board ask the tracker directly, as the PR index does" (plan :38). The PR index is written by fleetd's `pr-refresh.ts` (`CLAUDE.md:483`). The board switches on `fleetOwnsPrs` (`fleet.ts:1617-1622`), not on file validity: with the fleet up it reads the store and asks the host nothing, and a missing file yields `'the fleet has left no PR index to read'` (`fleet.ts:1630-1634`); with no fleet it asks the host into an in-memory overlay and never writes the store (`fleet.ts:1607-1613`, `:1692-1695`). Today `refreshIssues` runs in the board in both modes (`fleet.ts:1688`, `:1703`). The plan must name the process that folds issues (fleetd's `pr-refresh.ts`, by the one-writer rule), say that the board's own issue poll moves or stops under a running fleet, adopt the `fleetOwns` switch rather than "ask on a bad file", and add the closed-issue call to `PR_REQUESTS_PER_REFRESH` (`pr-refresh.ts:181-215`), whose comment requires an issue call to be counted the moment it becomes real (`:161-163`).

3. **The delta cannot see what the plan says it sees, and the full read is not periodic.** Must change before approval. The plan's port asks `closed:>=` / `resolved >= since` (plan :36) but the fold "asks for issues updated after the watermark" (plan :38); no operation in the plan answers *updated since*. A reopened issue loses its closing date and never appears in a closed-since query, so the claim "a closed ticket that reopens moves at the next fold" (plan :38) holds only if the full open list overrides the closed row, which the plan does not state. `DESIGN-index.md:71` and `:87` take the watermark from "the newest `updatedAt` the host RETURNED, never the local clock"; `Issue` has no `updatedAt` (`issue.ts:33-59`) and the plan adds `closedAt` and `open` only. `DESIGN-index.md:167` says "A periodic full read is required, not optional"; the plan reads every closed issue once (plan :38, Open Point :62). The plan must add `updatedAt`, name the delta operation, state the override rule for a reopened issue, and keep the periodic full read or argue against `DESIGN-index.md`.

4. **"Archived" means two things, and the board cannot see D7's archived stories.** Must change before approval. The plan defines `archived` by an `archived:` date and `done` as done without one (plan :54). The domain derives the `archived` standing from "every plan released" (`transitions/story.ts:402`), not from the date, and `archivalIsConsistent` (`entities/story.ts:72-79`) makes `done` without a date the inconsistent, half-archived case — so the plan's Done lane holds exactly the stories the domain calls inconsistent. Story discovery skips `docs/stories/archived/` on both read paths (`board.ts:1746`, `:1758`), so D7's "every archived story in an Archived lane" (story :78) cannot show a story archived by moving it there. The plan must say whether `storyLane` takes `derivedStanding` or the declared status plus date, and whether the board starts reading `docs/stories/archived/`.

5. **`?released=1` is claimed by two tabs.** Must change before approval. The plan keeps the Discovery toggle in `?released=1` (plan :56); the sibling keeps the Planning tab's *Show released* in the same parameter (`the-board-has-three-tabs.md:39`). The tab switch keeps every other parameter (`App.tsx:633-638`), so the two controls become one switch across tabs. D7 calls the Discovery toggle "tab-wide" and D8 makes *Show released* a separate checkbox (story :78-79). Name a separate parameter, or state in both plans that they share it and why.

6. **The plan persists tracker state that the entity and the adapter say must not be mirrored, and drops the fetch's answer.** Must change before approval. `issue.ts:20-23` refuses mirrored tracker state because it is "wrong forever after an outage", and `plot-host.sh:4618-4622` calls "a mirror of tracker state ... the copy that ages into a lie". `CLAUDE.md:487` admits "an issue's state" as an indexed answer, so the estate's texts disagree and this plan is the change that makes them meet; the sibling `the-board-has-three-tabs.md:41` amends the entity doc for its one new field, and this plan adds `closedAt`, `open` and a durable copy without a word. Also, `IssueFetch.answer` (`issue.ts:61-69`) and `issueAbsence` (`fleet.ts:1480-1499`) keep *answered*, *unsupported* and *failed* apart so an empty list never reads as "no issues" (`plot-host.sh:4623-4628`, `CLAUDE.md:481`). The index and the lanes must carry that answer, so a `trackerNone` or failed tracker shows the absence sentence and not three empty lanes.

7. **The lanes read non-terminal rows; the plan should name its exception.** Open Point. `CLAUDE.md:479` reads only terminal rows from the index; an issue's open or closed state is not terminal. The board already renders non-terminal PR rows from the store (`fleet.ts:1624-1647`), and the plan's "the lanes are a view and not a decision" (plan :38) is the same carve-out. The plan should cite that precedent and state that no decision reads a closed issue row from the index.

8. **`namedByPlan` is a boolean, but its source can be unknown.** Open Point. `referencedIssues` returns `null` when the plans cannot be read, and its doc forbids reading that as an empty set (`fleet.ts:1423-1426`). `ticketLane(issue, namedByPlan, now)` (plan :40) has no unknown, so a read failure moves every named GitHub ticket from In progress to Open.

9. **D7 files WONTFIX under Done, which the entity argues against.** Open Point; D7 binds, so this records a cost, not a re-decision. `issue.ts:51-56` leaves `statusCategory` empty for WONTFIX because "filing it as `Done` puts abandoned work beside finished work". The plan files it under Done (plan :52) and calls it a Jira case; the entity names Bitbucket. The slice should update that doc sentence so the entity and the lane rule do not disagree.

10. **Three plans widen `Tracker` and `Issue` with no order between them.** Open Point. This plan's first slice (`issueListClosed`, `closedAt`, `open`), `the-board-has-three-tabs`'s `feature/an-issue-names-its-assignee` (`Issue.assignee`, both connectors) and `the-fleet-verifies-what-it-delivered`'s `feature/a-refuted-claim-opens-an-issue` (`issueOpen`, both connectors, `trackerNone`) edit the same files with no `waits:` between them. If the Delivery tab's *Waiting on you* reads the new index, its rows must carry `assignee`; the plan does not say whether Delivery reads the index or keeps the in-memory list, which would let one ticket show two states on two tabs.

11. **The `waits:` sits on the wrong slice.** Open Point. The first slice touches only the port and connectors (plan :68), but waits on the tab rename; the note (plan :81) gives a reason that applies to the third slice, which renders the Discovery tab. Moving the wait lets the port work start in parallel with Phase 3.

12. **A Jira ticket in the `Done` category without a resolution date.** Open Point. `resolved >= since` never returns it and "closed within 14 days" cannot be computed, so the row `category Done, closed within 14 days` (plan :46) has no answer for it.
