# Cost juror: the-board-has-three-tabs

Position: amend

The plan adds no host or tracker call per scan. The assignee rides on the existing `issue-list` reads, and the payload grows by one short string per ticket. Three costs are not named and not bounded. First, *Only my work* over branches and builds needs an owner fact that no row carries today, and the plan does not say where that fact comes from or what it costs per scan. Second, the browser-test and docs churn of the rename is real and unstated: 47 test files open the old `agents` tab, 3 click buttons named `Agents` or `Plans`, and 24 docs and skill files name the old tabs. Third, the *Active sprint* toggle and the ticket arm of *Only my work* duplicate filters that exist or that this plan builds, so a person maintains two controls for one effect. A smaller design delivers the same Changelog: the toggle selects every Active sprint in the existing multiselect, and the Planning slice folds into the rename slice. Measured on `main` at `316d3de0e`.

## Findings

1. **High — *Only my work* over branches and builds has an unnamed data source and an unbounded cost.** `packages/board/src/app/lib/agent-rows/mine-filter.ts:76-88` states that a row without a PR "names no owner at all" and that a build is owned by "whoever owns the branch, which no fact on the row says"; the branch name is "deliberately not consulted". `packages/domain/src/rules/ownership.ts:43-46` has the kinds `pr`, `agent`, `plan` and `other`, and no `ticket`, `branch` or `build` kind. The plan (*Only my work*, Design) says "branches and PRs (by author)" and "builds (by the branch's owner)" and names no field, no read and no cost. The plausible sources are a `git log` per branch per scan (one spawn per branch, on the scan path), a host call, or the claim ref's author. Each has a different cost and a different failure mode, and the plan chooses none. Checked by reading both files and grepping `schema.ts` for a branch owner field (none; `claimedBy` at `schema.ts:2235` is a slice claim list).
2. **Medium — the *Active sprint* toggle duplicates the existing sprint multiselect.** `AgentList.tsx:540` reads `activeSprints = fleet.sprints`, and the multiselect options at `:589` are built from `activeSprints` only. So "every Active sprint" is already one state of the existing control: all options selected. The plan adds a new rule `activeSprintScope`, a second control, and a second membership computation beside `slugPassesSprintFilter`, which a person then keeps in agreement. Smaller design: the toggle is a shortcut that selects every option of the existing multiselect, with a unit test that the shortcut's selection equals `activeSprints`. Story Open Point 12 (union of several Active sprints) then answers itself.
3. **Medium — the browser-test cost of the rename and the new controls is not named.** `packages/board/test/integration/` holds 63 `*.browser.test.ts` files. 47 test files reference the `agents` tab (`tab: 'agents'` or `?tab=agents`, 20 URL occurrences). Three files click tab buttons by their old names and break on the rename: `agents-tab.browser.test.ts:2116-2119`, `mine-filter.browser.test.ts:325-330`, `unreachable-overlay.browser.test.ts:318-320`. The plan does not say whether the 47 files keep the old value (which then exercises the redirect on every run) or move to the new one (a 47-file diff). It also names no browser test for *Show released*, the *Active sprint* toggle, the inbox's *show every ticket* control or the unmatched-reader notice. CLAUDE.md (*The Layering Rule*) asks for the decision in a unit test and one browser test that proves the state is seen; the plan has unit tests only and no `## Acceptance` section that bounds either kind. Checked with `grep -rl` over `packages/board/test`.
4. **Medium — the docs churn is unbounded.** Slice 1 includes "the docs that name the old tabs". Outside `docs/plans/` and `docs/stories/`, 24 files in `skills/`, `docs/`, `README.md` and `packages/board/src` name `Agents tab`, `Plans tab`, `Stories tab` or an old `?tab=` value; under `skills/` and `packages/board/src` alone that is 49 occurrences in 16 files. The slice states no list and no count, so a worker cannot tell when it is done and a reviewer cannot check it.
5. **Low — the ticket arm of *Only my work* duplicates the *Waiting on you* default.** Tickets render in *Waiting on you* only (`AgentList.tsx:2367`). `waitingTickets` already filters them to the reader by default. *Only my work* over tickets is the same predicate on the same rows, so the section gets two controls for one filter and a person must define what each combination means. The PR and plan arms of *Only my work* already exist (`mine-filter.ts:135` `rowsForReader` by `pr.author`, `:162` `boardForReader` by `Assignee:`), so the Changelog line "*Only my work* also filters … PRs" is mostly true today and the new work is tickets, branches without a PR, and builds.
6. **Low — `planningColumns` builds on the wrong function.** `the-board-draws-the-declared-phases` merged as #1623 (`5d78df1e8`). The board server now builds its columns with `phaseColumns(map)` (`packages/domain/src/rules/workflow-phases.ts:221`, imported at `packages/board/src/server/board.ts:52`). The plan's `planningColumns(map, showReleased)` builds on `planPhases(map)` (`:169`), which answers names without leadership, accent or checklist. Building on `phaseColumns` avoids a second column list. Released plans are already in the payload today, so *Show released* adds no payload.
7. **Low — the host and tracker cost is zero new calls but the plan does not say so.** The GitHub arm adds `assignees` to the existing `gh issue list --json` (`plot-host.sh:4732`); the Jira arm adds `assignee` to `fields=` (`:4696`). No request is added. On GitHub the nested `assignees(first:100)` connection keeps a 100-issue page at about 1 GraphQL point (101 nodes / 100). The payload grows by one login or email per ticket: at most 1000 rows in the issue index (`ISSUE_INDEX_OPEN_LIMIT`, sibling plan `tickets-and-stories-have-lanes.md:73`), about 25 KB. The plan states none of these numbers.
8. **Low — the `ISSUE_INDEX_VERSION` raise has a transition cost.** Whichever of this plan and `feature/the-fleet-indexes-issues` (unmerged, `origin/feature/the-fleet-indexes-issues`) lands second raises the version. A store at the old version then reads as no index until the next fleet pass, which the sibling bounds at up to 22 minutes on a 1000-ticket Jira project (`tickets-and-stories-have-lanes.md:118`). During that window *Waiting on you* shows *the fleet has left no issue index to read* (`:232`). The plan does not name this window.
9. **Low — the shell cost is bounded.** The new keys fit on existing `jq` projection lines (`plot-host.sh:4710-4717`, `:4735-4736`), so `scripts/check-shell-lines.sh pr` can pass at net zero. The slice states the count after the fact; a target of 0 is stated nowhere.
10. **Low — five fleet agents for a change of moderate size.** Wave 1 has one slice, wave 2 three, wave 3 one. `feature/the-planning-tab-shows-design-to-testing` touches `App.tsx` and the Planning view that slice 1 renames, and it is a filter over one column plus a URL parameter. It can ride in slice 1 and save one agent and one review.

Facts checked and true on `main`: `App.tsx:118` `type Tab`; `parseTab` is at `:123` (the plan says `:122`, the doc comment); `App.tsx:633-638` keeps every parameter on a tab switch; `issue.ts:21-23` the refusal; `tracker-shell.ts:46` `issueOf`, `:120` `trackerReads`; `plot-host.sh:4684` `assignee = currentUser()`, `:4696`, `:4732`; `sprint.ts:9` `Active`; `mine-filter.ts:119` `readerFrom`, `:162` `boardForReader`; `sections.ts:25` the groups. The plan's path `lib/agent-rows/mine-filter.ts` is relative to `packages/board/src/app/`.
