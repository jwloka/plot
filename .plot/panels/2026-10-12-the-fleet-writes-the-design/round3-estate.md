# Estate juror, round 3: the-fleet-writes-the-design

Position: amend

I read the plan against `main` at `1ad9a9f4f`. The revision applies all seven round-2 moderation amendments and D34, and almost every file, function and line number it names exists and behaves as stated. The spike slice is sound and can be approved as it stands. The extraction of `rules/fleet-run.ts` and `shared/fleet-run.ts` removes the undeclared duplicate of round 2. Four defects remain through the estate lens, and the new text causes three of them. First, the refusal order of `specStart` puts the host reading (`host-unknown`) before the local refusals, and the domain takes readings as values, so fleetd must call `prState` on every pulse for each Design plan that waits, not once per run. Second, the *Working* row of a going spec run has no renderer: `the-board-has-three-tabs` builds a plan-level row in *Waiting on you* only. Third, `plot-design.mjs restart` writes the store that fleetd also writes, and the store's update is atomic only inside one process. Fourth, the open draft spec PR reaches the Delivery tab as a planless PR row that names the plan `<slug>-spec`, and the Board impact comment does not say so. Each fix is small, so the position is amend.

## Findings

1. **high: the refusal order makes the declined check a host call on every pulse, not once per run.** Evidence: the plan orders `specStart` as `off`, `running`, `declined`, `host-unknown`, `halted`, `stopped`, `waiting`, `queue-unread`, `no-free-agent`, `starved` (plan line 52). The domain takes readings as values (CLAUDE.md, *A note on shape*), so the caller must read `host.prState('idea/<slug>-spec')` before it calls `specStart` whenever the answer can reach `host-unknown`, that is, on every pass where the plan is `write-spec`, not running and not declined. The pass runs once per pulse: `fleetAutoWrites` calls `runAutoVerifyPass` after every scan (`packages/fleet/src/shared/auto-writes.ts:28-59`). A Design plan that waits 60 s or 120 s under `retryVerdict` (`packages/domain/src/rules/auto-deliver.ts:74-112`), or that waits for hours on `no-free-agent` or `starved`, therefore costs one `prState` per pulse. The cost paragraph (plan line 102) and the Acceptance (*"one pass reads `prState` once"*) count one read per run. `verifyStart` has no host reading at all (`packages/domain/src/rules/auto-verify.ts:164-179`). Checked: read `verifyStart`, `fleetAutoWrites` and the plan's order.
2. **medium: no sibling builds the *Working* row of a going spec run.** Evidence: Changelog item 5 and the Board impact comment say a going run shows in *Working* "through the plan-level row kind that `the-board-has-three-tabs` builds for the verification row". So the slice *The spec rows* must add a mapper over `fleet.design` and a plan-level path into the *Working* section itself. The slice text says it renders "through the plan-level row kind" that the sibling builds, which is true for *Waiting on you* only. Checked: the sibling plan's slice and Approach text, `AgentList.tsx:475`, `:1090`, `:1123`.
3. **medium: `plot-design.mjs restart` is a second writer of a store whose update is atomic only inside one process.** Evidence: `updateVerifyState` reads, changes and writes "in one synchronous step, so no other callback of this process writes between the read and the write" (`packages/fleet/src/shared/auto-verify.ts:183-205`); the temp file is named by pid and renamed. A restart that lands between fleetd's read and its rename is lost with no error, or fleetd's settlement is lost.
