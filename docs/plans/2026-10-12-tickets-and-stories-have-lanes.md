# Tickets and stories have lanes

> The Discovery tab shows the tag cloud, a tickets lane group (Open, In progress, Done) and a stories lane group (Draft, Active, Done), with one toggle that adds archived stories and every closed ticket. The tracker port lists closed issues from the source `issueSource` names, fleetd folds open issues and the last 14 days of closed issues into an issue index on a gate of its own, and the board reads the index.

## Motivation

D7 in [the story](../stories/plot-works-in-five-phases/STORY-plot-works-in-five-phases.md) puts tickets and stories, the two subjects of Discovery, side by side. Measured on `main` at `75f093cb9`, 2026-10-12:

- `packages/board/src/app/components/StoriesTab.tsx` groups stories as Draft, Active, Done and Archived, with Archived behind a toggle and a TF-IDF tag cloud from `packages/board/src/server/topics.ts`. `COLUMN_OF` (`StoriesTab.tsx:30-38`) decides the grouping in the component.
- The board reads open issues through `plot-host.sh issue-list` (`fleet.ts:1490` `hostSaid`), after `issueSource` (`rules/issue-source.ts:46-66`) decides between `tracker`, `git-host` and `nobody`. This repository declares no `Tracker` key, so its issues come from the git host. The `Tracker` port's `issueList` (`ports/tracker.ts:108`) has no production caller; the one production use of the port is `statusWrite` (`board/src/server/entry/issue-status.ts:133`). `trackerFor('')` resolves to `trackerNone` (`adapters/tracker/tracker-resolve.ts:35-44`).
- `plot-host.sh issue-list` (`:4617`) asks for open issues only. Its GitHub arm derives `statusCategory` from the state it asks for and gives every open issue `To Do` (`:4730-4736`). Its Bitbucket arm parses `bb issue list --state new --state open` (`:4758`), which prints no date and no assignee. Its Jira arm scopes the default query to `assignee = currentUser()` and, where `Ticket prefixes` is declared, to those projects, and reads one page (`:4652-4697`). With no `Ticket prefixes` the project clause is empty (`:4674-4684`), so the person clause is the only scope; `tracker_projects` (`:2480-2484`) records a shared instance that showed another customer's ticket.
- `Issue` carries `status` and `statusCategory` (`entities/issue.ts:44-58`) and no closing date.
- The board's open list is capped at 50 (`fleet.ts:190` `ISSUE_LIMIT`), and the payload drops every ticket a plan names (`fleet.ts:1577`). Measured 2026-10-12 on this repository: 108 open issues, 194 closed, and 154 of the 194 (79 %) closed in the last 14 days.
- `refreshIssues` (`fleet.ts:1472`) runs in the board on the 60 s PR gate, with and without a fleet (`fleet.ts:1688`, `:1703`), and keeps the result in memory. Under a fleet that call runs outside `PR_REQUESTS_PER_REFRESH` (`fleet.ts:1648`). The PR index writer is fleetd's `packages/fleet/src/shared/pr-refresh.ts:1281`, reached from `fleetPrs` (`packages/fleet/src/shared/fleet-clock.ts:149`, built at `registryd-main.ts:2014`) in `plot-registryd`. No index holds an issue.
- `setStoryStatus` writes `archived:` on every move to `done` (`transitions/story.ts:216-218`, refusal `archive-date-missing` at `:270`). The story-tracking skill archives a story by `git mv` into `<home>/archived/` (`skills/story-tracking/SKILL.md:135-160`). The board reads the story home from the `Story directory` key, `docs/stories/` by default (`board.ts:1846`), and skips its `archived/` directory (`board.ts:1746`, `:1758`), which holds 6 stories here.
- `App.tsx:633-638` keeps every query parameter on a tab switch.

## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §5, *Discovery*. The lanes are a view: no decision reads the issue index, and the board renders its open and closed rows as it renders non-terminal PR rows from the PR store (`fleet.ts:1624-1647`).

**The issue source decides, and the port follows it.** A new resolver `trackerForIssues(declared, gitHost, context)` in `adapters/tracker/tracker-resolve.ts` reads `issueSource`: `tracker` resolves to `trackerFor(declared)`, `git-host` resolves to a new read-only implementation `trackerGitHost`, and `nobody` resolves to `trackerNone` with the source's reason. `trackerGitHost` is built from `trackerReads` (`tracker-shell.ts:120-170`) with the git host's backend word (`github`, `bitbucket`) as its connector tag, so it lists through `plot-host.sh issue-list` as the GitHub and Jira connectors do, and its `limit()` reports the `host` connector's own bucket: it spends the git host's budget and opens no second one. It answers `unaskable` on `statusWrite`, so a repository that declared no tracker gets no tracker write. `trackerFor` and `statusWrite` do not change.

**The port doc changes with it.** `ports/tracker.ts:66-72` says a tracker is not a git host and keeps `unaskable` for a repository that declared no tracker, `:103` and `:114` return `unaskable` there, and `CLAUDE.md` *The Layering Rule* says such a repository gets `trackerNone`. The first slice rewrites the three: a repository that declared no tracker reads its issues from its git host through `trackerGitHost`, as `issueSource` decides, and answers `unaskable` on every write; `trackerNone` answers the `nobody` source; the `@returns` lines say `unaskable` where the issue source is `nobody`. The `CLAUDE.md` sentence changes the same way, and `AGENTS.md` follows through `./scripts/check-agents-md.sh --write`.

**Closed issues on the port.** `Tracker` gains `issueListClosed(since, limit)`, which lists issues closed at or after `since`, newest first, without bodies. `Issue` gains `closedAt: string | null`, the tracker's own closing time; `null` on an open issue and on a closed issue whose tracker states no date. No `open` field is added: a row's openness is the list that returned it. `plot-host.sh issue-list` gains `--state open|closed` (default `open`) and `--since <iso>`:

| Source | Closed read | `closedAt` |
|---|---|---|
| GitHub | the open arm with `gh_state=closed`, `--search "closed:>=<since>"` and `closedAt` in `--json`, `--limit <n>` | `closedAt` |
| Jira | `project IN (<Ticket prefixes>) AND resolved >= "<since>"`, with today's assignee clause until *The Jira project scope* below drops it, `ORDER BY resolved DESC`, `nextPageToken` loop to `<n>` | `resolutiondate` |
| Bitbucket | exit 4: `bb issue list` prints no closing date | — |

The Jira closed read requires `Ticket prefixes`: with none declared it exits 4 with the reason, because an unscoped `resolved >=` query reads the whole instance (`plot-host.sh` `tracker_projects`). `PLOT_JIRA_JQL` overrides the inbox read only, and the closed read does not read it. A read that returns `<n>` rows reports `complete: false`. Each arm records one budget call per page: the GitHub arm records one `budget_record_call` per 100 rows past the first, because the `gh` wrapper records one call per process (`plot-host.sh:3382-3388`), and `jira_curl` records each page itself (`:2648`).

**The open list.** The fold asks for every open issue up to `ISSUE_INDEX_OPEN_LIMIT = 1000`, with the GitHub page loop and per-page record above and a Jira `nextPageToken` loop, and reports `complete: false` at the limit. Planned tickets stay in the index; the inbox filter (`fleet.ts:1577`) moves to the board's read, so the Delivery tab's *Waiting on you* keeps today's content and the Discovery lanes get the planned tickets.

**The issue index.** fleetd writes the issue index; the board never writes it.

- **Writer.** `fleetIssues(world, state, warn)` in a new `packages/fleet/src/shared/issue-refresh.ts` runs the pass `refreshIssueIndex`. The fleet clock runs it beside `fleetPrs` (`fleet-clock.ts:149`), and `registryd-main.ts:2014` builds both. Its `IssueWorld` holds the tracker from `trackerForIssues`, the `issueSource` reading, the issue index store, and the PR state, whose backoff it shares (*Cost* below). `PrWorld` (`pr-refresh.ts:106-119`) does not change. A failure of one pass does not blank the other. A test `packages/fleet/test/unit/one-issue-index-writer.test.ts` asserts one caller of the encoder, in the shape of `one-pr-index-writer.test.ts`.
- **Shape.** `entities/issue-index.ts` exports `IssueIndexSchema`, `decodeIssueIndex`, `encodeIssueIndex` and `ISSUE_INDEX_VERSION`. One file per repository, `.plot/state/index/issues.json` under the common git dir. The name never matches a PR index file, which is `<connector>.json` (`pr-index-file.ts:31`). `PLOT_ISSUE_INDEX_HOME` overrides the directory, and `scripts/owned-run.sh` sets it beside `PLOT_PR_INDEX_HOME` (`:246`). The file holds `v`; `source`, the `issueSource` answer the pass read (`tracker` with its scheme, `git-host` with its backend, or `nobody` with its reason); `at`, the time of the last answered open read; the last pass's `answer` (`answered`, `unsupported`, `failed`) with its reason and `failedAt`; the open rows with `complete`; the closed rows with `since`, `complete` and the closed read's own answer; and, for a Jira source after *The Jira project scope*, the `inbox` rows. A `Tracker: github-issues` repository and a git-host GitHub repository both write `issues.json`; their `source` tells them apart. A `nobody` source writes the file with `answer: unsupported`, its reason and no rows.
- **Fold.** Each answered pass replaces the rows whole: the open list, and the closed issues since `at − 14 days`. Nothing is a delta, so there is no watermark, no `updatedAt` and no separate periodic full read: every pass is the full read of both bounded sets. A ticket that reopens leaves the closed set and enters the open set at the next pass.
- **A failed pass.** It keeps the previous rows and their `at`, and records `answer: failed`, `failedAt` and the reason, as `refreshIssues` keeps its last good list today (`fleet.ts:1466-1470`). `at` moves only on an answered read, as `askedAt` does in `CLAUDE.md` *A Decision Reads The Index*. The lanes then draw the kept rows under one line, *The last ticket read failed at <failedAt>: <reason>. Showing tickets read at <at>.* A failed pass with no kept rows shows that line in place of the lanes. A closed read that fails or answers `unsupported` while the open read answered leaves Open and In progress drawn and puts its own sentence in Done.
- **Cost.** The fold runs on its own gate and is priced apart from the PR refresh. `issueIntervalMs(pages)` in `packages/domain/src/rules/cadence.ts` answers `max(ISSUE_REFRESH_MS, pages × ISSUE_PAGE_MS)`, both 120 000 ms, where `pages` is the request count of the last pass. So the fold spends at most 30 requests an hour on any repository and source. On this repository one pass reads 2 open pages (108 issues) and 2 closed pages (154 closed in 14 days): 4 requests, a pass every 480 s, 30 GitHub requests an hour. `PR_REQUESTS_PER_REFRESH` (`pr-refresh.ts:181`) then prices `pr-list` alone: `github` stays 1, and its comment says that the issue reads run on their own gate and no longer ride the unit; `bitbucket` falls from 4 to 3, because `bb issue list` leaves the PR refresh. The PR pass subtracts the fold's derived spend, `pages × 3 600 000 / interval` an hour, from the observed rate it reads at `pr-refresh.ts:1341`, before `othersPerHour` (`cadence.ts:97-101`), so the fold does not stretch the PR cadence. Today the board's own `issue-list` call under a fleet runs every 60 s outside the table, 60 requests an hour that the cadence counts as another spender; that call stops. Per machine on a quiet account: GitHub spends 60 (PR) + 60 (board `issue-list`) = 120 requests an hour today, and 60 + 30 = 90 after; Bitbucket spends 60 + 60 = 120 today and 60 + 30 = 90 after. A Jira source spends the Jira account under the same bound, at most 30 requests an hour per machine with the D20 reads and the D23 inbox page included; `budget_record_jira` records each page, and the git-host cadence does not read it. The cost is freshness: tickets refresh every 120 s to 480 s here, where the inbox refreshed every 60 s.
- **Backoff.** A git-host issue read that the host refuses with a rate limit sets the PR state's backoff (`prNextAt`, `prNextIsBackoff`), and the issue gate stays shut while that backoff holds, because both spend one account. A Jira refusal backs off the issue gate alone.

**The board's read.** The board follows the PR store's switch, `fleetOwnsPrs` (`fleet.ts:1619`), and not the file's validity. With a fleet, its periodic refresh reads the issue index and asks the host nothing; a missing file, or a file whose `source` differs from the board's own `issueSource` reading, shows *the fleet has left no issue index to read*, as `readPrsFromStore` does (`fleet.ts:1636`). With no fleet, `refreshIssues` reads the same rows into memory on the same `issueIntervalMs` gate and backoff, kept on `CacheEntry` as `issueNextAt`, and writes no file. In both modes `refreshIssues` and the fold call `trackerForIssues(…).issueList(ISSUE_INDEX_OPEN_LIMIT)` and `.issueListClosed(since, ISSUE_INDEX_OPEN_LIMIT)` in place of `hostSaid(['issue-list', …])` (`fleet.ts:1490`), so one shell op has one route. The inbox (`entry.issues`) and the lanes come from the same rows, so one ticket cannot show two states on two tabs. A `nobody`, `unaskable` or `failed` answer with no rows reaches the lanes as `issueAbsence` text, never as three empty lanes.

**The payloads.** The lanes' open and 14-day closed rows ride the board payload (`/api/board`, polled every 30 s, `App.tsx:31`), without bodies, at most 1000 of each. The 4 s `/api/fleet` payload (`App.tsx:32`) carries only the inbox: the rows that pass the inbox filter, newest first, capped at `ISSUE_LIMIT` (50) as today. No closed row rides `/api/fleet`.

**The toggle's closed read.** With the toggle on, the tab asks `GET /api/issues/closed`, which calls `trackerForIssues(…).issueListClosed(null, 1000)`. The tab asks once when the toggle turns on and once on a page load with `?archived=1`, and never on a poll. The board keeps the answer for the issue gate's current interval and serves it to every tab in that time, and while the issue gate's backoff holds it serves the kept answer, or the backoff's reason, and asks nothing. The answer is not written to the index. D19 decides this retention: the index holds the open tickets and the tickets closed in the last 14 days, and the toggle reads every closed ticket from the host on demand, capped at 1000.

**The Jira project scope (D20, D23).** The Discovery lanes show every Jira ticket of the `Ticket prefixes` projects. In `feature/the-lanes-read-the-whole-jira-project`:

- **The lanes read.** The Jira open read and the closed read drop the clause `assignee = currentUser()` and keep `resolution = EMPTY` and the project scope. The project-wide read requires `Ticket prefixes`: with none declared, the open read keeps today's query byte for byte, the closed read exits 4 as above, and the lanes show the reader's own open tickets under the sentence *`Ticket prefixes` is not declared, so only your own Jira tickets are shown.* So no read without a person clause leaves the declared projects.
- **The inbox read (D23).** A Jira pass makes one more read, today's query `assignee = currentUser() AND resolution = EMPTY<scope> ORDER BY created DESC`, one page of 50, and the index holds its rows as `inbox`. `PLOT_JIRA_JQL` overrides this read, as its doc says it overrides the inbox, and not the lanes read. Before this slice the open read is today's query, so `inbox` is absent and the board takes the inbox from the open rows.
- **The Delivery inbox.** *Waiting on you* reads the project-wide rows filtered by `Issue.assignee` only for a reader whose handle carries a `jira:` spelling in `People` (D21). An unmatched reader on a Jira source sees the `inbox` rows, today's content, with no notice: D22's *every ticket and a notice* applies to GitHub and Bitbucket sources only (D23). So no Jira adopter's inbox widens at upgrade. The filter belongs to `feature/the-delivery-tab-filters-by-sprint-and-owner` of `the-board-has-three-tabs`, and this slice waits on it.
- **The docs.** `skills/plot-board-setup/SKILL.md:229-231`, `skills/plot-init/SKILL.md:205-208` and `plot-config.sh:180-183` say that an undeclared `Ticket prefixes` keeps the instance-wide query. They change to: an undeclared key keeps today's person-scoped inbox, and the project-wide lanes and the closed read need the key.

**The ticket lane.** `ticketLane(issue, reading, now)` in `packages/domain/src/rules/ticket-lane.ts` answers `open`, `in-progress`, `done` or `hidden`. `reading` holds `categoryStated` and `namedByPlan`. `categoryStated` is true only for the `jira` source: the GitHub and Bitbucket arms derive a category from the state they ask for, and D7 places those trackers under "no category". So `ticketLane` ignores a derived category.

| Ticket | Lane |
|---|---|
| category stated `To Do` | Open |
| category stated `In Progress` | In progress |
| category stated `Done`, `closedAt` within 14 days | Done |
| category stated `Done`, `closedAt` null or older | hidden; Done with the toggle on |
| category not stated, open, `namedByPlan` false | Open |
| category not stated, open, `namedByPlan` true | In progress |
| category not stated, closed, `closedAt` within 14 days | Done |
| category not stated, closed, `closedAt` older | hidden; Done with the toggle on |

Jira states a category for every status, so the category decides a resolved Jira ticket (D7): one resolved in a `To Do`-category status reads Open. `namedByPlan` comes from `referencedIssues` (`fleet.ts:1427`). When the plans cannot be read it answers `null`, and the ticket lane group shows *plans could not be read* and keeps its last good lanes, as `refreshIssues` does at `fleet.ts:1567-1574`.

**The Done lane (D24).** `doneTickets(rows, expanded)` in `ticket-lane.ts` orders the Done rows by `closedAt`, newest first, with a `null` date last, and answers the first `DONE_LANE_LIMIT = 20` and the count of the rest. The lane draws them and a *show all done (<n> more)* link, which draws every Done row: the 14-day rows with the toggle off, and every closed ticket the toggle read with it on. The link's state is per view and is not kept in the URL. On this repository the Done lane draws 20 of 154 rows.

**The story lane.** D7 names three lanes and their statuses; D12 makes the board's groupings come from the declared map. `storyLane(standing, location)` in `packages/domain/src/rules/story-lane.ts` answers D7's lane for a story; `storyLanes(map, stories)` returns D7's lanes in D7's order, restricted to a lane that holds a status `phaseOfStory(map, status)` (from `the-phases-are-declared`) places in a phase, or that holds a story:

| Story | Lane |
|---|---|
| under `<Story directory>/archived/` | Archived (toggle on only) |
| standing `draft`, `ready`, `paused` | Draft |
| standing `active`, `in-review` | Active |
| standing `done`, or derived standing `archived` | Done |

Archived means the location: a story moved under `<Story directory>/archived/`, as the story-tracking skill archives one. `standing` is `derivedStanding` (`transitions/story.ts:397`), which the board already reads (`board.ts:1695`), so `COLUMN_OF` moves into the domain. The derived standing `archived` (every plan of the story released, `transitions/story.ts:402`) is not a `StoryStatus` (`entities/story.ts:15`), so no map declares it: `storyLane` reads it as `done`, and so does the map lookup. A story with `status: done` and an `archived:` date still in the live directory is Done, because the controller writes the date on every move to `done` (`transitions/story.ts:216-218`). A story whose status no declared phase holds still shows in its D7 lane, because the Discovery tab lists every story whatever phase holds it (the spec's default for story Open Point 3, `the-phases-are-declared` Open Point 3); the map decides only which empty lanes are drawn. The board reads `<Story directory>/archived/*/STORY-*.md`, with the directory from the `Story directory` key (`board.ts:1846`), into a separate `archivedStories` list on the board payload; the story filter of the Planning tab keeps skipping them (`board.ts:1746`, `:1758`).

**The Discovery tab.** The tag cloud stays on top. Below it, the tickets lane group and the stories lane group render as separate lane groups. One tab-wide toggle, off by default, adds the Archived story lane and every closed ticket. The tab keeps it per viewer in `?archived=1`, a parameter of its own, and reads no other parameter for it: `App.tsx:633-638` keeps every parameter on a tab switch, so sharing `?released=1` with the Planning tab's *Show released* would make D7's and D8's two toggles one. A lane group whose fetch answered `unsupported` or `failed` with no kept rows shows the absence sentence.

**Every view state is a domain property.** Which lane a ticket and a story take, which story lanes the map draws, which Done rows show, and what the toggle adds come from `ticketLane`, `doneTickets`, `storyLanes` and `storyLane`, with one unit test per table row. The components render them.

**Entity text.** `entities/issue.ts:20-31` names `closedAt` as a read beside `status`, and states that the issue index is a cache of one fetch, replaced whole each answered pass and stamped with `at`, not a mirror Plot edits. Its WONTFIX sentence (`:51-56`) states that the lane places an uncategorised closed ticket in Done by D7.

**The shell lines.** `scripts/check-shell-lines.sh` refuses a change that grows the shipped shell. The first slice's new arms are paid for by these lines in `plot-host.sh`: the `nobody` preamble, copied in `issue-list` (`:4642-4649`) and `issue-view` (`:4831-4835`), becomes one `issue_source_or_exit`; the `gh` failure block, copied at `:4737-4745` and `:4863-4874`, becomes one helper; the GitHub closed read reuses the open arm's `gh_state` (`:4730`) and adds no arm; and the Jira open and closed reads share one `jira_search_pages` loop in place of the single-page call at `:4693-4698`. The D20 slice pays for its inbox read the same way inside the Jira arm. The PR of each slice states the net count that the gate printed.
