# The board has three tabs

> The board's tabs Stories, Plans and Agents become Discovery, Planning and Delivery, the old `?tab=` values redirect, the Planning tab shows plans from Design to Testing with a *Show released* checkbox, and the Delivery tab filters its tickets by assignee, selects the Active sprints in one step, and shows a failed verification in *Waiting on you*.

- **Type:** feature
- **Story:** plot-works-in-five-phases
- **Review:** pr
- **Rounds:** 1
- **Impl:** own branches

## Changelog

- The board's tabs are Discovery, Planning and Delivery. `?tab=stories`, `?tab=plans`, `?tab=board` and `?tab=agents` redirect to the new tab, so existing bookmarks keep working.
- The Planning tab shows plans in Design, Development and Testing. A *Show released* checkbox, off by default, adds Released plans.
- The Delivery tab's *Waiting on you* shows only the tickets assigned to you by default, and says how many tickets it hides, with a control that shows every ticket. On GitHub and Bitbucket a reader the board cannot match, or a source that states no assignee, sees every ticket and a sentence that names the reason; on Jira a reader whose `People` entry names no `jira:` account sees the tickets Jira assigns to them, as today.
- *Only my work* also filters tickets: it hides a ticket assigned to somebody else. It filtered PRs by author and plans by `Assignee:` before this plan, and it still shows a branch without a PR and a build, because neither names an owner.
- An *Active sprint* button in the Delivery tab's sprint filter selects every Active sprint.
- A failed or stopped verification run shows in *Waiting on you* with its reason, its log and its restart command, and a fleet that the 3-failure guard halted says so there.

## Motivation

D6, D8 and D9 in [the story](../stories/plot-works-in-five-phases/STORY-plot-works-in-five-phases.md) name the tabs after the work each one shows. Measured on `main` at `c7186b7be`, 2026-10-13:

- `packages/board/src/app/App.tsx:118` declares `type Tab = 'stories' | 'plans' | 'agents'`, and `parseTab` (`:123`) redirects `?tab=board` to `plans`. The tab decision is made in the component and has no domain test. Fourteen more `App.tsx` sites name a tab value: `:349`, `:367`, `:378`, `:584`, `:613`, `:637`, `:644`, `:683-685`, `:764`, `:814`, `:953`, `:974`, `:989-991` and the labels at `:1045-1047`.
- The Plans tab draws one column per declared phase that holds a plan state, four with the default map (`phaseColumns`, `packages/domain/src/rules/workflow-phases.ts:221`, built on the server at `packages/board/src/server/board.ts:2332`). It has a sprint filter, a story filter, *Story lanes* and *Only my work* (`packages/board/src/app/lib/agent-rows/mine-filter.ts:162` `boardForReader`).
- The Agents tab (`components/AgentList.tsx`, 2533 lines) groups rows into the six sections of `lib/agent-rows/sections.ts:25`. *Waiting on you* holds unplanned tickets, broken agents and Draft plans with no branch (`AgentList.tsx:1123`, `:2367`). Its sprint multiselect lists `fleet.sprints` (`AgentList.tsx:540`, `:589`), which holds only the Active sprints (`packages/board/src/server/fleet.ts:6340` `activeSprints`), and filters rows through `slugPassesSprintFilter` and `rowIsSprintExempt` (`lib/filters.ts:283`, `:329`).
- *Only my work* already filters PRs by author (`mine-filter.ts:135` `rowsForReader`) and plan cards by `Assignee:` (`:162`), both through `isMine` (`packages/domain/src/rules/ownership.ts:135`). `OwnedRow` (`ownership.ts:42-46`) reads an issue, a build and a branch with no PR as `other`, which names no owner, and `mine-filter.ts:73-86` refuses to guess a branch's owner from its name.
- `Issue` carries no assignee by stated design (`packages/domain/src/entities/issue.ts:21-23`). The board does not read tickets through `issueOf`: `refreshIssues` (`fleet.ts:1474`) parses `plot-host.sh issue-list` by hand (`:1536-1561`) into `IssueRowSchema` (`packages/board/src/contract/schema.ts:3368`), whose doc (`:3321`) says *No labels, no assignee*. On this repository 127 open issues carry 0 assignees (`gh issue list --state open --json assignees`, 2026-10-13).
- `/api/fleet` carries `verification` (`schema.ts:4427`, `VerificationStatusSchema` `:3973`, `fleet.ts:6769` `verificationPayload`) since #1635, and nothing under `packages/board/src/app` reads it. Issue #1640 tracks the missing row.
- The reader is a git host login, a git email and the `People` directory (`mine-filter.ts:119` `readerFrom`).

## Design

### Approach

The design spec is [DESIGN-phases.md](../stories/plot-works-in-five-phases/DESIGN-phases.md) §5.

**The tab is a domain answer.** A new rule `boardTabOf(param)` in `packages/domain/src/rules/board-tab.ts` returns the tab and, for an old value, the new value to redirect to: `stories` to `discovery`, `plans` and `board` to `planning`, `agents` to `delivery`. An absent or unknown value answers `planning`, as `plans` is the default today. `App.tsx` calls it in place of `parseTab` and replaces the URL silently, as `parseTab` does today; every other `App.tsx` site above takes the new value, and `revealBranch` (`:683-685`) writes `?tab=delivery`. The tab names are fixed (D6). The Discovery tab renders today's `StoriesTab` until `tickets-and-stories-have-lanes` rebuilds it.

**The Planning tab.** `PhaseColumn` (`workflow-phases.ts:201`) gains `releasedOnly: boolean`, true for a phase whose only plan state is `released`; `phaseColumns` sets it beside `checklist`. `planningColumns(columns, showReleased)` in `workflow-phases.ts` drops a `releasedOnly` column unless `showReleased` is on. It runs in the client over the payload's `board.columns`, because *Show released* is per viewer and Released plans already ride the payload; the server and the payload do not change. With the default map it answers Design, Development and Testing, and Released with the checkbox on. A custom map (D12, D26) that puts `plan:released` in a phase with another plan state keeps that column drawn whole, so the checkbox never hides a Delivered plan. The sprint filter, the story filter, *Story lanes* and *Only my work* stay. *Show released* is off by default and is kept in the URL (`?released=1`), as `DESIGN-phases.md` §5 states. `?released=1` belongs to the Planning tab alone: the Discovery tab's toggle uses `?archived=1` (`tickets-and-stories-have-lanes`), because `App.tsx:633-638` keeps every parameter on a tab switch and one shared parameter would make two toggles one.

**The assignee.** `Issue` gains `assignees: string[]`, the tracker's own logins or accounts, `[]` where the tracker states none. A list and not one string, because a GitHub issue carries several assignees; a ticket is the reader's when any element resolves to the reader. It is a read, under the reasoning that admitted `status` and `statusCategory` (`issue.ts:25-31`): Plot reads it and never writes it. The status write's refusal to widen (`ports/tracker.ts:31-41`) is about writes and does not change. The value comes from the `plot-host.sh issue-list` arms: the GitHub arm adds `assignees` to its `--json` list (`:4732`) and `[.assignees[].login]` to its `jq` projection; the Jira arm adds `assignee` to `fields=` (`:4696`) and projects its `emailAddress`, or its `accountId` where Jira hides the email. The Bitbucket arm is unchanged: `bb issue list` prints no assignee (`plot-host.sh:2132`), and an absent key reads as `[]`. Each new key goes on an existing line, so the slice adds no net shell lines (`scripts/check-shell-lines.sh pr`).

**The assignee's path to the board.** The slice routes the field through every path that reaches *Waiting on you*, and waits on the spike `feature/the-fleet-indexes-issues` of `tickets-and-stories-have-lanes`. After that spike, two paths exist: under a fleet the board reads the inbox from `issues.json`, which the fold writes through `trackerReads`/`issueOf` (`adapters/tracker/tracker-shell.ts:46`, `:120`); with no fleet `refreshIssues` keeps its hand projection until `feature/the-index-holds-closed-issues` moves it onto `trackerForIssues`. So the slice extends `issueOf`, `IssueIndexSchema` with a raised `ISSUE_INDEX_VERSION`, the board's projection from an index row into `IssueRow`, `refreshIssues`' projection (`fleet.ts:1536-1561`) and `IssueRowSchema` with its doc (`schema.ts:3321`). Why this and not a wait on the later lanes slices: `IssueRowSchema` is the wire row on every path and needs the field anyway, and a wait on `feature/the-index-holds-closed-issues` would hold the Delivery tab behind four lanes slices for a projection of six lines. Why the wait on the spike: it makes the index change unconditional, and the spike is claimed (`930cb07d7`) while this plan is a Draft.

**The ticket owner.** `OwnedRow` in `rules/ownership.ts` gains `{ kind: 'ticket'; assignees: string[]; source: 'github-issues' | 'bitbucket' | 'jira' }`, and `ownership` answers it through `ticketOwnership`. No parallel resolver exists beside `prOwnership` and `planOwnership`.

- **GitHub and Bitbucket.** Each assignee is a host login, as a PR author is, so the arm compares it to the reader's host login through `resolvePerson` (`entities/person.ts:43`) as `prOwnership` (`ownership.ts:66-72`) does: `mine` when any assignee resolves to the reader, `theirs` when every assignee resolves to another person. An undeclared login resolves to itself, so a GitHub reader owns their own tickets with no `People` entry, as they own their own PRs today.
- **Jira.** An assignee is a Jira email or account ID, which `People` names as a spelling `jira:<value>` (D21; `parsePersonDirectory` at `person.ts:75` already reads it as a spelling of the handle). `mine` when a `jira:` spelling of the reader's handle names any assignee, `theirs` when a `jira:` spelling of another handle names it, `unknown` when no handle declares it, as `planOwnership` (`ownership.ts:82-89`) treats an undeclared spelling.
- **An unassigned ticket.** An empty `assignees` answers `unknown`, as an empty PR author does. `isMine` keeps it, so *Only my work* shows an unassigned ticket and hides only a ticket assigned to somebody else. The inbox default below is stricter, because D9 shows "only tickets assigned to the current user"; it hides the unassigned ticket and counts it.

**Waiting on you.** The section keeps today's content: tickets, broken agents and Draft plans with no branch. `waitingTickets(issues, inbox, reader, source, showAll)` in `packages/domain/src/rules/waiting-tickets.ts` answers `{ tickets, hidden, notice }`. `inbox` is the index's `inbox` rows, which a Jira source holds after `feature/the-lanes-read-the-whole-jira-project`; before that slice, and on every other source, it is absent and the open rows are the inbox. The section renders the answer; the components decide nothing.

- **A matched reader** sees the tickets whose `ticketOwnership` is `mine`, and `hidden` counts the rest, for example *127 tickets are not assigned to you — show every ticket.* On this repository that reader sees 0 tickets and the count 127, so nothing is hidden silently (D22). The control *show every ticket* sets `showAll`; then every ticket shows and `hidden` is 0. The control is component state, off on each load, as the sprint selection is.
- **GitHub and Bitbucket, unmatched.** When the reader has no host login, or the source states no assignee (Bitbucket answers `[]` for every ticket), it answers every ticket, as today, and a notice that names the reason, for example *jwloka is not a host login the board can read — showing every ticket.* A Bitbucket inbox therefore never shows empty because its tickets carry no assignee.
- **Jira, unmatched.** When no `jira:` spelling names the reader's handle, it answers the `inbox` rows, today's read, with no notice and no count (D23). Today's read is `assignee = currentUser()`, or `PLOT_JIRA_JQL` where an adopter sets it (`plot-host.sh:4684`); the inbox keeps whichever applies. So no Jira inbox widens at upgrade.
- ***Only my work*** applies `isMine` over the ticket arm on top of the answer, so with *show every ticket* on it hides the tickets assigned to somebody else and keeps the unassigned ones.

**The inbox cap.** `/api/fleet` carries at most 50 ticket rows (`ISSUE_LIMIT`, `fleet.ts:192`), and after the lanes spike the board applies the planned-ticket filter and that cap at its read. `waitingTickets` runs in the client over those rows, so `hidden` counts within the 50. Before the lanes index the board reads only 50 tickets, so no reader's ticket exists beyond them; with the index at up to 1000 open rows, an assigned ticket older than the 50 newest is not in the payload. That case is an Open Point below.

**The assignee filter comes before a project-wide Jira read (D20).** Today the Jira rows are the user's only because the Jira query reads `assignee = currentUser()` (`plot-host.sh:4684`). D20 makes the Discovery lanes project-wide, and the inbox reads the same rows as the lanes. So D9's default becomes this filter, and `tickets-and-stories-have-lanes` drops the clause only in `feature/the-lanes-read-the-whole-jira-project`, which waits on this plan's `feature/the-delivery-tab-filters-by-sprint-and-owner`. That slice keeps today's query as a second Jira read and stores its rows in the issue index as `inbox` (D23).

**Active sprint.** A shortcut, not a second rule. `fleet.sprints` holds only Active sprints, so "the active sprint's rows" is today's multiselect with every option selected, and `slugPassesSprintFilter` passes a row in any selected sprint, which is the union story Open Point 12 asks for. An *Active sprint* button beside the multiselect sets the selection to `activeSprintSelection(sprints)`, every slug of `fleet.sprints`, through the existing `setSprintFilter`; the rows, the exempt mark and the hidden count then come from the existing join. With no Active sprint the button is disabled and says *No sprint is Active.* The helper lives beside `sanitizeSelection` in `packages/board/src/app/lib/filters.ts`, where the join it feeds lives; moving that join into the domain changes no behaviour and is outside this plan.

**The verification row.** *Waiting on you* rows are per-branch `AgentRow`s, so a plan-level row is a new row kind, `verification`. It renders each entry of `fleet.verification.rows` with its plan, `reason`, `log` and `restart` command (`/plot-deliver --verify <slug>`), marks a `stopped` run, and shows one line when `verification.halted` is true: the fleet starts no verify run until a person restarts one. The rows come from `verificationRow` (`packages/domain/src/rules/auto-verify.ts:321`, signature `(slug, commit, store, log, now)`), which fleetd already writes to `.plot/state/auto-verify-in-flight.json`; the board decides nothing about them. This plan owns the Delivery tab, so the row is a slice here, and that slice closes #1640's *The board row* item (H7).

**Every view state is a domain property.** The tab, the Planning columns, which tickets *Waiting on you* shows and how many it hides, and whose a ticket is come from `boardTabOf`, `planningColumns`, `waitingTickets` and `ticketOwnership` in `@plot-pm/domain`, with unit tests. The *Active sprint* selection and the verification row's fields come from the payload through board helpers with unit tests. The components render them.

### Cost

- **Host and tracker calls.** Zero new calls per scan: the assignee rides the existing `issue-list` reads. On GitHub the nested `assignees` connection keeps a 100-issue page at about 1 GraphQL point.
- **Payload.** One login or email per assignee per ticket: at most 50 rows on `/api/fleet`, and at most 1000 rows in the issue index, about 25 KB. *Show released* adds nothing, because Released plans already ride `/api/board`.
- **The index version.** The raised `ISSUE_INDEX_VERSION` makes a stored index read as no index until the next fleet pass writes one, up to 22 minutes on a 1000-ticket Jira project (`tickets-and-stories-have-lanes.md:118`). During that window *Waiting on you* shows *the fleet has left no issue index to read*.
- **Shell.** The assignee slice adds no net shell lines; every other slice touches no shell.
- **Tests and docs of the rename.** 47 files under `packages/board/test` open the old `agents` value; they keep it and exercise the redirect, so no 47-file diff. Three files click a tab button by its old label and change: `agents-tab.browser.test.ts`, `mine-filter.browser.test.ts`, `unreachable-overlay.browser.test.ts`. `grep -rlE "Agents tab|Plans tab|Stories tab|tab=(agents|plans|stories|board)"` over `skills`, `docs`, `README.md` and `packages/board/src`, outside `docs/plans` and `docs/stories`, names 24 files. The rename changes the 17 current ones: 16 under `packages/board/src` and `skills/plot/scripts/plot-fleet-scan.sh`. The 7 dated release lists and sprint files keep their words, because they record what was true then.

### Open Points

- [x] How a tracker assignee matches the reader (story Open Point 7). — resolved by D21 and D22: a `jira:` spelling in `People`, the host login as the reader, and every ticket with a notice for an unmatched reader. `feature/people-names-a-tracker-account` builds the match as the `ticket` arm of `OwnedRow`.
- [x] *Active sprint* with more than one Active sprint (story Open Point 12). — resolved: the shortcut selects every Active sprint, and `slugPassesSprintFilter` passes a row in any selected sprint, so it shows their union, the story's default.
- [ ] *Only my work* over a branch without a PR and over a build. D9 names both; no fact on such a row names an owner (`mine-filter.ts:73-86`), and every source found costs a spawn per branch per scan or reads the operator's own git identity, which every fleet commit carries. This plan narrows *Only my work* to rows with an owner and leaves both shown. Recommended answer: a later plan reads a branch through the registry agent whose desk holds it, so `agentOwnership` (`ownership.ts:99`) answers it with zero host calls, and a build follows its branch; that plan first measures how many branch rows have such an agent.
- [ ] Assigned tickets beyond the 50-row inbox cap. With the lanes index holding up to 1000 open rows, an assigned ticket older than the 50 newest is not in `/api/fleet`. Recommended answer: the board's read orders the reader's tickets ahead of the cap, because the server holds the reader (`ServerInfo.hostUser` and `people`, `mine-filter.ts:119`), and the count names the rows the cap left out.
