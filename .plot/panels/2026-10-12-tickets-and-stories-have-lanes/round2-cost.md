## New defects

1. **`github 1 -> 2` is not the count, and the plan does not say what it costs the PR cadence.** Must change. (a) The plan says the open read "was already counted" (plan `:63`). The table says the opposite: `github: 1` counts only `pr-list`, and "the GitHub `issue-list` and `runs` calls ride the same GraphQL budget and the board's own measurement treats the refresh as one unit" (`pr-refresh.ts:182-185`). Bitbucket's 4 counts its issue call as one question (`:186-188`). By the Bitbucket rule the GitHub pass is 3 questions (pr-list, open, closed); by the GitHub rule it stays 1; neither rule gives 2. (b) The page count is also wrong: the plan says "1 closed page" (`:63`), and this repository closed 154 issues in the last 14 days, so the closed read is 2 pages. With the per-page records the plan adds (`:54`), one pass on this repository writes 1 + 2 + 2 = 5 GraphQL records to the ledger against a declared cost of 2. (c) The cadence reads that ledger. `spend-rate` sums every bucket of the git-host connector (`plot-host.sh:5236-5240`), fleetd reads it each pass (`pr-refresh.ts:1341`), and `othersPerHour` treats every record above `cost x refreshes` as another spender (`cadence.ts:97-101`). By the arithmetic of `targetStretch` and `cadenceStretch` (`cadence.ts:120-148,173`), 3 undeclared records per pass at a declared cost of 2 settle at a stretch of 2.5: a quiet account refreshes PRs every ~300 s, against ~120 s today (today the board's undeclared `issue-list` already settles a stretch of 2). On a busy account the ceiling is `MAX_CADENCE_STRETCH = 8` (`cadence.ts:32`), so doubling the base moves the ceiling from 480 s to 960 s; this account spent 1145 GraphQL requests in the last hour, so it sits at the ceiling now. The cost of the issue fold is therefore paid in PR, merge and `checks green` latency on every GitHub repository that runs fleetd, and the plan does not say so. (d) The table is keyed by git host, and the issue cost is keyed by issue source: a GitHub repository that declares `Tracker: jira` makes no GitHub issue read, so `github: 2` over-declares there, which the table's own comment names as the mirror failure (`pr-refresh.ts:204-206`). The plan must give the per-pass count as a function of issue source and pages, and choose: price it honestly and state the PR latency it buys, or run the issue fold on its own gate with its own cost (issues are signals that a 14-day Done lane does not need at 60 s), behind the same backoff.

2. **The project-wide Jira read (D20) has no figure and no pace.** Must change. The plan says Jira spend "this table does not pace" (`:63`). It is also invisible to every cadence: `spend-rate` defaults to the git-host connector (`plot-host.sh:5233`), and `budget_record_jira` records basis `unknown` (`:2688-2691`). Before D20 the open read is one person's tickets in one page (`:4686-4690`, "small by construction"). After D20 it is every unresolved ticket of the declared projects, up to `ISSUE_INDEX_OPEN_LIMIT = 1000` (plan `:56`): up to 10 pages of about 100 rows, plus the 14-day closed pages, on every pass. At the fleetd gate that is 30 passes an hour on GitHub (at the 120 s base the plan sets) and 15 on Bitbucket, so up to about 330 and 165 Jira requests an hour per machine, before any second board or worker. The plan must state this figure for the D20 slice and bound it, for example by the separate issue gate in defect 1.

3. **The acceptance contradicts the toggle read.** Must change (wording). Acceptance `:134` says "With a fleet running, the board makes no `issue-list` call". The toggle read is a board call: `GET /api/issues/closed` calls `issueListClosed` (plan `:67`), which goes through `plot-host.sh issue-list --state closed` (`tracker-shell.ts:145`, plan `:44`). Either the acceptance names the periodic read only, or the test fails the first time a person turns the toggle on. The same paragraph states no cache and no backoff for the toggle read: with `?archived=1` in a shared URL, every page load in every tab asks up to 10 pages. The plan should say the read holds the PR backoff and caches its answer for a stated time.

4. **The open rows grow on the 4 s payload.** Open point. The inbox `entry.issues` rides `/api/fleet` (`fleet.ts:6707`), polled every 4 s per tab (`App.tsx:32`). Today it holds at most 50 rows (`fleet.ts:190`). The plan raises the open read to 1000, keeps planned tickets, and moves the inbox filter to the board's read (plan `:56`); D22 shows every ticket to an unmatched reader, and D20 makes the Jira set project-wide. The plan says no closed row rides `/api/fleet` (`:67`) and says nothing on the open rows. D19 states that it "bounds the index file, the pass and the payload" (story `:94`); the plan should name which payload carries the open lanes and the bound on `/api/fleet`.

5. **A rate-limited issue read does not hold the gate.** Open point. The plan keeps the issue fold on the PR gate "so the issue lookup cannot become a second cadence" (`fleet.ts:1692-1695` gives the reason today), and says a failure of one does not blank the other (plan `:60`). It does not say whether an issue read that the host refuses with a rate limit sets the backoff that `refreshPrs` owns. With up to 4 issue pages per pass against 1 PR call, the issue read is the call most likely to hit the limit.

6. **The Bitbucket saving is real and unstated.** Open point, in the plan's favour. Under a fleet, the board stamps its gate with `PR_REFRESH_MS` and not the backend's cost (`fleet.ts:1648`), so today it calls `bb issue list` every 60 s, 60 requests an hour outside the 4x pacing. Moving that call into fleetd's 240 s pass saves about 45 Bitbucket requests an hour per board. The plan should state this number beside the GitHub cost, because it is the case the table's 429 measurement was about (`pr-refresh.ts:157-161`).

## Ready to approve?

No. The revision closes most of round 1's cost findings: the git-host path, the bounded sets, the file name, the miss path and the closed rows on the 4 s payload are sound. The accounting it adds is not the count. `github 1 -> 2` disagrees with the table comment it changes, with the page count measured on this repository (154 closed in 14 days, so 2 pages), and with the per-page ledger records the plan itself adds; through `cadenceStretch` that difference slows every GitHub PR refresh, and the plan does not name that cost. The D20 Jira read has no figure. Defects 1–3 must change before approval; one design choice (a separate issue gate with its own cost, or an honest price with its PR latency) resolves 1, 2 and 5 together.
