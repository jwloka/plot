Also `reachFrom` in `packages/board/src/server/entry/branch-state.ts` maps the scan's `partial` host word to `failed`; the plan does not name `partial`.

Manifesto question 2 is the reason it matters: a repository with no git host (`HostReach` `unasked`, no `pr-list`) that lands work by merge commit has zero-ahead-behind as its ONLY merge signal, and the literal rule removes it.

5. **`open` for a zero-ahead ref is claim-safe but reaches two consumers differently.** The worker loop cuts the branch from `origin/main` (`plot-worker-loop.sh` ~:884-:890, `checkout -b`), so its later push fast-forwards the older ref and is not rejected; `claim.ts` pushes an empty claim commit on top of `origin/main`, also a fast-forward. No duplicate, no rejected push. But the supervisor queue's `claimedBranches` (`registryd-main.ts:534-541`) treats ANY existing ref as claimed, so a zero-ahead ref reading `open` is offered by `plot-fleet-scan.sh --next` and held `not-claimable` by the supervisor, while the board's `open` arm writes *eligible — nobody has taken it*. That is the #1090 stuck state rendered as NOT STARTED. The plan's first "does NOT do" bullet says the queue *"hands out a slice whose ref exists"*; for the supervisor that is the opposite of the code. The plan should state which of the two it accepts. The fix also defeats the operator's recovery move recorded in the plan's own Notes (an empty ref pushed at `origin/main` to hold a slice, #1100): after the fix that ref reads `open` and `--next` offers it.
